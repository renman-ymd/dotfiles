## A throwaway macOS VM on the Air

Research date: 2026-11-02. Versions seen: Tart 2.41.1 upstream (2026-10-15) and 2.37.0 in nixpkgs, Lume 0.6.1 (CHANGELOG 2026-10-04, `main` at [ebd3393](https://github.com/trycua/cua/commit/ebd3393112798507018c3c22757546d322fd098f)), UTM 5.0.8 (2026-10-17), VirtualBuddy 2.2.1 (2026-10-19), macosvm 0.2-3 (2026-06-22), vfkit 0.6.3 in nixpkgs (v0.6.4 upstream), macOS Tahoe 26 software licence agreement (the PDF Apple serves today; it matches the copy installed on this Mac). Host: Mac17,4, 32 GB RAM (`sysctl hw.memsize` = 34359738368), macOS 26.5.2 (`sw_vers`), 366 GiB free on the Data volume (`df -h /System/Volumes/Data`; `/` itself shows the sealed system volume). "nixpkgs-unstable" means the branch head read on 2026-11-02 (revision 5c9de89); the repo's locked nixpkgs is [e62746b](https://github.com/NixOS/nixpkgs/commit/e62746b0b472753ef019baceab6f1e2e52014980) (`flake.lock`, `lastModified` 1793225069). Both carry the same version of every package named here. Source trees were read at the tags named in the links. Tools were run only for `--version` and `--help`; no VM, IPSW or image was created, downloaded or started. Registry manifests and a `HEAD` request on one IPSW were the only network reads of images. Anything marked **Unverified** is not established by a primary source.

### 1. Candidates and what each can script

Five things matter to ticket 13: create a guest without the GUI, clone or snapshot it, start it headless and reach it over SSH, delete it, all from a script.

**Tart** ([README and docs](https://github.com/openai/tart/blob/2.41.1/docs/quick-start.md); the project moved from `cirruslabs/tart` to `openai/tart`, and GitHub redirects the old URL)

- **Create:** `tart create --from-ipsw=<path|url|latest> <name>` ([Create.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Create.swift)). It installs macOS but then stops at Setup Assistant: the docs say you "need to manually go through the macOS installation process", then enable auto-login, Remote Login and passwordless sudo by hand ([quick-start](https://github.com/openai/tart/blob/2.41.1/docs/quick-start.md)). The unattended path (`tart run --provisioning-opts=username=…,password=…,enablesRemoteLogin=true`) requires a macOS 27 host and a macOS 27 guest ([Run.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Run.swift); Apple's [`VZMacGuestProvisioningOptions`](https://developer.apple.com/documentation/virtualization/vzmacguestprovisioningoptions) is "macOS: 27.0.0 -" and earlier guests "ignore these settings"). So on 26.5.2 the GUI-free route is a published image.
- **Published image:** `tart clone ghcr.io/cirruslabs/macos-tahoe-vanilla:<tag> <name>` pulls and clones in one step. The quick-start documents `admin`/`admin` for GUI, console and SSH. The [Packer template](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/templates/vanilla-tahoe.pkr.hcl) that builds the vanilla image drives Setup Assistant by keystrokes, creates `admin`/`admin`, enables Remote Login and Screen Sharing, writes `/etc/sudoers.d/admin-nopasswd`, sets auto-login and disables the screen lock; its FileVault pane is skipped ("Mac Data Will Not Be Securely Encrypted"). Unverified: that the already-published `26.5` image was built from this revision of the template. Registry tags for `macos-tahoe-vanilla` read on 2026-11-02: `latest`, `26.0` to `26.5`, `26.6.1`, `26.6.2` (`latest` is 26.6.2, newer than this host; see §3).
- **Snapshot/clone:** there is no snapshot command (the `tart --help` of 2.37.0 lists create, clone, run, set, get, list, login, logout, ip, exec, pull, push, import, export, prune, rename, stop, delete, suspend). `tart clone <vm> <vm2>` is a copy-on-write APFS clone, "a cloned VM won't actually claim all the space right away" ([Clone.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Clone.swift)), so a clone of a stopped VM is the snapshot. `tart suspend` (SIGUSR1 to the `tart run` process, [Suspend.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Suspend.swift)) saves RAM state, and needs the VM started with `--suspendable`.
- **Headless and SSH:** `tart run --no-graphics <name>` ("Don't open a UI window", [Run.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Run.swift)); `tart ip <name> --wait <s>` reads the host's DHCP lease file for the guest's MAC address ([IP.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/IP.swift)); then plain `ssh`, with `sshpass` for the password ([quick-start](https://github.com/openai/tart/blob/2.41.1/docs/quick-start.md)). `tart exec` is an alternative only when Tart's guest agent runs in the guest, and the docs say non-vanilla images have it ([Exec.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Exec.swift)); vanilla ones do not. Host prerequisite for headless runs: on macOS 15 and later Virtualization.framework needs an unlocked `login.keychain` on the host. Logged into the Air's GUI session that is the case ([FAQ](https://github.com/openai/tart/blob/2.41.1/docs/faq.md)). A macOS "Local Network" prompt can also appear the first time another tool connects to the guest; its non-interactive workaround edits system preferences with `sudo defaults write` (same FAQ), which this repo's rules would make a decision for Renaud.
- **Stop and delete:** `tart stop <name>` (graceful, 30 s default timeout, then forced, [Stop.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Stop.swift)); `tart delete <name>…` ([Delete.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/Commands/Delete.swift)). `tart run` exits when the guest stops (`guestDidStop` → `sema.signal()`, [VM.swift](https://github.com/openai/tart/blob/2.41.1/Sources/tart/VM.swift)).
- **Verdict on scriptability:** every step after the base image exists is a plain command with an exit code.

**Lume** (Cua's CLI; `trycua/lume` redirects into the `trycua/cua` monorepo, `libs/lume`; [README](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/libs/lume/README.md), [CLI reference](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/docs/content/docs/lume/reference/cli.mdx))

- **Create without the GUI, on macOS 26:** `lume create <name> --ipsw <path|latest> --unattended tahoe`. Lume installs from the IPSW, boots once, mounts the guest's Data volume on the host and writes the `lume` account, SSH, auto-login and no-sleep settings as plain files, then boots again and finishes when SSH answers ([how Lume works](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/docs/content/docs/lume/concepts/how-lume-works.mdx)). The README says "Tahoe is E2E verified from a local IPSW". Default credentials `lume`/`lume`. This is the only candidate that goes from Apple's IPSW to an SSH-ready guest with no human and no third-party image on this host.
- **Clone:** `lume clone <name> <new>`; the controller's comment says "uses APFS clonefile for disk.img" ([LumeController.swift L531](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/libs/lume/src/LumeController.swift#L531)); the how-it-works page says `lume clone` copies disk and NVRAM together. No snapshot command in the reference.
- **Headless and SSH:** `lume run <name> --display none --detach` (optionally `--vnc disabled`); `lume get <name> --format json` gives the IP; `lume ssh <name> '<cmd>'` runs one command and returns its exit status, handling the password itself (no `sshpass`); `lume cp`, `lume shutdown` and `lume restart` go over the same SSH. `lume stop <name> --force`, `lume delete <name> --force` ([CLI reference](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/docs/content/docs/lume/reference/cli.mdx)).
- **Caveats:** the sudo password is the SSH password (`lume`), not passwordless ([CLI reference](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/docs/content/docs/lume/reference/cli.mdx), `lume shutdown`); telemetry to PostHog EU is on by default and `lume config telemetry disable` or `LUME_TELEMETRY_ENABLED` turns it off ([README](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/libs/lume/README.md)); the project is young (0.6.x, nightly channel, fast-moving docs). Unverified: that `--ipsw latest` picks an image the 26.5.2 host supports; pass a local IPSW of the host's version instead (`lume ipsw` prints the URL).

**UTM 5.0.8** (`utmctl`; [source at v5.0.8](https://github.com/utmapp/UTM/blob/v5.0.8/utmctl/UTMCtl.swift))

- `utmctl` has list, status, start, suspend, stop, attach, file, exec, ip-address, clone, delete, usb and a `snapshot` group. It drives the UTM app (Scripting Bridge), so the app has to be present.
- Its macOS-guest features are mostly macOS 27 only. Snapshots for Apple-backend VMs are behind `#available(macOS 27, *)` ([UTMSnapshotService.swift](https://github.com/utmapp/UTM/blob/v5.0.8/Services/UTMSnapshotService.swift)); `--disposable` needs 27 ([UTMAppleVirtualMachine.swift](https://github.com/utmapp/UTM/blob/v5.0.8/Services/UTMAppleVirtualMachine.swift)); `--provision-*` says "Requires macOS 27 or later on both the host and the guest" ([UTMCtl.swift](https://github.com/utmapp/UTM/blob/v5.0.8/utmctl/UTMCtl.swift)). On 26.5.2 that leaves clone, start, stop, delete, and `ip-address` (by ARP for Apple VMs; "no guest agent available").
- AppleScript can create an Apple-backend macOS VM from an IPSW ([UTMScriptingCreateCommand.swift](https://github.com/utmapp/UTM/blob/v5.0.8/Scripting/UTMScriptingCreateCommand.swift)), but Setup Assistant then needs the GUI. Unverified: that the first-boot install runs without a window.
- Ticket 06 removed UTM from mac-apps; it would come back only as a Nix-store app.

**VirtualBuddy 2.2.1:** a GUI app (restore-image wizard, "Save and restore macOS virtual machine state"); its [README](https://github.com/insidegui/VirtualBuddy/blob/2.2.1/README.md) documents no CLI. For cloning it suggests duplicating the VM in Finder. Not scriptable as documented; not researched further.

**macosvm 0.2-3** ([README](https://github.com/s-u/macosvm/blob/0.2-3/README.md)): a CLI. `macosvm --disk disk.img,size=32g --aux aux.img --restore <ipsw> vm.json` installs macOS, but "you need the GUI to get through" Setup Assistant; later runs can be headless (`--ephemeral` discards changes; `cp -c disk.img master.img` is the CoW clone; `--mac` plus `arp -a` finds the IP; a launch-script hook exists since 0.2-2). Guests "must be equal to or lower than the host version" per its README. Ships a binary tarball; not a nixpkgs package.

**vfkit 0.6.3:** runs a macOS guest only from an already-installed bundle (`--bootloader macos,machineIdentifierPath=…,hardwareModelPath=…,auxImagePath=…`); it cannot install from an IPSW, and its docs say macOS guests "can't run headlessly" and that "it's not possible to run more than two macOS VMs at a time" ([usage.md](https://github.com/crc-org/vfkit/blob/v0.6.3/doc/usage.md)). Rejected.

**Not assessed:** Parallels Desktop, VMware Fusion and Anka are commercial products; the only Parallels attribute in nixpkgs is `prl-tools` (guest tools, `nix search`), so none could run from Nix. Unverified whether any is worth a licence for this.

**Implications for this repo:** Tart and Lume are the two candidates that script every step; Lume alone builds the base from Apple's IPSW without a human on this host. UTM, VirtualBuddy, macosvm and vfkit each need the GUI for first setup or lack snapshots on 26.5.2.

### 2. Nix: availability and whether a Nix build can run VMs

| Tool | nixpkgs attribute | Version (unstable 2026-11-02 / locked) | Upstream latest |
|---|---|---|---|
| Tart | `tart` | 2.37.0 / 2.37.0 | 2.41.1 |
| UTM | `utm` | 5.0.8 / 5.0.8 | 5.0.8 |
| vfkit | `vfkit` | 0.6.3 / 0.6.3 | 0.6.4 |
| Lume | none (`nix eval` finds no attribute) | | 0.6.1 stable |
| VirtualBuddy | none | | 2.2.1 |
| macosvm | none | | 0.2-3 |

Checked with `nix eval …#<attr>.version` against both revisions, and `nix search` on 2026-11-02 for lume, virtualbuddy, macosvm, anka and parallels.

- **Tart:** [package.nix](https://github.com/NixOS/nixpkgs/blob/e62746b0b472753ef019baceab6f1e2e52014980/pkgs/by-name/ta/tart/package.nix) does not build Tart. It fetches the upstream `tart.tar.gz` release (`sourceProvenance = binaryNativeCode`), copies `tart.app` to `$out/Applications` and makes `$out/bin/tart` a `makeWrapper` around `tart.app/Contents/MacOS/tart`. Its comment: that binary "is required to be used in order to trick macOS to pick tart.app/Contents/embedded.provision profile for elevated privileges". I confirmed on this Mac (read-only): `codesign -dv --entitlements -` on the store path shows the Cirrus Labs signature (team 9M2P8L4D89), `com.apple.security.virtualization` and `com.apple.vm.networking`, `codesign --verify --deep --strict` passes, and `embedded.provisionprofile` is present. So a Nix store copy keeps the entitlements Apple granted through the profile; the entitlement is not lost by being in `/nix/store`. Unverified: that macOS accepts that profile when the app runs from `/nix/store` (needs an actual `tart run`).
  - **Why ad hoc signing alone would not do:** Tart's own development build is signed ad hoc with only `com.apple.security.virtualization` and `get-task-allow` ([tart-dev.entitlements](https://github.com/openai/tart/blob/2.41.1/Resources/tart-dev.entitlements), [run-signed.sh](https://github.com/openai/tart/blob/2.41.1/scripts/run-signed.sh)); `com.apple.vm.networking` is in the production entitlements together with the provisioning profile ([tart-prod.entitlements](https://github.com/openai/tart/blob/2.41.1/Resources/tart-prod.entitlements)). The virtualization entitlement itself can be ad hoc: nixpkgs' `vfkit` does `codesign --entitlements vf.entitlements -f -s -` ([package.nix](https://github.com/NixOS/nixpkgs/blob/5c9de89ec55bff981cb8da1a4ee92b10f1438ffc/pkgs/by-name/vf/vfkit/package.nix)).
  - **Unfree:** the licence is FSL-1.1-ALv2, which nixpkgs marks unfree. `nix run nixpkgs#tart` fails with "Refusing to evaluate package 'tart-2.37.0' … unfree license"; `NIXPKGS_ALLOW_UNFREE=1 nix run --impure nixpkgs#tart -- --version` printed `2.37.0` (observed). Flake-pinned form: `nixpkgs.legacyPackages.aarch64-darwin` with `config.allowUnfree`.
  - **Self-sign hook:** per the memory note, this repo re-signs Home Manager apps with the nix-selfsign certificate, and apps carrying a provisioning profile must be skipped (as for Zen). `tart.app` carries one, so do not install Tart through Home Manager or nix-darwin without adding it to that skip list; `nix run` or `nix shell` avoids the question. Re-signing would drop the profile; **Unverified** for Tart specifically.
  - **Version lag:** nixpkgs is four minor versions behind upstream (2.37.0 vs 2.41.1). The commands used below exist in 2.37.0's `--help` (observed). Running even `--help` created an empty `~/.tart` on this Mac (I removed it); `TART_HOME` relocates the store ([FAQ](https://github.com/openai/tart/blob/2.41.1/docs/faq.md)).
- **UTM:** [package.nix](https://github.com/NixOS/nixpkgs/blob/e62746b0b472753ef019baceab6f1e2e52014980/pkgs/by-name/ut/utm/package.nix) unpacks the upstream `UTM.dmg` into `$out/Applications` and wraps the binaries in `$out/bin`. Same pattern as Tart: the signed app, not a source build.
- **Lume:** not in nixpkgs. The official route is `curl … cua.ai/lume/install.sh | bash`, which installs to `~/.local/bin` and `~/.local/share/lume` and by default sets up a background LaunchAgent (`--no-background-service` skips it) ([install.sh](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/libs/lume/scripts/install.sh)). Its entitlements are the same two as Tart's ([lume.entitlements](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/libs/lume/resources/lume.entitlements)). Unverified: whether the release tarball runs from a store path via a hand-written `fetchurl` derivation (nobody has tried it in a primary source); a source build would need Swift and signing.

**Implications for this repo:** Tart is the only recommended candidate that runs ephemerally from Nix with its signature intact. Lume would be an ad hoc install outside Nix.

The macOS inside any guest is under Apple's licence, not the tool's. Whether Cirrus Labs may publish macOS images on `ghcr.io` is a question for them; I did not assess it.

**Apple's macOS licence** ([Tahoe 26 SLA](https://www.apple.com/legal/sla/docs/macOSTahoe.pdf); the same §2B(iii) text is in `/System/Library/CoreServices/Setup Assistant.app/Contents/Resources/en.lproj/OSXSoftwareLicense.html` on this Mac): §2B(iii) grants "up to two (2) additional copies or instances of the Apple Software … within virtual operating system environments on each Apple-branded computer you own or control that is already running the Apple Software, for purposes of: (a) software development; (b) testing during software development; (c) using macOS Server; or (d) personal, non-commercial use". Service-bureau, time-sharing and similar uses are excluded, as is running iOS, iPadOS, watchOS or tvOS in a VM. My reading, not legal advice: testing Renaud's own install and remove scripts on his own Air fits (b) and (d); the question of whether a work-machine script counts as "personal, non-commercial" is Renaud's. **Unverified** beyond the text.

**Hardware and count**

- macOS guests need an Apple-silicon host: Apple's [Virtualize macOS on a Mac](https://developer.apple.com/documentation/virtualization/virtualize-macos-on-a-mac) page is titled "Configure and run macOS guests on Apple silicon".
- Two at once: the licence says two; the framework enforces a limit, surfacing as [`VZError.Code.virtualMachineLimitExceeded`](https://developer.apple.com/documentation/virtualization/vzerror/code/virtualmachinelimitexceeded) ("Unable to create an additional VM"); vfkit's docs call two "hardcoded limitations in the Apple Virtualization framework" ([usage.md](https://github.com/crc-org/vfkit/blob/v0.6.3/doc/usage.md)). One VM at a time is enough here, leaving one slot spare.
- **A live bug on this OS:** Apple Developer Forums [thread 830119](https://developer.apple.com/forums/thread/830119) (June to July 2026, macOS 26.5, M4 Max) reports that after a guest-initiated shutdown the framework later returns code 6 (`VZErrorVirtualMachineLimitExceeded`) with no VM running, suspecting the kernel counter `hv_apple_isa_vm_quota` is not decremented; only a host reboot helps. Apple acknowledged it (FB22967193) and has offered no workaround. A second reporter hits it in CI when `tart stop` stops a `tart run --no-graphics` VM. Tart's own tracker has the same symptom on 26.3.1 with 2.31.0: [issue 1217](https://github.com/openai/tart/issues/1217) (run, shut down, run, shut down, third run fails), closed as a duplicate of [445](https://github.com/openai/tart/issues/445). Unverified: whether it hits at every shutdown or only some, and whether a guest `reboot` counts. This is the main operational risk of a loop of runs: budget a host reboot after a handful of runs, and make the harness stop and report the error text instead of retrying.
- Guest version: Apple's [`isSupported`](https://developer.apple.com/documentation/virtualization/vzmacosrestoreimage/issupported) on a restore image only says "whether the current host supports this restore image". macosvm's README states the guest must be "equal to or lower than the host version". Take the `26.5` tag, not `latest` (26.6.2), for a 26.5.2 host. Unverified that 26.5 is exactly the host's patch level; a newer-patch guest is not known to be a problem, only newer minor is suspect.

**Implications for this repo:** Tart's licence is fine for personal testing (and is why nixpkgs marks it unfree). Apple's licence allows two concurrent guests for testing or personal use; run one, and expect the quota bug.

### 4. What ticket 13 needs inside the guest

**Admin and SSH without a human**

- **Tart vanilla image:** `admin`/`admin`, Remote Login on, passwordless sudo, auto-login (template in §1). The harness can run `sshpass -p admin ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null admin@$(tart ip <vm> --wait 120) 'sudo -n sh -s' < script`; `sshpass` 1.10 is in nixpkgs-unstable and lists aarch64-darwin. Better, install the host's public key into the base image once; then clones carry it.
- **Lume:** `lume`/`lume`, sudo needs the password on stdin (`sudo -S`); `lume ssh` handles the SSH password.
- **Lix installer:** `ensure_root` re-executes itself as `sudo --set-home …` and keeps `NIX_INSTALLER*` variables ([cli/mod.rs](https://git.lix.systems/lix-project/lix-installer/src/commit/40ef289e4c83cbe671f523224d874137203d7400/src/cli/mod.rs)), so passwordless sudo and `--no-confirm` (README option table) are enough. Unverified: that a non-interactive, non-TTY SSH session runs the installer without prompts.
- **First connection:** the host's "Local Network" permission pop-up (see §1) may need one human click on the first run.

**Lix installer and the APFS volume**

- The macOS planner takes the root disk from `diskutil info -plist /` (`ParentWholeDisk`) and creates the volume with `diskutil apfs addVolume` ([planner/macos/mod.rs](https://git.lix.systems/lix-project/lix-installer/src/commit/40ef289e4c83cbe671f523224d874137203d7400/src/planner/macos/mod.rs), [create_apfs_volume.rs](https://git.lix.systems/lix-project/lix-installer/src/commit/40ef289e4c83cbe671f523224d874137203d7400/src/action/macos/create_apfs_volume.rs)). A VM's virtual disk is an ordinary APFS container (the Tart FAQ shows `diskutil list`, `diskutil apfs resizeContainer` inside guests), so nothing in this path is host-specific. **Unverified:** I found no primary source stating that Lix's or Determinate's installer runs in a Tart, Lume or Virtualization.framework guest. The first run of ticket 13 is that test.
- Encrypted volume: the planner calls `fdesetup isactive` and treats an active FileVault as a reason to encrypt (library path). The CLI's `--encrypt` option has `default_value = "false"`, so what the default CLI does under an active FileVault is unclear from the source alone; doc 03 and the local install (the "Nix Store" keychain item exists here) indicate it encrypts. Check `diskutil info "Nix Store"` and the keychain item after the FileVault-on run instead of assuming.

**FileVault in the guest (the keychain case from ticket 04)**

- Setup Assistant in a Tahoe guest shows the FileVault panes (the vanilla template steps through "You Mac is Ready for FileVault" and "Mac Data Will Not Be Securely Encrypted"), so the OS offers it. Howard Oakley (secondary source, [2024-07-18](https://eclecticlight.co/2024/07/18/securing-virtual-machines-on-apple-silicon/)) reports that macOS 15 VMs created from scratch can use full-strength FileVault tied to an Apple ID, and that older or upgraded VMs get a weaker form. Lume refuses to grow the disk of a FileVault guest ([how Lume works](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/docs/content/docs/lume/concepts/how-lume-works.mdx)), which implies such guests exist. For this test the strength does not matter: `fdesetup isactive` and the System keychain item do.
- Enabling it from a script: `fdesetup enable -inputplist` reads the user name and password from stdin, `-norecoverykey`/`-outputplist` handle the recovery key (`man fdesetup`, read from the local macOS 26.5.2 man page; no web copy was checked). **Unverified** that this succeeds in a Virtualization.framework guest without an Apple ID or the GUI; no primary source says. Plan on a one-time GUI step (`tart run` with its window, then System Settings) to make a separate FileVault base image, and treat the rest as the first-run experiment.
- **Reboot trap:** with FileVault on, [Apple's auto-login page](https://support.apple.com/en-us/102316) lists "FileVault is turned on" as a reason auto-login is unavailable. After a plain reboot the guest sits at the unlock screen and is unreachable over SSH. `fdesetup authrestart` ("restarts the system, bypassing the initial unlock", with `-inputplist`) is the documented bypass but "may not work on all systems" (local man page). Unverified in a guest.
- Install FileVault before Lix, because the planner reads FileVault state at plan time.

**Reboot (the `/nix` stub check)**

- A guest reboot is a normal `sudo shutdown -r now` (Lume's `lume restart` does exactly that over SSH, [GuestPower.swift](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/libs/lume/src/Commands/GuestPower.swift)). **Unverified** whether Virtualization.framework keeps the VM process alive across a macOS guest restart or reports `guestDidStop`; Tart exits `tart run` on `guestDidStop` and Apple's [doc](https://developer.apple.com/documentation/virtualization/vzvirtualmachinedelegate/guestdidstop(_:)) says only "the guest operating system stopped the VM". Write the harness so it copes with both: after sending the reboot, wait until SSH drops, then if the `tart run` process is gone start it again, then wait for `tart ip --wait` and SSH.
- Whether the shutdown-then-restart pattern feeds the quota bug in §3 is unknown.

**Snapshots in ticket 13's sense**

The before/after file manifests are taken inside the guest over SSH; the hypervisor only needs clone. Mapping to ticket 04's checklist: the "extra snapshot" for the in-place baseline run, and the separate failure-injection and Nix-store-parent runs, are each a fresh `tart clone` of the pristine base (cheap on APFS), run once and deleted. No RAM snapshot is needed.

**Implications for this repo:** the install/remove/reboot/diff loop is doable over SSH with either tool. Two cases need a human once: building the FileVault-on base image, and approving the first "Local Network" prompt. Everything else is unattended.

### 5. Cost on the Air

- **Free disk:** 366 GiB available on the Data volume, 351 GiB used of 926 GiB (`df -h /System/Volumes/Data`, 2026-11-02).
- **Tart vanilla `26.5`:** 23.8 GB compressed download (sum of the layers in the registry manifest, read anonymously), logical disk 50 GB (annotation `org.cirruslabs.tart.uncompressed-disk-size` = 50000000000). A `tart list` in Tart's tracker for a clone of `macos-tahoe-vanilla:26.2` shows disk 50, size 25 (GB) ([issue 445](https://github.com/openai/tart/issues/445), comment of 2026-03-20), so about 25 GB on disk. Remote images land in `~/.tart/cache/OCIs/`, local VMs in `~/.tart/vms/` ([FAQ](https://github.com/openai/tart/blob/2.41.1/docs/faq.md)); a clone from the cache is an APFS clone on the same volume, so base plus clone is close to 25 GB, not 50. Each run then adds only what the guest writes. Unverified: the exact local size of the 26.5 tag and of a Lix install (not measured; nothing was pulled).
- **Building from an IPSW instead:** one 26.6.2 IPSW is 19.8 GB (`Content-Length` of a `HEAD` request on Apple's CDN URL used by the vanilla template; I did not download it), plus a 50 to 100 GB logical disk (Tart default 50 GB; Lume default 100 GB for macOS, with "about 50 GB free disk" in its [quickstart](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/docs/content/docs/lume/quickstart.mdx)).
- **Planning figure:** pristine base (about 25 GB), a FileVault-on base (a clone that diverges, a few GB more), and a few live clones: roughly 30 to 60 GB at the peak, 10 to 15 % of the free space. An estimate from the figures above, not a measurement.
- **RAM:** Tart's default is 2 CPUs and 4 GB ([quick-start](https://github.com/openai/tart/blob/2.41.1/docs/quick-start.md)); Lume's is 4 CPUs and 8 GB ([CLI reference](https://github.com/trycua/cua/blob/ebd3393112798507018c3c22757546d322fd098f/docs/content/docs/lume/reference/cli.mdx)); Cirrus builds its vanilla image with 4 CPUs and 8 GB ([template](https://github.com/cirruslabs/macos-image-templates/blob/d6a3774b296fb80aa42c2a4885d6eb364a909ffd/templates/vanilla-tahoe.pkr.hcl)). Apple warns that less than the restore image's [`minimumSupportedMemorySize`](https://developer.apple.com/documentation/virtualization/vzmacosconfigurationrequirements/minimumsupportedmemorysize) gives "undefined behavior". `tart set <vm> --memory 8192 --cpu 4` (megabytes) leaves 24 GB for the host on a 32 GB Air.

**Implications for this repo:** disk and RAM are not a constraint; the VM-slot bug and the one-off GUI steps are.

### Recommendation

**Tart, run ephemerally from nixpkgs, on the `macos-tahoe-vanilla:26.5` image.** It is the only candidate that scripts clone, headless start, IP lookup, stop and delete, comes from Nix as the vendor-signed app, and starts from a prepared image with SSH, passwordless sudo and auto-login already set. Outline of a run:

1. Once: `NIXPKGS_ALLOW_UNFREE=1 nix shell --impure nixpkgs#tart nixpkgs#sshpass`, then `tart clone ghcr.io/cirruslabs/macos-tahoe-vanilla:26.5 base`; set `tart set base --cpu 4 --memory 8192`; install the host key once. Optionally build `base-fv` (FileVault on) by hand.
2. Per run: `tart clone base run-<id>`, then `tart run --no-graphics run-<id>` in the background, `tart ip run-<id> --wait 120`, and wait for SSH.
3. Over SSH: manifest before; Lix install (`sudo`, `--no-confirm`); manifest; the work-machine install script; remove script; manifest; `ls -ln /nix` and `launchctl print`; then `sudo shutdown -r now`, reconnect (restart `tart run` if it exited), check the stub after the reboot; copy results out.
4. Cleanup (also on any failure, with a trap): `tart stop run-<id>`, `tart delete run-<id>`. For the in-place baseline and failure-injection runs, clone `base` again.
5. If any start fails with `VZErrorVirtualMachineLimitExceeded` or "number of VMs exceeds the system limit", stop and ask Renaud to reboot the Mac.

**Fallback: Lume**, if Renaud does not want to trust a third-party image or the vanilla `26.5` tag misbehaves: `lume create base --ipsw <local 26.5 IPSW> --unattended tahoe` builds the base from Apple's file with no human, then the same clone, run, `lume ssh`, stop, delete loop. The cost is a non-Nix install (script into `~/.local`, telemetry to switch off, LaunchAgent to skip).

**Decisions that are Renaud's:** the third-party base image versus Lume's IPSW build; whether a host reboot after a few runs is acceptable; whether to allow the "Local Network" prompt workaround that edits system preferences.

### Unverified

- That a Nix-store `tart.app` actually starts a VM (signature and entitlements check out, launch not tried).
- That the published `vanilla:26.5` image matches the `vanilla-tahoe` template at the revision read, and its on-disk size.
- That Lix's installer works in a Virtualization.framework guest; that it encrypts the volume under FileVault by default.
- That FileVault can be enabled in a guest from a script, and that `fdesetup authrestart` works there.
- Whether a guest restart ends `tart run`, and whether guest restarts feed the VM-slot bug.
- That a non-TTY SSH session runs the Lix installer without prompts.
- The Apple licence reading for work-machine testing; Cirrus Labs' right to host macOS images; Parallels, Fusion and Anka.
- Whether Lume's release tarball runs from a Nix store path; whether its `--ipsw latest` suits a 26.5.2 host.
