### 1. Home Manager's `programs.claude-code`

**Where it is and what it covers.** The module is `modules/programs/claude-code/{default,options,lib}.nix`, introduced by the 2025-08-15 news entry, with `skills` added on 2025-11-25 ([locked tree](https://github.com/nix-community/home-manager/tree/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/programs/claude-code), [news 2025-08-15](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/misc/news/2025/08/2025-08-15_15-51-02.nix), [news 2025-11-25](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/misc/news/2025/11/2025-11-25_02-56-51.nix)). Paths below are relative to `configDir`, default `~/.claude` ([options.nix](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/programs/claude-code/options.nix)).

| Option | Writes | Kind of file |
|---|---|---|
| `settings` (JSON attrset) | `settings.json`, with `"$schema"` added; also gets `extraKnownMarketplaces` when `marketplaces` is set and `disabledMcpjsonServers` for disabled shared MCP servers | One symlink to a store file built with `install -Dm444` (read-only) |
| `context` (string or path) | `CLAUDE.md` | One symlink to a store file |
| `rules` (name to string or path), `rulesDir` | `rules/<name>.md`, or the contents of a directory | `rules`: one symlink per file. `rulesDir`: `recursive = true`, a real directory whose leaves are symlinks (via lndir) |
| `agents`, `commands`, `outputStyles`, and `agentsDir`, `commandsDir` | `agents/<n>.md`, `commands/<n>.md`, `output-styles/<n>.md` | Same two kinds as rules |
| `hooks` (name to script), `hooksDir` | `hooks/<name>`, marked executable | Symlinks to store files. This writes scripts only. Claude Code reads hook definitions from `settings.json` (key `hooks`), a plugin's `hooks/hooks.json` or skill/subagent frontmatter, not from a `hooks/` directory ([hooks docs, "Hook locations"](https://code.claude.com/docs/en/hooks#hook-locations)), so wiring goes in `settings.hooks` |
| `skills` (attrset, or a path to a directory of skill folders) | Attrset: string value gives `skills/<n>/SKILL.md`; path to a file gives `skills/<n>/SKILL.md`; path or store-path string to a directory gives `skills/<n>/` with all files. Path form: the whole directory under `skills/` | Text and file entries are one file symlink. Directory entries and the path form use `recursive = true`: real directories, symlinked leaves ([lib.nix `mkSkillEntry`](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/programs/claude-code/lib.nix), [default.nix](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/programs/claude-code/default.nix)) |
| `plugins` (name to package or path; a list is deprecated) | `skills/<name>` as ONE directory symlink to a wrapped copy of the plugin, loaded as a personal plugin | Needs Claude Code 2.1.157 or later. Older versions (2.1.76 to 2.1.156) get a `--plugin-dir` wrapper script instead, and `package = null` is treated as newest |
| `marketplaces` (name to package or path) | `extraKnownMarketplaces` in `settings.json` and `plugins/known_marketplaces.json` (with `lastUpdated` 1970 and `autoUpdate = false`) | Store symlinks. Claude Code itself rewrites `known_marketplaces.json` ([plugin docs](https://code.claude.com/docs/en/plugins/loading#find-plugins-on-disk)) |
| `mcpServers`, `lspServers`, `enableMcpIntegration` | A generated plugin (manifest name `hm`) holding `.mcp.json` and `.lsp.json`, linked as `skills/claude-code-home-manager` | One directory symlink. Not written to `~/.claude.json`, where `claude mcp add --scope user` writes. Values land in the world-readable store (master's option text says to keep secrets out) |
| `package` (nullable, default `pkgs.claude-code`), `finalPackage` | Puts the CLI in `home.packages`; `null` configures files only | |
| `configDir` | Moves everything above and exports `CLAUDE_CONFIG_DIR` when it differs from `~/.claude` | |

- **Every managed file is a read-only store symlink**, except the directories HM builds around them. `~/.claude` itself and `~/.claude/skills` stay real directories, because HM only links entries inside them. I checked this by evaluating the locked module on `aarch64-darwin` with `package = null`: `settings.json`, `CLAUDE.md`, `rules/code-comments.md` and `skills/inline/SKILL.md` came out as single-file symlinks, a store-path skill came out `recursive = true`, and the MCP plugin came out as the single entry `skills/claude-code-home-manager` (local evaluation; Lix `nix eval` on `builtins.getFlake` of the two locked revisions).
- **`inline` and `*Dir` options are mutually exclusive** (`rules` and `rulesDir`, and so on); the module asserts it. `skills` and plugin names must not collide either.
- **Platforms:** the module source has no platform conditions and no `meta.platforms` (`grep` for `platforms`, `isDarwin` and `isLinux` over the three files finds nothing), and the evaluation above ran on `aarch64-darwin`. The default package is restricted: nixpkgs' `claude-code` lists `aarch64-darwin`, `aarch64-linux` and `x86_64-linux` ([package.nix](https://github.com/NixOS/nixpkgs/blob/b6c98e9e6633ee64753b594ff4a5febf0367fc00/pkgs/by-name/cl/claude-code/package.nix)), and it is unfree. With `package = null` neither matters.
- **First activation over existing files:** the repo sets `home-manager.backupFileExtension = "backup-nix-home-manager"`, so HM moves each existing target to `<target>.backup-nix-home-manager` before linking ([files.nix, backup branch](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/files.nix#L353-L362)). The hand-written `~/.claude/settings.json`, `CLAUDE.md` and `rules/code-comments.md` would be renamed, not merged.

**Locked revision versus master.** The only differences are in `default.nix` and `options.nix`; `lib.nix` is identical ([master tree](https://github.com/nix-community/home-manager/tree/c58f54c733a7894d84fa2fdff26cc12088c4b78c/modules/programs/claude-code)).

- **New on master: `programs.claude-code.mutableSettings`** (default `false`, [options.nix](https://github.com/nix-community/home-manager/blob/c58f54c733a7894d84fa2fdff26cc12088c4b78c/modules/programs/claude-code/options.nix#L34)). When `true`, `settings.json` and `known_marketplaces.json` stop being store symlinks. A `home.activation.claudeCodeSettings` step, ordered after `linkGeneration`, merges the declared values into a writable file with `jq`-style `$dynamic * $static` (mode 600) through `lib.hm.generators.mkImpureConfigMerger` ([default.nix](https://github.com/nix-community/home-manager/blob/c58f54c733a7894d84fa2fdff26cc12088c4b78c/modules/programs/claude-code/default.nix#L332), [generators.nix](https://github.com/nix-community/home-manager/blob/c58f54c733a7894d84fa2fdff26cc12088c4b78c/modules/lib/generators.nix)).
  - **What the option text promises:** declared values, including permission arrays, replace existing ones; undeclared values and Claude's own marketplace timestamps survive; comments and formatting are lost; removing a declaration does not remove it from the file; switching back needs the writable files backed up or removed; it does not manage `~/.claude.json`.
  - **Not tested:** I read this and did not run it. The locked revision, `0b2f1129`, does not have it.
- **Also new on master:** the `mcpServers` text warning about secrets in the store, and a pointer to `programs.mcp.servers` with `env.<NAME>.file` for secrets.

**Implications for this repo.** All of it is Home Manager options, so it satisfies [ADR 0002](../../adr/0002-toolboxes-and-hosts-in-one-flake.md) and could sit in `modules/home` and run standalone. What the repo can own without fighting Claude Code is `context`, `rules`, `skills` and `agents`; `settings` is the one Claude Code also writes (section 2). The module sets up files only. It does nothing about `~/.claude.json`, auth, transcripts or auto memory.

**Unverified:** `mutableSettings` behaviour in practice, and the module on a Linux host (source has no platform branches, evaluation done on `aarch64-darwin` only).

### 2. What Claude Code writes at runtime, and read-only symlinks

All rows below come from the official docs unless marked.

| Path | Written when | If it is a read-only store symlink |
|---|---|---|
| `~/.claude/settings.json` | First change in `/config` to an option stored in user settings (theme and similar); `/model` saving a default; the `/memory` auto-memory toggle (`autoMemoryEnabled`); `claude plugin marketplace add` (`extraKnownMarketplaces`) and user-scope plugin installs (`enabledPlugins`) ([settings](https://code.claude.com/docs/en/settings#where-settings-live), [memory](https://code.claude.com/docs/en/memory#enable-or-disable-auto-memory), [plugin loading](https://code.claude.com/docs/en/plugins/loading#check-which-stage-a-plugin-reached), [discover plugins](https://code.claude.com/docs/en/discover-plugins)) | For a saved default: the docs say the change applies to the current session and is gone in the next one, and tell you to set the key in the tool that generates the file ([settings, troubleshooting](https://code.claude.com/docs/en/settings#a-change-you-made-in-claude-code-is-lost-in-new-sessions)). The docs do not describe the failure mode for the other writers (plugin install, marketplace add): unverified |
| `~/.claude.json` | Sign-in session, user and local-scope MCP servers, per-project trust and state, and the global keys that `/config` writes. Earlier versions are copied to `~/.claude/backups/` (five kept) ([claude-directory](https://code.claude.com/docs/en/claude-directory), [settings](https://code.claude.com/docs/en/settings#where-settings-live)) | Not managed by HM (the `mutableSettings` text says so). Local: it is 69 KB and was rewritten today at 10:19, so it is written constantly. Nothing documents a read-only variant; leave it alone |
| `~/.claude/CLAUDE.md`, `rules/` | Only by edits: `/memory` opens the file in your editor (and creates it if absent), and Claude's edit tool can change it when asked ([memory](https://code.claude.com/docs/en/memory#view-and-edit-with-%2Fmemory)) | Edits to a store file would fail (inference; the docs do not say). The docs do confirm symlinked `rules/` and `CLAUDE.md` load ([memory, symlinks](https://code.claude.com/docs/en/memory#share-rules-across-projects-with-symlinks)) |
| `~/.claude/projects/<project>/memory/` (`MEMORY.md` and topic files) | Auto memory, every session; exempt from the retention sweep ([memory](https://code.claude.com/docs/en/memory#auto-memory)) | Must stay writable. HM manages nothing under `projects/` |
| `projects/*.jsonl`, `file-history/`, `plans/`, `tasks/`, `debug/`, `paste-cache/`, `session-env/`, `shell-snapshots/`, `sessions/`, `history.jsonl`, `backups/`, `usage-data/` | Every session; most are swept after `cleanupPeriodDays` (default 30) ([claude-directory, application data](https://code.claude.com/docs/en/claude-directory#application-data)) | Must stay writable. `telemetry/` and `cache/` exist locally but I did not find them in the docs tables I read |
| `~/.claude/plugins/` (`known_marketplaces.json`, `installed_plugins.json`, `cache/`, `marketplaces/`, `data/`) | `/plugin` installs, marketplace adds and auto-updates ([plugin loading](https://code.claude.com/docs/en/plugins/loading#find-plugins-on-disk)) | HM's `marketplaces` writes `known_marketplaces.json` as a store file, which collides with this. Master's `mutableSettings` exists for that case |
| `~/.claude/skills/synced/`, `skills/.trash/` | When signed in with a claude.ai account in the terminal (Claude Code 2.1.273 or later), it downloads the account's skills into `skills/synced/` and moves removed ones to `.trash/`. `syncClaudeAiSkills: false` stops it ([skills, synced skills](https://code.claude.com/docs/en/skills#where-synced-skills-load)) | `skills/` must remain a real directory. HM's `skills` options keep it real, as evaluated in section 1. A whole-`skills/` single symlink would block this (inference) |
| `.claude/settings.local.json` (project) | "Yes, and don't ask again" on a permission prompt ([settings](https://code.claude.com/docs/en/settings#where-settings-live)) | Project file, outside HM |

- **Symlinked config is supported.** The changelog lists fixes for dotfile-managed links, including one that names nix/home-manager: 2.1.247 (sandbox cleanup deleted a symlinked `settings.json`), 2.1.181 (setting changes failed with ENOENT through a relative symlink under a symlinked `~/.claude`), 2.1.139 and 2.1.140 (hot reload of symlinked settings) ([changelog](https://code.claude.com/docs/en/changelog)). Skill folders may be symlinks to directories elsewhere ([skills, "Symlinked folders"](https://code.claude.com/docs/en/skills#where-skills-live)).
- **Hot reload:** Claude Code watches `~/.claude/skills/` and picks up edits inside the running session ([skills, live change detection](https://code.claude.com/docs/en/skills#live-change-detection)). Settings reload on save too ([settings](https://code.claude.com/docs/en/settings#when-edits-take-effect)).
- **Scope of the Claude desktop app:** the Code tab reads the same `~/.claude/settings.json`, `~/.claude.json`, skills and hooks ([desktop, shared configuration](https://code.claude.com/docs/en/desktop#shared-configuration)). Cowork and cloud sessions do not read `~/.claude/skills/` on this machine; they load skills synced from the claude.ai account ([skills, Cowork and cloud](https://code.claude.com/docs/en/skills#skills-in-cowork-and-cloud-sessions)). Desktop scheduled tasks run locally and do read it.

**Implications for this repo.** With a read-only `settings.json`, anything changed from inside Claude Code lasts one session. That is acceptable for stable keys (permissions, hooks, `autoMemoryEnabled`), and a bad fit if `/config` and `/model` choices are meant to stick. Options: leave `settings.json` unmanaged; manage it and accept the loss; or take `mutableSettings` from master (a Home Manager bump, which `CLAUDE.md` keeps as its own commit).

**Unverified:** failure modes of plugin install, marketplace add and `/memory` edits on read-only targets; whether the desktop UI writes `~/.claude/settings.json` for any of its own toggles.

### 3. The `skills` CLI

- **Which package:** `npm` package `skills` (bins `skills` and `add-skill`), source [vercel-labs/skills](https://github.com/vercel-labs/skills), MIT; `@latest` resolved to 1.7.2 on 2026-10-13, requires Node 22.20 or later ([npm registry](https://registry.npmjs.org/skills), [package.json](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/package.json)). `npx --yes skills@latest --version` printed 1.7.2 with a scratch `HOME`, and `--help` lists `add`, `use`, `remove`, `list`, `find`, `update` (alias `upgrade`), `init`, `experimental_install` and `experimental_sync`. nixpkgs at the locked revision has `skills` 1.6.0 (local `nix eval`).
- **What `add mattpocock/skills` does:** the source is parsed as GitHub `owner/repo`. Only `vercel`, `vercel-labs`, `heygen-com` and `remotion-dev` owners (and `zapier/connectors`) use the skills.sh snapshot download, so this repo is fetched with a git clone ([add.ts, `BLOB_ALLOWED_OWNERS`](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/add.ts#L1168-L1170), [blob.ts](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/blob.ts)). Skills are discovered under `skills/` (up to three levels, so the `skills/<bucket>/<name>` layout works) and through `.claude-plugin/` manifests ([README, discovery](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/README.md)).
- **Where it installs:** the Claude Code global directory is `$CLAUDE_CONFIG_DIR/skills`, else `~/.claude/skills` ([agents.ts](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/agents.ts#L11)); a project install goes to `./.claude/skills`. With one target agent it defaults to **copy mode**, which matches the plain copies in `~/.claude/skills`. With several agents it asks between symlink (a canonical copy in `.agents/skills`, linked to each agent) and copy ([add.ts](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/add.ts#L860-L887)). A skill folder is flattened to `<skills dir>/<name>/`, dropping `.git`, `__pycache__` and `metadata.json` ([installer.ts](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/installer.ts#L471-L477)).
- **Whether it records the source:** yes, in two places. Global scope (`-g` or the prompt answer) writes `~/.agents/.skill-lock.json`, or `$XDG_STATE_HOME/skills/.skill-lock.json`, with `source`, `sourceUrl`, `ref`, `skillPath` and `skillFolderHash` (the GitHub tree SHA of the skill folder) per skill ([skill-lock.ts](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/skill-lock.ts#L67)). Project scope writes `./skills-lock.json` with a SHA-256 `computedHash` of the files ([local-lock.ts](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/local-lock.ts#L69)). **Local observation:** neither `~/.agents/`, `~/.local/state/skills/` nor a `skills-lock.json` in `~` exists, so there is no record on this Mac of where the 21 folders came from (not checked: other directories where a project-scope lock might sit).
- **Update command:** `npx skills update [skills...]` (`-g`, `-p`, `-y`), as the upstream README also says ([vercel-labs README](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/README.md), [mattpocock README](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/README.md#L95)). `experimental_install` restores a project's skills from `skills-lock.json`.
- **How an update treats local edits: it does not look at them.** `update` compares the locked hash against the upstream hash only. If upstream changed, it runs `add <url> --skill <name> … -y`, and `add` empties the target with `rm -rf` and copies the upstream folder in ([update.ts, global](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/update.ts#L600), [update.ts, project](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/update.ts#L938), [installer.ts `cleanAndCreateDirectory`](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/src/installer.ts#L198-L205)). Edited skills are overwritten silently when upstream changes them, and left alone, edits and all, when it does not. The README tells you to re-run `add` to pick up new skills.
- **Collision with Home Manager:** the same `rm -rf` would remove an HM symlink or an HM-built directory under `~/.claude/skills/<name>` and put a real folder in its place, which breaks the next HM activation for that name. The `skills` CLI and HM should not manage the same skill names (inference from the code above).
- **Telemetry** is on unless `DISABLE_TELEMETRY` or `DO_NOT_TRACK` is set ([README](https://github.com/vercel-labs/skills/blob/671e8c320810d36fed80fac5f1a2c1bf7e82d812/README.md#telemetry)).

**Unverified:** which `skills` version and flags produced the current folders (no lock survives); I did not run `add` or `update`.

### 4. Consuming mattpocock/skills from Nix with local edits on top

(Local-only comparison, upstream commit `c55ee46` of 2026-09-18 used as the baseline.)

**Options.**

| | (a) Non-flake input + `applyPatches` | (b) Fork, jj bookmark rebased on upstream | (c) Vendored copy + diff script |
|---|---|---|---|
| In this repo | `inputs.skills = { url = "github:mattpocock/skills/<tag or rev>"; flake = false; }`, a `.patch` file, a few lines of Nix | Only a flake input `github:<you>/skills/<bookmark>` (`flake = false`) | The skill folders themselves, plus a script and an upstream input to diff against |

| Upstream update | `nix flake update skills` (or a new tag in the URL); the build is the check | `jj git fetch --remote upstream`, `jj rebase -b <bookmark> -d main@upstream`, `jj git push`, then `nix flake update skills` | Run the script; reconcile by hand or with a 3-way merge tool (needs the old upstream rev as base; not tested) |
| When upstream touched an edited line | Build fails with a rejected hunk. With default fuzz 2, a hunk can instead apply on shifted context without warning; `-F0` makes that fail too | The conflict is recorded in the rebased commit and resolved there; the fork keeps its own history | You see it only when you run the script |
| Measured here | 12 hunks; 0 fail on v1.3.1, 1 fails on main | Not measured; the same 1 hunk is where the rebase would stop | Not measured |
| Layout | Upstream is `skills/<bucket>/<name>`, so `programs.claude-code.skills` takes an attrset of `"${patched}/skills/<bucket>/<name>"` strings (documented usage); the path form needs a flat directory | Same | A flat folder works with the path form |
| Cost of staying behind | None: the lock pins it | None | None |
| Extra upkeep | Rewrite the patch when a hunk breaks | Maintain a public fork (or private if the input has credentials); every update is two steps (rebase, then lock bump) | Keep the script and copies in sync; upstream text sits in your repo |
| Contributing a fix back | Patch file is the PR basis | Cleanest: the bookmark is a branch | Manual |

- **A separate input (any option) means a separate `flake.lock` bump**, so under this repo's `CLAUDE.md` an update is its own `flake: update inputs` commit.
- **Fourth route, upstream's own plugin:** `.claude-plugin/plugin.json` lists the skill folders, and HM's `plugins.<name> = <store path>` links such a repo as a personal plugin ([plugin.json](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/.claude-plugin/plugin.json), [HM `mkPluginEntry`](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/programs/claude-code/lib.nix)). That carries the unedited skills, and plugin skills are namespaced `/mattpocock-skills:tdd` ([skills docs, "Plugin skills"](https://code.claude.com/docs/en/skills#where-skills-live)), so it changes how you invoke them, and a patched copy would still be needed for the jj edits. Whether the skills' references to each other by bare name still resolve when namespaced is unverified. Upstream's recommended install is `claude plugin install mattpocock-skills@claude-plugins-official`, which updates itself ([README](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/README.md#L35)).
- **Status quo (the `skills` CLI)** is the cheapest per update and the most destructive: no lock on this Mac, and `update` overwrites edits without a prompt (section 3).

**License.** MIT, "Copyright (c) 2026 Matt Pocock", unchanged between the baseline and `main` ([LICENSE](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/LICENSE), `package.json` also says MIT). It allows use, modification and redistribution, and requires the copyright and permission notice in "all copies or substantial portions". What follows for each option is my reading, not legal advice: (a) the repo holds only a patch with short context lines and the input points at upstream; (b) a fork carries `LICENSE` automatically; (c) vendored folders in a public repo are copies, so they need the notice (a `LICENSE` file beside them). The skills linked into `~/.claude/skills` from the store (a) have no notice unless the Nix expression adds one.

**Unverified:** that the jj rebase stops only at the `wayfinder` hunk (I patch-tested, not rebased); how often upstream rewrites the edited lines (tags v1.2.3 to v1.3.1 in about two months, `main` moves faster).

### 5. Claude Code from Nix, next to the desktop app

- **What the desktop app is:** the `claude` cask installs only `Claude.app`, with no `claude` binary ([cask API](https://formulae.brew.sh/api/cask/claude.json)). The app "includes Claude Code, so you don't need to install Node.js or the CLI", and the CLI is installed separately ([desktop quickstart](https://code.claude.com/docs/en/desktop-quickstart)). Local: the app (2.31226.1) downloads Claude Code into `~/Library/Application Support/Claude/claude-code/<version>/…/claude.app`; versions 2.1.293 and 2.1.295 are there, and `claude` is not on `PATH`.
- **Do they coexist:** yes by the docs: "You can run both simultaneously on the same machine, even on the same project", sharing `~/.claude`, `~/.claude.json`, skills, hooks, settings and project memory, with separate session lists ([desktop, coming from the CLI](https://code.claude.com/docs/en/desktop#coming-from-the-cli)). `claude --desktop` and `/desktop` hand sessions between them (needs Claude Code 2.1.285 or later, signed in with a subscription).
- **nixpkgs' `claude-code`:** at the locked revision it is 2.1.278 (build date 2026-09-19); `nixpkgs-unstable` `8edc0c72` has 2.1.293; the desktop app embeds 2.1.295 and npm `latest` is 2.1.296 (stable 2.1.287) ([locked manifest](https://github.com/NixOS/nixpkgs/blob/b6c98e9e6633ee64753b594ff4a5febf0367fc00/pkgs/by-name/cl/claude-code/manifest.zst.json), [unstable manifest](https://github.com/NixOS/nixpkgs/blob/8edc0c72e3a38faf5434e40d1f19431125fe4b30/pkgs/by-name/cl/claude-code/manifest.zst.json), [npm](https://registry.npmjs.org/@anthropic-ai/claude-code)). The CLI would therefore sit 17 patch releases behind the app unless the lock is bumped, and the shared state files are written by both. Whether an older CLI mishandles state a newer one wrote is unverified; the plugin docs show Claude Code drops install records "no version" can read ([plugin loading](https://code.claude.com/docs/en/plugins/loading#find-plugins-on-disk)), which hints at cross-version care.
- **What the package is:** a repack of Anthropic's own native binary, fetched from `downloads.claude.ai` and unpacked, wrapped with `DISABLE_AUTOUPDATER=1`, `DISABLE_INSTALLATION_CHECKS=1`, `USE_BUILTIN_RIPGREP=0`, and `ripgrep` and `procps` on `PATH`. It sets `__noChroot` on darwin; the Air's Lix reports `sandbox = false`, so that is moot here ([package.nix](https://github.com/NixOS/nixpkgs/blob/b6c98e9e6633ee64753b594ff4a5febf0367fc00/pkgs/by-name/cl/claude-code/package.nix)). It is unfree, so Hydra does not build it: the store path `cj8vvm9x…-claude-code-2.1.278` returned 404 from cache.nixos.org on 2026-10-13, meaning a local build (download plus unzstd). The native installer's own auto-update is off in this wrapper, so updates come only through the lock ([setup docs, auto-updates](https://code.claude.com/docs/en/setup#auto-updates)).
- **Home Manager's module with the app:** `programs.claude-code.package = null` writes the config files and installs no CLI; the desktop app reads them as shown in section 2. With `package = pkgs.claude-code` the module adds the CLI to `home.packages`. The module's personal-plugin path needs a version of 2.1.157 or later and assumes it for `null`.
- **Other ways to get a CLI:** the Homebrew cask `claude-code` (stable channel, 2.1.287 today, links `claude` into Homebrew's `bin`), which fits the repo's `homebrew.casks` habit but not its Nix-first one ([cask API](https://formulae.brew.sh/api/cask/claude-code.json), [setup docs](https://code.claude.com/docs/en/setup)); or Anthropic's native installer, which owns `~/.local/bin/claude` and auto-updates.

**Implications for this repo.**

- **Ticket 31 (what the repo owns):** HM can own `CLAUDE.md`, `rules/`, `skills/` (patched upstream plus `pr-and-issue-voice`), `agents/`, and `settings.json` either immutable (locked HM) or merged (master `mutableSettings`). It should not own anything under `projects/`, `plugins/`, `~/.claude.json` or the retention directories. The `skills` CLI and HM must not share skill names.
- **Ticket 11 (standalone work-machine home host):** `programs.claude-code` is a Home Manager option, so it fits ADR 0002. There is no desktop app there, so `package = pkgs.claude-code` is the only CLI route, which needs `allowUnfree` in that host's `pkgs` and excludes `x86_64-darwin`. Personal config such as the global `CLAUDE.md` should not ship to a work machine; that choice belongs to ticket 31.
- **The `claude` feature:** it is currently the desktop-app cask on darwin and a package on NixOS ([07-apps §4](07-apps.md#4-claude-desktop-on-linux)). The desktop app and the CLI are different things. A CLI feature (the HM module, usable on the work host too) would be separate from it. Whether the Linux desktop beta embeds Claude Code like the macOS app is unverified.

**Unverified:** version-skew behaviour between the nixpkgs CLI and the desktop's embedded copy; whether a Nix build of `claude-code` works on macOS with the sandbox on (the Air has it off).
