## The streaming box

Research date: 2026-10-07. Package versions below come from the `nixos-unstable` branch of nixpkgs and the Gentoo `master` tree as fetched today. The repo pins `nixpkgs-unstable`, which can lag `nixos-unstable` by a few days.

Fetching caveat: Crunchyroll's help center is now a JavaScript app and returns an empty shell to plain fetches. Mozilla's support site (SUMO) returns a bot challenge, which I did not try to bypass. I therefore read Crunchyroll's first-party articles through archive.org copies (dates given) and cite Mozilla's source tree and wiki instead of SUMO. The live pages may differ from the copies.

### 1. Crunchyroll on Linux

**Supported browsers and OS**
- Crunchyroll's "Why can't I watch videos on my browser?" article lists four supported browsers: Chrome 117+, Firefox 117+, Edge 117+ and Safari 16.1+. It names no operating systems and does not mention Linux. Source: [archived 2026-06-30](https://web.archive.org/web/20260630162031/https://help.crunchyroll.com/hc/en-us/articles/204537599-Why-can-t-I-watch-videos-on-my-browser), [live URL](https://help.crunchyroll.com/hc/en-us/articles/204537599-Basic-Video-Help-Browser-Streaming).
- The "Basic troubleshooting" article covers browsers, iOS/Android, Roku, Apple TV, Android TV, Fire TV, Nintendo Switch, PlayStation, Xbox and Chromecast. Its only OS-specific browser tip is a Windows/Mac refresh shortcut, and Linux does not appear. Source: [archived 2025-04-20](https://web.archive.org/web/20250420224131/https://help.crunchyroll.com/hc/en-us/articles/18934150961684-Basic-troubleshooting-for-common-issues-and-error-codes).
- Unknown: whether any Crunchyroll page lists desktop operating systems. The "[BSR] What platforms and devices are supported?" article shows up in search but I could not render it, and no archive copy exists. I cannot say whether it concerns the streaming service or a game.

**DRM**
- The "What do I do with a DRM Error?" article covers errors `MED` and `SHAK-6*`. It says most are fixed by updating the browser or enabling protected-content playback, and it links to Chrome, Firefox, Edge and Safari help pages. Source: [archived 2026-06-30](https://web.archive.org/web/20260630162030/https://help.crunchyroll.com/hc/en-us/articles/20757542357396-What-do-I-do-with-a-DRM-Error).
- The only DRM vendor that article names is Widevine, in the Edge instruction to enable the `edge-widevine-drm` flag. Crunchyroll's help pages do not say which DRM systems it uses per platform, so Widevine for Chrome and Firefox is implied rather than stated. Unverified for PlayReady and FairPlay.
- Secondary, Windows only, not Linux: [a Zen Browser issue](https://github.com/zen-browser/desktop/issues/14107) shows `KAT-6005` with an HTTP 403 from Crunchyroll's `/license/v1/license/widevine` endpoint. The reporter said the same account played in Opera. This suggests the license server can reject some browser builds even when a Widevine CDM is present. Treat it as an anecdote.

**Resolution**
- Crunchyroll's quality article offers only Highest, Moderate and Data Saver, with adaptive bitrate. It says exact resolutions such as 1080p are not selectable, and it documents no cap by platform or browser. Source: [archived 2026-05-30](https://web.archive.org/web/20260530173347/https://help.crunchyroll.com/hc/en-us/articles/36816426440980-What-video-quality-options-do-I-have).
- Unknown: the resolution Crunchyroll serves to a Linux browser using the Widevine software CDM. I found no first-party statement, and the Widevine documentation I could reach does not state per-level resolution policy. Third-party DRM vendor blogs say software-only desktop CDMs are limited to sub-HD, which I did not treat as a citation.

**Implications for this repo:** Linux is neither listed nor excluded. The supported-browser table is "Chrome, Firefox, Edge, Safari at version 117 or newer", so a stock Firefox or Chrome with a working Widevine CDM is the only configuration Crunchyroll could plausibly be asked to support. Skip Chromium forks. The box's job is one site, so keep the setup tiny and measure the real resolution once on the actual projector, for example with `chrome://media-internals` in Chrome. That test settles the 720p-versus-1080p question that no document answers. If it matters, it is the main argument for the officially supported TV-stick route in section 5.

### 2. Widevine on x86_64 Linux

**Google Chrome**
- Chromium's `widevine.gni` enables Widevine by default in Chrome-branded builds and makes the library CDM available on Linux x64 and arm64. It bundles the CDM only in Chrome and Chrome for Testing builds, and unbranded Chromium can opt in on non-Android platforms, subject to the Widevine LICENSE in that tree. The Linux installer's `BUILD.gn` ships `libwidevinecdm.so` when the CDM is bundled. Source: [widevine.gni](https://github.com/chromium/chromium/blob/main/third_party/widevine/cdm/widevine.gni), [installer BUILD.gn](https://github.com/chromium/chromium/blob/main/chrome/installer/linux/BUILD.gn).
- Google's stated Linux requirements for Chrome: 64-bit Ubuntu 18.04+, Debian 10+, openSUSE 15.5+ or Fedora 39+, on an x86-64 CPU with SSE3. Source: [Chrome install help](https://support.google.com/chrome/answer/95346?hl=en).

**Chromium and nixpkgs**
- `chromium` in nixpkgs takes `enableWideVine ? false`. When true, a wrapper derivation copies the `widevine-cdm` package's `WidevineCdm` directory into `libexec/chromium`. The comment says this avoids rebuilding Chromium. `proprietaryCodecs` defaults to true. Source: [chromium/default.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/applications/networking/browsers/chromium/default.nix).
- `widevine-cdm` lives at `pkgs/by-name/wi/widevine-cdm`. It is unfree, binary-only, and covers `x86_64-linux` and `aarch64-linux`. The x86_64 manifest pins version 4.10.3050.0, unpacked from a Google component-updater CRX (the last bump commit is dated 2026-06-05). Source: [package.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/wi/widevine-cdm/package.nix), [x86_64-linux.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/wi/widevine-cdm/x86_64-linux.nix), [meta.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/wi/widevine-cdm/meta.nix), [x86_64-manifest.json](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/wi/widevine-cdm/x86_64-manifest.json).
- `google-chrome` in nixpkgs repackages Google's `.deb` from `dl.google.com`, version 154.0.8037.97 today, unfree, x86_64-linux and aarch64-linux. It has a `libvaSupport ? true` option with a comment pointing at `--enable-features=VaapiVideoDecoder`. Source: [google-chrome/package.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/go/google-chrome/package.nix).
- nixpkgs' Hydra evaluation sets `allowUnfree = false` with the comment "Don't build packages marked as unfree". Source: [release.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/top-level/release.nix). That is consistent with `google-chrome` and `widevine-cdm` not being in the binary cache. I did not check cache.nixos.org directly. Unverified: whether the free `chromium` base package is cached.

**Firefox**
- Firefox fetches the Widevine CDM through its Gecko Media Plugin (GMP) updater. Mozilla's `widevinecdm.json` source manifest has a `Linux_x86_64-gcc3` entry pointing at Widevine 4.10.3050.0 on Google's component CDN, the same version nixpkgs packages. It has no Linux aarch64 entry. Source: [widevinecdm.json](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/content/gmp-sources/widevinecdm.json).
- `GMPUtils.sys.mjs` defines two Widevine plugin IDs. `gmp-widevinecdm` is the general one, and a comment says the `-l1` variant is only available for Windows x64. So Firefox on Linux uses the software (L3-class) CDM. Source: [GMPUtils.sys.mjs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/modules/GMPUtils.sys.mjs).
- Firefox's EME can be forced on and locked with the enterprise policy `EncryptedMediaExtensions` (`Enabled`, `Locked`; it maps to `media.eme.enabled`). On Linux the policy file goes in `/etc/firefox/policies`. Source: [policy templates](https://mozilla.github.io/policy-templates/).

**Firefox on NixOS**
- nixpkgs builds Firefox with EME enabled. `enableEMENagbar ? true` only matters because `--disable-eme` is passed when it is false. The Firefox wrapper contains no Widevine handling. nixos-unstable has Firefox 157.0 today. Source: [build-mozilla-mach/default.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/build-support/build-mozilla-mach/default.nix), [firefox.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/applications/networking/browsers/firefox/packages/firefox.nix).
- Whether the downloaded CDM actually plays DRM video end to end on NixOS x86_64: no first-party document or test found. The only evidence is secondary: [nixpkgs issue #338245](https://github.com/NixOS/nixpkgs/issues/338245) (August 2024, stale) says Firefox downloads Widevine from Google at runtime on x64 and that the gap is aarch64. The [NixOS wiki Firefox page](https://wiki.nixos.org/wiki/Firefox) does not mention Widevine. Unverified.

**Gentoo**
- `www-client/google-chrome`: version 154.0.8037.92 in the tree, keywords `-* amd64 arm64`, license `google-chrome`, `RESTRICT="bindist mirror strip"`, IUSE `qt6 selinux`. The ebuild downloads Google's `.deb` from `dl.google.com`. Source: [ebuild](https://github.com/gentoo/gentoo/blob/master/www-client/google-chrome/google-chrome-154.0.8037.92.ebuild), [packages.gentoo.org](https://packages.gentoo.org/packages/www-client/google-chrome).
- `www-plugins/chrome-binary-plugins`: fetches the same Chrome `.deb` and installs only the `WidevineCdm` directory into `/usr/lib64/chromium-browser` (`libdir` aware). Keywords `-* amd64 arm64`, `RESTRICT="bindist mirror strip"`. Source: [ebuild](https://github.com/gentoo/gentoo/blob/master/www-plugins/chrome-binary-plugins/chrome-binary-plugins-154.0.8037.92.ebuild).
- `www-client/chromium` (source build) has a `widevine` USE flag, described as "Unsupported closed-source DRM capability (required by Netflix VOD)". In ebuild 151.0.7922.169-r1 it defaults on and passes `enable_widevine` to the build. That ebuild does not reference `chrome-binary-plugins`, so how the CDM from that package is picked up is Unverified. Source: [metadata.xml](https://github.com/gentoo/gentoo/blob/master/www-client/chromium/metadata.xml), [ebuild](https://github.com/gentoo/gentoo/blob/master/www-client/chromium/chromium-151.0.7922.169-r1.ebuild).
- `www-client/firefox` USE flags: `eme-free` ("Disable EME (DRM plugin) capability at build time", off by default), `+gmp-autoupdate` (on by default; lets Gecko Media Plugins, the binary blobs, download and update in user profiles), `hwaccel` (off by default, forces hardware-rendering prefs and pulls `libva-utils` and `pciutils`), `wayland`, `pulseaudio` ("may be PulseAudio or Pipewire"). Source: [metadata.xml](https://github.com/gentoo/gentoo/blob/master/www-client/firefox/metadata.xml), [ebuild 157.0.1](https://github.com/gentoo/gentoo/blob/master/www-client/firefox/firefox-157.0.1.ebuild). `www-client/firefox-bin` has the same `gmp-autoupdate` flag. Source: [firefox-bin metadata](https://github.com/gentoo/gentoo/blob/master/www-client/firefox-bin/metadata.xml).

**Implications for this repo:** For NixOS the choice is between `google-chrome` (Widevine bundled, officially a Crunchyroll-supported browser, unfree, a repackaged `.deb`) and `firefox` (free, cached, CDM downloaded into the profile at first use). The Firefox route has no first-party NixOS confirmation, but it is a cheap thing to test on the box. Do not rely on `chromium.override { enableWideVine = true; }` as the primary path: Crunchyroll's list says "Chrome", not Chromium, and the override is a nixpkgs convention that Google does not document. If Firefox is chosen, the profile directory holds both the login and the downloaded CDM, so it must persist across reboots and rebuilds. Chrome in the NixOS config needs `allowUnfree` for `google-chrome` and `widevine-cdm`. Rough decision rule: Chrome if the Firefox test shows DRM errors, Firefox if it works, since Firefox avoids unfree packages.

### 3. NixOS as an appliance

**`services.cage`** (module [cage.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/services/wayland/cage.nix), verified in source)
- Options: `enable`, `user` (default `"demo"`), `program` (type `path`, default `xterm`), `extraArguments` (list of strings, passed to Cage itself), `environment` (attrs of strings, set on the unit), `restartIfChanged` (default false), `package`.
- The unit runs `cage <extraArguments> -- <program>` as `user` on tty1, and conflicts with `getty@tty1`. It uses its own PAM service (`cage`, `nullok` unix auth) and `pam_systemd`, and sets `hardware.graphics.enable = mkDefault true`, `security.polkit.enable = true` and the default target to `graphical.target`. That makes the module itself the autologin: no display manager or greeter.
- Because `program` is a single path and `extraArguments` precedes the `--`, browser flags need a wrapper script (or a wrapped package), not `extraArguments`.
- Cage is a Wayland kiosk that runs one maximized application. nixpkgs ships Cage 0.3.1 on wlroots 0.20. Source: [Cage README](https://github.com/cage-kiosk/cage), [package.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/ca/cage/package.nix).

**Kiosk flags and Wayland**
- Firefox: `--kiosk URL` opens full screen without UI, since Firefox 71 ([Mozilla wiki](https://wiki.mozilla.org/Firefox/CommandLineOptions); handled in [nsAppRunner.cpp](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/xre/nsAppRunner.cpp), which also has `--kiosk-monitor`). Firefox defaults to Wayland over XWayland since 121 ([release notes](https://www.mozilla.org/en-US/firefox/121.0/releasenotes/)).
- Chromium and Chrome: the `kiosk` switch exists ("not Chrome OS kiosk mode") in [chrome_switches.h](https://github.com/chromium/chromium/blob/main/chrome/common/chrome_switches.h). The nixpkgs `chromium` and `google-chrome` wrappers add `--ozone-platform-hint=auto` (plus window-decoration and IME features) only when `NIXOS_OZONE_WL` and `WAYLAND_DISPLAY` are set, so on Cage set `services.cage.environment.NIXOS_OZONE_WL = "1"` (see [chromium/default.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/applications/networking/browsers/chromium/default.nix)).

**Kodi**
- The module is `services.xserver.desktopManager.kodi` (`enable`, `package`; starts `kodi --standalone` as an X session). nixpkgs also has `kodi-wayland` and `kodi-gbm` packages. nixos-unstable's Kodi is 21.3 "Omega". Source: [kodi.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/services/x11/desktop-managers/kodi.nix), [unwrapped.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/applications/video/kodi/unwrapped.nix).
- nixpkgs `kodiPackages` includes `inputstream-adaptive` (21.5.18) and `inputstreamhelper` (0.6.1+matrix.1) but no Crunchyroll add-on in the directory listing I read. Source: [inputstream-adaptive](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/applications/video/kodi/addons/inputstream-adaptive/default.nix), [inputstreamhelper](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/applications/video/kodi/addons/inputstreamhelper/default.nix).
- Kodi's own repository (Nexus, Omega and Piers indexes fetched today from `mirrors.kodi.tv`) has `inputstream.adaptive` and `script.module.inputstreamhelper` but no Crunchyroll entry.
- A third-party add-on exists: [smirgol/plugin.video.crunchyroll](https://github.com/smirgol/plugin.video.crunchyroll), a fork of MrKrabat's plugin. It supports Omega and Nexus, needs a Crunchyroll account, uses device-code login, and installs from its own repository or a zip. Its README says all Crunchyroll API traffic goes through `cloudscraper`, and its changelog notes endpoint and auth changes. Its last commit is 2026-10-06 ([commit feed](https://github.com/smirgol/plugin.video.crunchyroll/commits/main.atom)). Known issue listed: soft-subs broken.
- Kodi's DRM path needs a separate Widevine CDM that is not bundled with `inputstream.adaptive` on non-Android systems ([README](https://github.com/xbmc/inputstream.adaptive)). `inputstreamhelper` obtains Widevine from Chrome OS recovery images and supports Linux x86_64 ([README](https://github.com/emilsvennesson/script.module.inputstreamhelper)).
- Unknown: whether Crunchyroll playback through that add-on works on NixOS at all, whether `inputstreamhelper` works unmodified there (nixpkgs applies a patch to it for reasons I did not investigate), and what resolution the add-on gets.

**VA-API decode**
- `hardware.graphics.enable` ("hardware accelerated graphics drivers", including video decode acceleration) and `hardware.graphics.extraPackages` (VA-API/VDPAU drivers) are the current option names, replacing `hardware.opengl.*`. The option text says `intel-media-driver` supports Broadwell (2014) and newer, and older hardware should use `intel-vaapi-driver`. Example in the source: `with pkgs; [ intel-media-driver intel-ocl intel-vaapi-driver ]`. Source: [graphics.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/hardware/graphics.nix).
- The NixOS wiki (community) says AMD iGPUs need nothing beyond `hardware.graphics.enable`, and that `intel-vaapi-driver` can behave better for browsers on Skylake. [Accelerated Video Playback](https://wiki.nixos.org/wiki/Accelerated_Video_Playback).
- Firefox 115 enabled hardware video decoding by default for Intel GPUs on Linux ([release notes](https://www.mozilla.org/en-US/firefox/115.0/releasenotes/)). Chromium's own doc says VA-API on Linux is "not supported" but may work behind flags, and it shows how to check (`chrome://media-internals`, `video_decoder` should read `GpuVideoDecoder`). Source: [vaapi.md](https://github.com/chromium/chromium/blob/main/docs/gpu/vaapi.md). Gentoo's wiki points to `about:support#graphics` for Firefox ([Gentoo wiki Firefox](https://wiki.gentoo.org/wiki/Firefox)).
- Unknown: whether Widevine-protected playback in either browser on Linux uses hardware decode. No primary source found. It must be tested empirically on the box.

**Audio, minimal profile, updates**
- PipeWire: `services.pipewire.enable`, with `alsa.enable` and `pulse.enable` sub-options ([pipewire.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/services/desktops/pipewire/pipewire.nix)). `google-chrome` in nixpkgs has `pulseSupport ? true`. Which HDMI output the projector exposes is Unknown until the hardware is seen.
- `nixos/modules/profiles/minimal.nix` (all `mkDefault`): turns off documentation (man, info, doc, NixOS manual), empties `environment.defaultPackages`, disables `stub-ld`, `command-not-found`, `logrotate`, `udisks2`, and XDG autostart, icons, mime and sounds. It does not touch graphics, kernel or services otherwise. Source: [minimal.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/profiles/minimal.nix).
- Remote deploy: `nixos-rebuild --target-host user@host` activates on the remote over SSH (root needed for switch/boot/test); `--build-host` builds elsewhere and, without `--target-host`, copies the result back; `--use-substitutes` makes the target fetch from caches; ssh options via `NIX_SSHOPTS`. Source: [nixos-rebuild man page](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/pkgs/by-name/ni/nixos-rebuild-ng/nixos-rebuild.8.scd).
- Remote install: nixos-anywhere connects over SSH, kexecs into an installer if none is present, partitions with disko, and installs. The target needs x86-64 Linux with kexec support (most have it), at least 1 GB RAM when kexec is used, a network that is not Wi-Fi-only, and the source machine can be anything with Nix. Without kexec, boot a NixOS installer image first. Source: [README](https://github.com/nix-community/nixos-anywhere), [quickstart](https://github.com/nix-community/nixos-anywhere/blob/main/docs/quickstart.md). It can generate `hardware-configuration.nix` on the target via `--generate-hardware-config`.
- Unattended updates: `system.autoUpgrade` has `enable`, `flake` (a flake URI; disables `channel`), `operation` (default `switch`, or `boot`), `upgrade`, `flags`, `dates` (default `04:40`), `randomizedDelaySec`, `fixedRandomDelay`, `persistent` (default true), `allowReboot` (default false), `rebootWindow` (`lower`/`upper`, only with `allowReboot`) and `runGarbageCollection` (default false). With a flake it runs `nixos-rebuild <operation> --refresh --flake <uri>` and honors the lock file, so it only upgrades when a newer lock is pushed. Source: [auto-upgrade.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/tasks/auto-upgrade.nix).

**Implications for this repo:** NixOS fits the single-job role well and one declarative host definition covers the whole stack, which matches how the repo already works. Nothing here needs more than Cage, a browser wrapper script, `hardware.graphics` and PipeWire, plus `minimal.nix` for a smaller closure. Run `nixos-rebuild --target-host` from the Framework: it builds locally there (x86_64-linux, so no cross-build) and activates on the box, which keeps compile and evaluation work off an 8 GB machine. A Mac would need a Linux builder, so treat the Framework as the deploy machine. For hands-off updates, `system.autoUpgrade.flake` pointing at the public GitHub mirror, with `operation = "boot"` and a reboot window, avoids surprise mid-movie restarts. That relies on the mirror staying in sync, and nothing secret can live in that repo unencrypted. Note that autoUpgrade evaluates and builds on the box itself, and unfree packages such as `google-chrome` are not in the binary cache (inference from the Hydra setting above), so that step is a local repackage, which should be cheap. Kodi is the weakest path: no Crunchyroll add-on in official or nixpkgs repositories, a third-party add-on that proxies through a Cloudflare workaround, and an unverified Widevine setup on NixOS. A browser kiosk is the lower-risk design. The iGPU vendor is the missing input for `extraPackages`.

### 4. Gentoo for this role

**Official binary host**
- Announced on 2023-12-29 ("Gentoo goes Binary!"). amd64 and arm64 get broad coverage (more than 20 GB of packages); other architectures only the core system. Packages are signed with the stage-signing key and are in GPKG format. The announcement's original amd64 builds used `-march=x86-64 -mtune=generic -O2 -pipe` for the `17.1` profile with a few USE combinations (the stable openrc, plasma/systemd and gnome/systemd profiles). Builds only match when your USE flags match; otherwise Portage compiles locally and mixes the two freely. No `~amd64` binaries at announcement time. Source: [announcement](https://www.gentoo.org/news/2023/12/29/Gentoo-binary.html).
- An x86-64-v3 variant was announced on 2024-02-04. Source: [news](https://www.gentoo.org/news/2024/02/04/x86-64-v3.html).
- Current setup: a file under `/etc/portage/binrepos.conf/` with `sync-uri = https://distfiles.gentoo.org/releases/amd64/binpackages/23.0/x86-64/` (profile 23.0), and `getbinpkg` in `FEATURES` or `--getbinpkg`/`-g` per run; new stage3 tarballs ship the config preconfigured. Source: [Binary host quickstart](https://wiki.gentoo.org/wiki/Gentoo_Binary_Host_Quickstart), [Binary package guide](https://wiki.gentoo.org/wiki/Binary_package_guide).
- Since 2026-05-03 (news item), Portage verifies binpkg signatures by default and stores remote binpkgs separately under `/var/cache/binhost/NAME`; official-binhost users need no action. Source: [news item](https://www.gentoo.org/support/news-items/2026-05-03-portage-binpkg-changes.html).
- What is actually in the binhost today (index `Packages` under the 23.0 `x86-64` directory, timestamp 2026-10-07 12:32 UTC): `www-client/firefox` 140.16.0, 153.3.0 and 153.4.0 in several USE combinations (with `wayland`, `gmp-autoupdate`, `clang`, `pulseaudio` in most), plus `mesa`, `libva`, `pipewire`, `sway`, `mpv`, `gentoo-kernel`. Not present: `firefox-bin`, `google-chrome`, `chromium`, `chrome-binary-plugins`. The index header shows `ACCEPT_LICENSE: @FREE @BINARY-REDISTRIBUTABLE`, which fits the proprietary ones being absent. Source: [Packages index](https://distfiles.gentoo.org/releases/amd64/binpackages/23.0/x86-64/Packages).

**Browsers: source versus `-bin`**
- `www-client/firefox` 153.4.0 (ESR) is stable on amd64; 157.0.1 is `~amd64` ([ebuild](https://github.com/gentoo/gentoo/blob/master/www-client/firefox/firefox-157.0.1.ebuild), [153.4.0](https://github.com/gentoo/gentoo/blob/master/www-client/firefox/firefox-153.4.0.ebuild), [packages page](https://packages.gentoo.org/packages/www-client/firefox)). The ebuild checks for 9.7 GB of free build disk, or 10.9 GB with LTO and 18.7 GB with PGO or debug. The Gentoo wiki says Firefox takes a long time to compile and recommends `firefox-bin` to save time ([Gentoo wiki Firefox](https://wiki.gentoo.org/wiki/Firefox)).
- `www-client/firefox-bin` 157.0.1 and 153.4.0 are stable on amd64 ([ebuild keywords](https://github.com/gentoo/gentoo/blob/master/www-client/firefox-bin/firefox-bin-157.0.1.ebuild), [packages page](https://packages.gentoo.org/packages/www-client/firefox-bin)).
- The Chromium ebuild's `check-reqs` demands 4 GB of RAM (9 GB when LTO or PGO is on) and roughly 10 GB of build disk (14 GB with PGO); the wiki warns it takes a lot of real time, CPU time and memory ([ebuild](https://github.com/gentoo/gentoo/blob/master/www-client/chromium/chromium-151.0.7922.169-r1.ebuild), [Gentoo wiki Chromium](https://wiki.gentoo.org/wiki/Chromium)). Binary Chrome is `www-client/google-chrome` (section 2).

**Update model and remote management**
- The handbook's update command is `emerge --update --deep --newuse @world`; `@world` is the set of explicitly installed packages (the `/var/lib/portage/world` file); `emerge --ask --depclean` cleans up afterwards. Source: [Handbook: Working with Portage](https://wiki.gentoo.org/wiki/Handbook:AMD64/Working/Portage). The binhost announcement's example adds `-av` and `-g`: `emerge -uDNavg @world`.
- Ansible's `community.general.portage` module can run `emerge` for a package or `@world` with `update`, `deep`, `newuse`, `getbinpkg`, `usepkg`, `sync` and `depclean` parameters ([docs](https://docs.ansible.com/ansible/latest/collections/community/general/portage_module.html)). I found no first-party Gentoo document describing a declarative whole-system equivalent; the binary package guide only covers serving your own binhost from another machine.

**Implications for this repo:** Gentoo can do the job, and a binhost plus `firefox` or `google-chrome` avoids long compiles, but it adds an imperative layer (Portage config files, world file, Ansible) that sits outside the Nix repo, while NixOS keeps the box in the same flake and tooling as the other machines. For this box in particular: Gentoo's binhost does not carry any of the Widevine-bundling browsers, so the realistic Gentoo configurations are `firefox` from the binhost (with a USE set that matches the binhost, otherwise a local build) or `google-chrome`/`firefox-bin` (proprietary or prebuilt, no compile). A Chromium source build clears the ebuild's RAM check on an 8 GB box only without LTO or PGO (4 GB versus 9 GB), and it is the slowest path. The deciding question is not capability but whether Renaud wants to manage a second, non-declarative system. The only advantage I found specific to Gentoo for this role is the ability to compile for the exact CPU, which a streaming box does not need.

### 5. Other options

- **ChromeOS Flex:** Google's requirements are an Intel or AMD x86-64 device, 4 GB RAM, 16 GB storage, and USB boot; Intel or AMD hardware from 2012 and earlier and Nvidia from 2014 and earlier are "not recommended or supported". Only certified models are guaranteed, and a [certified models list](https://support.google.com/chromeosflex/answer/11513094?hl=en) (updated 2026-09-02) exists. Source: [prepare for installation](https://support.google.com/chromeosflex/answer/11552529), [differences from ChromeOS](https://support.google.com/chromeosflex/answer/11542901?hl=en). Unknown: whether Widevine streaming works on Flex and at what resolution; neither the [known-issues page](https://support.google.com/chromeosflex/answer/11541806?hl=en) nor the differences page mentions DRM or streaming.
- **Minimal Debian with Google Chrome:** Google lists Debian 10+ (64-bit, SSE3 x86-64) as a supported Linux for Chrome ([Chrome install help](https://support.google.com/chrome/answer/95346?hl=en)), and Chrome carries Widevine ([widevine.gni](https://github.com/chromium/chromium/blob/main/third_party/widevine/cdm/widevine.gni)). This is the only option here where the OS, the browser and the CDM all come from vendors who document Linux support. It is imperative like Gentoo, though.
- **LibreELEC (Kodi appliance):** a LibreELEC post states Generic PC images needed no change for Widevine, which is installed through the InputStream Helper add-on ([post, 2021-05-30](https://libreelec.tv/2021/05/30/le-9-2-7-10b4-fix-widevine/)). It inherits the Kodi/add-on caveats from section 3.
- **Official TV platform instead of desktop Linux:** Crunchyroll's own troubleshooting page lists Android TV, Fire TV, Roku, Apple TV, Chromecast and consoles as supported platforms ([archived copy](https://web.archive.org/web/20250420224131/https://help.crunchyroll.com/hc/en-us/articles/18934150961684-Basic-troubleshooting-for-common-issues-and-error-codes)). A projector with an HDMI stick is the one route Crunchyroll documents end to end, and it would also retire the box.
- **Zen Browser on Linux:** Zen's FAQ says its DRM limitation "only affects Microsoft Windows and MacOS", so Linux can play DRM content ([FAQ](https://docs.zen-browser.app/faq)). The repo already has a `zen-browser` flake input, but Crunchyroll's support list does not include Zen.

**Implications for this repo:** If the goal is the least unknowns, the ranking by evidence is: official TV stick (documented by Crunchyroll), Debian with `google-chrome` (OS, browser and CDM all vendor-documented, but imperative), NixOS with the same `google-chrome` binary (Google does not list NixOS, so it is a repackage of a supported binary), NixOS with Firefox (needs the empirical test), then Kodi, ChromeOS Flex and Gentoo (each leaves one core question unanswered by primary sources or adds a non-declarative layer). Since the repo is Nix-based and the Framework laptop is planned as the management machine, NixOS with `google-chrome` as the fallback and Firefox as the first thing to try is the combination that stays inside the repo.
