**Facts that change a decision**

- sops-nix converts an SSH ed25519 private key to an X25519 age identity at activation and hands it to sops through `SOPS_AGE_KEY_FILE` ([main.go](https://github.com/Mic92/sops-nix/blob/master/pkgs/sops-install-secrets/main.go)). The sops CLI can also encrypt to native `ssh-ed25519` recipients ([sops age docs](https://github.com/getsops/docs/blob/main/content/en/docs/usage/identities/age/_index.md)), but the sops-nix README tells you to derive `age1...` recipients with ssh-to-age ([README](https://github.com/Mic92/sops-nix/blob/master/README.md)). Unverified: whether sops-install-secrets can open a file encrypted to a native `ssh-ed25519` recipient. Its code never sets `SOPS_AGE_SSH_PRIVATE_KEY_FILE`.
- Passphrase-protected SSH keys do not work unattended with either tool. The age README says `ssh-agent` is not supported ([age README](https://github.com/FiloSottile/age/blob/main/README.md)); the agenix notices say the same consequence in practice ([notices](https://github.com/ryantm/agenix/blob/main/doc/notices.md)); the sops-nix README has you strip the passphrase before conversion ([README](https://github.com/Mic92/sops-nix/blob/master/README.md)); and `SOPS_AGE_SSH_PRIVATE_KEY_CMD` output must not be passphrase-protected ([sops age docs](https://github.com/getsops/docs/blob/main/content/en/docs/usage/identities/age/_index.md)).
- The age README warns against decrypting with SSH keys that people treat as revocable authentication keys ([age README](https://github.com/FiloSottile/age/blob/main/README.md)).
- sops user-side lookup of the age key on macOS: `$XDG_CONFIG_HOME/sops/age/keys.txt`, else `~/Library/Application Support/sops/age/keys.txt`. Overrides: `SOPS_AGE_KEY_FILE`, `SOPS_AGE_KEY`, `SOPS_AGE_KEY_CMD` ([sops age docs](https://github.com/getsops/docs/blob/main/content/en/docs/usage/identities/age/_index.md)). `SOPS_AGE_KEY_CMD` is the hook for fetching the admin key from a password manager at edit time.
- sops-nix on nix-darwin: the default `sops.gnupg.sshKeyPaths` is `/etc/ssh/ssh_host_rsa_key`, so GPG import of the host RSA key is on by default, while `sops.age.sshKeyPaths` defaults to the host ed25519 key ([darwin module](https://github.com/Mic92/sops-nix/blob/master/modules/nix-darwin/default.nix)). Open issue [#974](https://github.com/Mic92/sops-nix/issues/974) (2026-08-09) reports a failing activation tied to that GPG import with a stale launchd daemon. The HM launchd agent has an open issue where it fails at login ([#801](https://github.com/Mic92/sops-nix/issues/801), last activity 2025-06) and a closed one for an empty `PATH` ([#890](https://github.com/Mic92/sops-nix/issues/890)).
- sops-nix on Darwin calls the same `MountSecretFs` (hdiutil RAM disk plus `mount`) in HM user mode ([main.go](https://github.com/Mic92/sops-nix/blob/master/pkgs/sops-install-secrets/main.go), [darwin.go](https://github.com/Mic92/sops-nix/blob/master/pkgs/sops-install-secrets/darwin.go)). Unverified: that this succeeds without root on current macOS.
- agenix churn: 0.15.0 was 2023-12-20; 0.16.0, 0.17.0 and 0.18.0 landed 2026-09-26 and 2026-09-27. 0.16.0 renamed the rules file to `agenix-rules.nix` (`secrets.nix` still works with a warning and is slated for removal) ([releases](https://github.com/ryantm/agenix/releases), [reference](https://github.com/ryantm/agenix/blob/main/doc/reference.md)). On nix-darwin, agenix detects darwin through `options.environment.darwinConfig` ([age.nix](https://github.com/ryantm/agenix/blob/main/modules/age.nix)), which nix-darwin master still defines ([nix-darwin environment module](https://github.com/nix-darwin/nix-darwin/blob/master/modules/environment/default.nix)).
- **agenix-rekey** adds per-host rekeying and secret generators on top of agenix, with NixOS and darwin modules; the README names a YubiKey/FIDO2/TPM or plain age identity as the master key and does not mention Home Manager. Last push 2026-03-26 ([README](https://github.com/oddlama/agenix-rekey)). It can keep rekeyed per-host files out of the repo, so a later-leaked host key cannot open older committed files ([README](https://github.com/oddlama/agenix-rekey)).
- **ragenix** is a drop-in replacement for the agenix CLI built on the Rust `rage`; last push 2026-10-04 ([repo](https://github.com/yaxitech/ragenix)).

**What an encrypted file exposes in a public repo**

- sops (YAML/JSON/ENV/INI): keys stay in cleartext and only values are encrypted; BINARY mode encrypts the whole file as a blob ([sops security doc](https://github.com/getsops/docs/blob/main/content/en/docs/security/_index.md)). The `sops:` block lists every recipient (age public keys or PGP fingerprints), `lastmodified`, the sops version and a MAC; the example in the sops-nix README shows nested key names in clear and a `data:` length that follows the plaintext length (`password1` gives 12 base64 characters) ([README](https://github.com/Mic92/sops-nix/blob/master/README.md)). The sops-nix README states encrypted sops files can be committed to version control and that sops files can be added to the Nix store without leaking secrets ([README](https://github.com/Mic92/sops-nix/blob/master/README.md)). The sops threat model recommends keeping encrypted files "reasonably private" against a future AES weakness ([sops security doc](https://github.com/getsops/docs/blob/main/content/en/docs/security/_index.md)).
- agenix: the whole `.age` file is opaque. The age header carries one stanza per recipient. An `ssh-ed25519` or `ssh-rsa` stanza includes a 4-byte SHA-256 tag of the recipient's public key ([age agessh source](https://github.com/FiloSottile/age/blob/main/agessh/agessh.go)), and the age spec says identifiers trade away recipient anonymity ([age spec](https://github.com/C2SP/C2SP/blob/main/age.md)). File size is visible too; the `age-inspect` example in the v1.3.0 notes splits a file into header, armor overhead, a 32-byte encryption overhead and payload ([release](https://github.com/FiloSottile/age/releases/tag/v1.3.0)).
- agenix files carry no MAC: anyone with write access can alter a secret because the recipients are public ([threat model](https://github.com/ryantm/agenix/blob/main/doc/threat-model-warnings.md)); sops has a MAC ([same page](https://github.com/ryantm/agenix/blob/main/doc/threat-model-warnings.md)). In a public repo read-only for others, this matters only if someone can push to it.
- Harvest-now-decrypt-later: the agenix doc says age is not post-quantum safe as of June 2024 and advises encrypting only rotatable secrets ([threat model](https://github.com/ryantm/agenix/blob/main/doc/threat-model-warnings.md)). age 1.3.0 (2025-12-27) added native post-quantum recipients (`age1pq1...`, `age-keygen -pq`) ([release](https://github.com/FiloSottile/age/releases/tag/v1.3.0)). sops parses `age1pq1` recipients and PQ identities in v3.12.2 and v3.13.3 ([keysource.go](https://github.com/getsops/sops/blob/main/age/keysource.go)); sops-nix pins sops v3.12.2 ([go.mod](https://github.com/Mic92/sops-nix/blob/master/go.mod)). SSH-derived keys are classical X25519, so a PQ recipient needs a native key such as `age-keygen -pq` used through `sops.age.keyFile`. Unverified end to end: a full sops-nix activation with a PQ identity.

**Implications for this repo:** Both tools ship NixOS, nix-darwin and Home Manager modules, so module coverage does not decide it. The real differences are templating, file shape and how identities are supplied. sops-nix gives templates, nested keys and per-host rule files; agenix gives opaque files and less to configure. The template advantage is smaller than it looks: Wi-Fi secrets fit agenix's whole-file model (an env file for NetworkManager, a `varname=value` file for wpa_supplicant), and wakatime can read its key from a file (question 6). A sops-nix choice should set `sops.gnupg.sshKeyPaths = []` on the Mac, given the default GPG import and issue #974 (inference, not tested), and should prefer decrypting at the nix-darwin level with `owner = "renman-ymd"` plus a template `path` into the home directory, which avoids the HM launchd agent that has open failures. Public-repo exposure differs: with sops, secret names and nesting are public (use neutral key names, not SSIDs), while with agenix only sizes and recipient tags are. Whichever tool is chosen, do not reuse the GitHub authentication key `~/.ssh/id_ed25519` as the long-lived decryption identity (age README warning above); a dedicated age key is cleaner. The age 1.3 PQ recipients are worth a look given the repo is public and ciphertext is permanent, but only sops (not agenix's documented SSH-only path) has verified support in source.

### 2. Bootstrapping a new machine and the role of Vaultwarden

**Per-host keys: derived from SSH host keys, or separate**

- sops-nix: the README calls SSH host keys (OpenSSH enabled) the easiest way to add machines, converting with `ssh-to-age` ([README](https://github.com/Mic92/sops-nix/blob/master/README.md)). The alternative is `sops.age.keyFile` with `sops.age.generateKey = true`, which makes a key at that path on first activation if missing; default off ([darwin module](https://github.com/Mic92/sops-nix/blob/master/modules/nix-darwin/default.nix), [README](https://github.com/Mic92/sops-nix/blob/master/README.md)).
- agenix: uses SSH keys only. `age.identityPaths` defaults to the host rsa/ed25519 keys on NixOS and to `/etc/ssh/ssh_host_ed25519_key` and `/etc/ssh/ssh_host_rsa_key` on darwin; the HM default is `~/.ssh/id_ed25519` and `~/.ssh/id_rsa` ([age.nix](https://github.com/ryantm/agenix/blob/main/modules/age.nix), [reference](https://github.com/ryantm/agenix/blob/main/doc/reference.md)).
- Local observation: `/etc/ssh/ssh_host_ed25519_key` exists on the MacBook, root:wheel, mode 0600, dated 2026-04-02. Unknown: whether macOS updates or Remote Login toggling preserve or regenerate it.
- Getting the first key onto a fresh NixOS machine: nixos-anywhere can install files into the target before first boot with `--extra-files`, and `--copy-host-keys` copies existing `/etc/ssh/ssh_host_*`; its docs describe exactly this to bootstrap sops-nix or agenix ([secrets how-to](https://github.com/nix-community/nixos-anywhere/blob/main/docs/howtos/secrets.md)). agenix-rekey can encrypt to a dummy public key for a host whose key does not exist yet; runtime decryption then fails until the real host key is generated ([README](https://github.com/oddlama/agenix-rekey)).
- Unverified: the exact manual sequence from the NixOS installer ISO (placing a key under `/mnt/etc/ssh` before `nixos-install`); not covered by docs I read.

**Vaultwarden SSH-key item support (server side)**

- 1.32.5 (2024-11-18) added SSH-key storage, usable with desktop 2024.12.0+, and required `EXPERIMENTAL_CLIENT_FEATURE_FLAGS=ssh-key-vault-item,ssh-agent` ([release](https://github.com/dani-garcia/vaultwarden/releases/tag/1.32.5)). 1.33.0 (2025-01-25) fixed ssh-key sync ([release](https://github.com/dani-garcia/vaultwarden/releases/tag/1.33.0)).
- `/api/sync` drops type-5 (SSH key) ciphers unless the client sends a version of at least 2024.12.0 ([ciphers.rs](https://github.com/dani-garcia/vaultwarden/blob/main/src/api/core/ciphers.rs)).
- 1.37.4 (2026-10-05) removed the `ssh-agent` and `ssh-key-vault-item` flags because no client reads them anymore. A flag `ssh-agent-v2` ("Desktop >= 2026.2.1") remains optional and defaults to unset ([release](https://github.com/dani-garcia/vaultwarden/releases), [.env.template](https://github.com/dani-garcia/vaultwarden/blob/main/.env.template)). Reading of the notes (inference): on 1.37.4+ no flag is needed; on 1.32.5 to 1.37.3 the friend must have set the two flags; before 1.32.5 SSH key items do not exist.

**Reading the server version as a non-admin**

- `GET /api/version` returns the Vaultwarden version string and its route has no auth guard in source. `GET /api/config` is also unauthenticated but reports a Bitwarden-compatible version (`"2026.6.0"` in this commit), plus `gitHash`, `server.name`, `settings.disableUserRegistration` and `featureStates`; it is not the Vaultwarden release ([core/mod.rs](https://github.com/dani-garcia/vaultwarden/blob/main/src/api/core/mod.rs), source at commit 1f802f8, 2026-10-07).
- Clients cache `/api/config` for about an hour ([.env.template](https://github.com/dani-garcia/vaultwarden/blob/main/.env.template)).
- Unknown: whether the friend's reverse proxy exposes `/api/version`. Unverified: whether the web vault UI shows the server version to normal users. I did not contact the server.
- Compatibility pressure: 1.37.0 and 1.37.2 state that updates are required for clients 2026.7.0+ and 2026.8.0+ ([1.37.0](https://github.com/dani-garcia/vaultwarden/releases/tag/1.37.0), [1.37.2](https://github.com/dani-garcia/vaultwarden/releases/tag/1.37.2)). Newer `bw` or desktop builds may misbehave against an unpatched server (nixpkgs currently carries `bitwarden-cli` 2026.9.0 and `rbw` 1.15.0 per `nix eval`).

**Implications for this repo:** Vaultwarden is a good home for the human-held admin secrets (the age or sops identity, the GPG key backup, SSH keys), and a poor runtime secret source for hosts. `rbw` and `bw` both need the master password interactively (pinentry) or stored somewhere, Secrets Manager is unsupported, and the streaming box and the work machines should not carry vault credentials at all. A clean split is: per-host age keys (or host-key-derived) as recipients for runtime secrets, and the single admin age identity stored as a vault item, fetched when editing (`SOPS_AGE_KEY_CMD='rbw get ...'` or `bw get`) and never copied to hosts. For a first key on a fresh host, pre-generating the host key off-box and placing it with `--extra-files` is the documented path for NixOS; `generateKey` or a first-boot host key needs a second rebuild after adding the recipient, which matters for the streaming box (Wi-Fi password needed before it can get online; question 5). The version probe above tells whether the friend's server can hold SSH key items at all.

### 3. Trust model of a friend-run Vaultwarden

**What the end-to-end design hides and exposes**

- Vault data (logins, passkeys, cards, identities, notes, secrets) is encrypted on the client; each item has its own key wrapped by the user or organization key. The master key comes from PBKDF2-SHA256 (default 600,000 iterations, email as salt) or Argon2id, is stretched with HKDF, and wraps a random symmetric key stored on the server. A master-password hash derived from the master key authenticates to the server, which hashes it again ([white paper](https://bitwarden.com/help/bitwarden-security-white-paper/)). KDF defaults: PBKDF2 600,000; Argon2id 32 MiB, 6 iterations, 4 threads ([KDF help](https://bitwarden.com/help/kdf-algorithms/)). Vaultwarden's own server-side re-hash defaults to 600,000 iterations and refuses values under 100,000 ([config.rs](https://github.com/dani-garcia/vaultwarden/blob/main/src/config.rs)).
- The server and its admin still see account metadata. Per ETH Zurich's analysis, much of Bitwarden's metadata and many settings are not encrypted, including item field names and KDF settings, which are stored unauthenticated ([USENIX Security 2026 paper](https://www.usenix.org/system/files/conference/usenixsecurity26/sec26_prepub_scarlata.pdf)). The Vaultwarden admin page lists per-user email, last activity, item count, attachment count and size ([admin.rs](https://github.com/dani-garcia/vaultwarden/blob/main/src/api/admin.rs)).

**Risks when someone else administers the server**

- Availability and deletion: with the admin token, the admin can delete or disable any user (`/users/<id>/delete`, `disable_user`) ([admin.rs](https://github.com/dani-garcia/vaultwarden/blob/main/src/api/admin.rs)). Vaultwarden's wiki tells operators to back up the SQLite file, attachments and `rsa_key.*` themselves ([backup page](https://github.com/dani-garcia/vaultwarden/wiki/Backing-up-your-vault)); Bitwarden says users are responsible for their own vault backups ([data storage](https://bitwarden.com/help/data-storage/)).
- Offline resilience: as long as you stay logged in, clients keep an encrypted copy of the vault and read it offline; edits need the server; offline sessions expire after 30 days; logging out clears the local copy ([Bitwarden blog](https://bitwarden.com/blog/configuring-bitwarden-clients-for-offline-access/), [data storage](https://bitwarden.com/help/data-storage/)). `rbw` also keeps its own local vault per profile ([README](https://github.com/doy/rbw/blob/main/README.md)).
- Modified web vault: Vaultwarden bundles a modified web vault in its containers ([README](https://github.com/dani-garcia/vaultwarden/blob/main/README.md)), and Bitwarden's white paper says the web client's integrity depends on the TLS connection delivering it, so an attacker who can tamper with that traffic can deliver a malicious client ([white paper](https://bitwarden.com/help/bitwarden-security-white-paper/)). The ETH paper sets a malicious client aside as a trivial attack that audits would detect and that would be risky for a vendor, and it says this holds most strongly for signed releases such as desktop and mobile clients and browser extensions ([paper](https://www.usenix.org/system/files/conference/usenixsecurity26/sec26_prepub_scarlata.pdf)). Whoever runs the server controls what the web vault serves; desktop, CLI and `rbw` come from separate distribution (nixpkgs, app stores). Unverified: that the Bitwarden desktop app never loads UI code from the configured server.
- Malicious-server attacks beyond the web vault: the paper finds 12 attacks on Bitwarden under a fully malicious server, for example lowering the KDF iteration count for a user who logs in (BW07, "1 login") and legacy-format downgrades that need two logins (BW11, BW12). Most need client interaction. The authors say vendors were "well advanced" in mitigations at the time (BW01, BW03, BW11, BW12 addressed; minimum PBKDF2 iterations now 5,000), and that most users are unlikely targets ([paper](https://www.usenix.org/system/files/conference/usenixsecurity26/sec26_prepub_scarlata.pdf)). Bitwarden says seven issues are resolved or being fixed and three were accepted as design decisions ([Bitwarden blog](https://bitwarden.com/blog/security-through-transparency-eth-zurich-audits-bitwarden-cryptography/)). Unverified: which fixes live in the client versions Renaud would run, and which are Vaultwarden-specific.
- Patch cadence of the server: 1.37.4 (2026-10-05) fixes seven privately-tracked advisories, one rated High (organization member revocation) ([release](https://github.com/dani-garcia/vaultwarden/releases)).

**Backups and export formats**

- Bitwarden export formats: `.json` and `.csv` (plaintext), `.json (Encrypted)`, and `.zip` with attachments. Only JSON exports include cards, identities, passkeys and SSH keys ([export help](https://bitwarden.com/help/export-your-data/)). Encrypted exports are either account-restricted (importable only into the same account, invalidated by an account-key rotation) or password-protected: the password goes through your configured KDF settings and HKDF to a key that encrypts and MACs the data ([encrypted export](https://bitwarden.com/help/encrypted-export/)). CLI: `bw export --format encrypted_json --password ...` ([export help](https://bitwarden.com/help/export-your-data/)). Attachments are handled separately (zip option).

**Implications for this repo:** The friend can delete the account, lose the server, or patch late; he cannot read the vault unless the server is attacked or he mounts an active attack (modified web vault, KDF downgrade) against a login, so the web vault served from his domain is the weakest client path and the native clients are the safer ones. Practical consequences: never hold the only copy of the root secret (the age or sops admin identity) in that vault; keep a password-protected encrypted JSON export (it includes SSH keys) somewhere Renaud controls and refresh it after key changes; check the account's KDF setting (Argon2id, raised parameters) on a device with enough memory; prefer a long master password because it is the only barrier if the server database leaks; and read `/api/version` to judge whether the friend patches promptly. Because the repo ciphertext is public and permanent, the vault only holds the key to it; losing or exposing the vault entry is the same event as losing or exposing every secret ever committed.

### 4. SSH and signing keys across machines

**Primary guidance on per-device vs shared keys**

- GitHub's docs show one title per device ("Personal laptop" in the example) when adding a key and tell you to delete keys you do not recognize or that are out of date ([add key](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account), [reviewing keys](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/reviewing-your-ssh-keys)). I found no GitHub or OpenSSH page that states per-device keys as a rule; this is a reading of the examples, not a stated recommendation.
- Bitwarden's SSH page says services generally support per-user keys and that sharing an SSH key across an organization should be reviewed against best practices ([About SSH](https://bitwarden.com/help/about-ssh/)).
- GnuPG manual: `--export-secret-subkeys` exports secret subkeys without the primary key's secret part (a GNU extension that other OpenPGP implementations may not import), intended for putting a signing subkey on a main machine while the primary key stays elsewhere ([GnuPG manual](https://www.gnupg.org/documentation/manuals/gnupg/Operational-GPG-Commands.html)). "One signing subkey per machine" is a practice built on that command, not stated in the manual.

**jj signing (0.45.1 docs)**

- Backends: `gpg`, `gpgsm`, `ssh`, `none` ([jj config 0.45.1](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/config.md)).
- GPG: `signing.key` is anything `gpg -u` accepts, defaulting to the key for `user.email`. SSH: `signing.key` is either a literal public key (`ssh-ed25519 AAAA...`) or a path to a public key file ([jj config 0.45.1](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/config.md)).
- jj runs `ssh-keygen -Y sign -f <pubkey file> -n git` ([ssh_signing.rs](https://github.com/jj-vcs/jj/blob/v0.45.1/lib/src/ssh_signing.rs)), and `ssh-keygen -Y sign -f` accepts a public key whose private half is in an ssh-agent ([ssh-keygen(1)](https://man.openbsd.org/ssh-keygen)). So an agent-held key (Bitwarden or rbw agent) can sign.
- `signing.behavior`: `drop`, `keep`, `own`, `force`; `force` signs every commit after modification even if you are not the author. `git.sign-on-push = true` signs only on push, suggested when the backend needs interaction ([jj config 0.45.1](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/config.md)). The repo currently uses `backend = "gpg"`, `key = "CB49EE78601E1E1B"`, `behavior = "force"` (`modules/home.nix`).
- Verification: `signing.backends.ssh.allowed-signers` (an `allowed_signers` file) and `revocation-list`; `ui.show-cryptographic-signatures` is off by default ([jj config 0.45.1](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/config.md)). The `allowed_signers` format supports `valid-after` and `valid-before` timestamps ([ssh-keygen(1)](https://man.openbsd.org/ssh-keygen)).
- Conditional config exists in 0.45: `[[--scope]]` tables with `--when.repositories`, `--when.workspaces`, `--when.hostnames`, `--when.commands`, `--when.platforms`, or a top-level `--when.*` at the start of a file in `conf.d/` ([jj config 0.45.1](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/config.md)). A scope table can override `signing.key` and `user.email` for a path such as a work repository.

**GitHub behaviour**

- SSH signing: an existing authentication key can be uploaded again as a signing key (a key used for both must be uploaded twice, once per type), with no limit on the number of signing keys ([about verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification), [add key](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account)). The same page says a GPG key can expire or be revoked and that a GPG signature may carry that information; it makes no such statement for SSH keys.
- Persistent verification: once a signature is verified on push, a record is stored and the commit stays "Verified" within its repository network even if keys are later rotated or revoked ([about verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)).
- Vigilant mode: when on, unsigned commits attributed to you are "Unverified", and a signed commit whose author has vigilant mode on but who is not the committer is "Partially verified" ([vigilant mode](https://docs.github.com/en/authentication/managing-commit-signature-verification/displaying-verification-statuses-for-all-of-your-commits)).

**Analysis: SSH signing with per-machine keys vs one GPG key**

- Distribution of private material: per-machine SSH signing keys are generated on the device and never move, so the public repo can hold the public keys in the clear (for `allowed_signers` and for GitHub) and needs no encrypted signing secret. One shared GPG key (or a shared SSH key) means its private part must reach every machine, through sops/agenix, the vault or a manual copy, and a compromised machine compromises the one identity.
- Revocation: per-machine keys let one machine be removed on GitHub without touching the others, and past commits stay Verified because of persistent records; GitHub's docs describe expiry and revocation only for GPG keys, so a retired per-machine SSH key most likely has to be removed from the account by hand (inference; I did not find a GitHub page on SSH key expiry).
- Local verification: GPG needs one public key imported; SSH needs an `allowed_signers` entry per machine (with optional `valid-after`/`valid-before` for rotation), which can be generated from the repo's key list.
- Tooling on the Mac: the repo's darwin module documents trouble with gpg-agent under launchd and works around it (`modules/darwin.nix` comments near line 131); SSH signing drops the gpg-agent and pinentry dependency but needs an agent or an unencrypted private key with `ssh-keygen`, and a Bitwarden or rbw agent that prompts per signature interacts badly with `behavior = "force"` unless `git.sign-on-push` batches the prompts.
- Second identity: a work identity key lives only on the work machine (no personal keys there); on a personal machine, a `--when.repositories` scope can switch `signing.key` and `user.email` for work repositories. If the same GitHub account is used from machines that do not sign, vigilant mode would flag those commits "Unverified".
- GPG subkeys give a middle path (one identity, per-machine signing subkeys, primary key kept off the machines), but jj's handling of a subkey selector such as a trailing `!` in `signing.key` is Unverified (jj only says "anything `gpg -u` accepts"), and the exported-subkeys format is a GnuPG extension.

### 5. Wi-Fi passwords

**NixOS, NetworkManager** (nixos-unstable `networkmanager.nix` as of 2026-10-07, [source](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/services/networking/networkmanager.nix))

- `networking.networkmanager.ensureProfiles.profiles` takes keyfile-format attrsets; `networking.networkmanager.ensureProfiles.environmentFiles` is a list of paths loaded as environment files, and `$VAR` references in the profiles are substituted with `envsubst`. The option's own example uses `psk = "$HOME_WIFI_PASSWORD"` and `environmentFiles = [ "/run/secrets/network-manager.env" ]`.
- Mechanism: a oneshot unit `NetworkManager-ensure-profiles` (wanted by `multi-user.target`, before `network-online.target`) renders each profile to `/run/NetworkManager/system-connections/<id>.nmconnection` with `UMask=0177`, then `nmcli connection reload` (same source). The rendered files sit on `/run`, not in the Nix store.
- Quirks from the option text: editing a declarative profile in a GUI creates a second profile; a removed profile persists until reboot (same source). `envsubst` substitutes every `$NAME` in a profile, so a literal `$` elsewhere needs care (inference from the mechanism).

**NixOS, wpa_supplicant** ([wpa_supplicant.nix](https://github.com/NixOS/nixpkgs/blob/nixos-unstable/nixos/modules/services/networking/wpa_supplicant.nix))

- `networking.wireless.secretsFile` is a path to a file of `varname=value` lines; networks refer to them as `ext:varname`, for example `networking.wireless.networks.home.pskRaw = "ext:psk_home"` (`pskRaw` must be a 64-hex PSK or an `ext:` reference), and EAP `password=ext:pass_work`. The module adds `ext_password_backend=file:<secretsFile>` to the wpa_supplicant config and bind-mounts the file read-only into the unit. The old `environmentFile` option was removed in favour of this.

**How sops-nix plugs in** (composition of the two sources above with the sops-nix template docs; not an example I found)

- NetworkManager: a sops-nix secret per password plus a template whose content is `HOME_WIFI_PASSWORD=${config.sops.placeholder."..."}`, with `environmentFiles = [ config.sops.templates."...".path ]`; the NixOS template default path is `/run/secrets/rendered/<name>` ([sops-nix README](https://github.com/Mic92/sops-nix/blob/master/README.md)). Alternatively the env file can be one whole secret (no template), the only shape agenix offers.
- wpa_supplicant: point `secretsFile` at a decrypted `varname=value` file or at a template rendering one (same sources).
- Ordering: sops-nix decrypts during activation, before systemd starts the units above (README: activation time), so the files exist when the units run. This relies on the host key being present at the first activation.

**macOS**

- nix-darwin has no Wi-Fi module. The networking module's `knownNetworkServices` only drives `networksetup` for DNS servers, search domains and DHCP client ID ([networking module](https://github.com/nix-darwin/nix-darwin/blob/master/modules/networking/default.nix)). Apple's `networksetup` has `-setairportnetwork <device> <network> [password]` and `-addpreferredwirelessnetworkatindex <device> <network> <index> <security type> [password]` (local `networksetup -printcommands`).
- Unverified: how macOS stores saved Wi-Fi passwords (keychain) and whether the `networksetup` commands above work unattended from an activation script without prompting.

**Implications for this repo:** On NixOS both mechanisms keep the password out of the Nix store and on tmpfs, and sops-nix or agenix decrypts to a file that either mechanism reads, so the choice between NetworkManager profiles and wpa_supplicant is about the machine (NetworkManager fits the Framework laptop with a GUI; wpa_supplicant with `secretsFile` is lighter for a mostly headless streaming box), not about secret handling. The catch is the first boot of the streaming box: the machine has no Wi-Fi until its host key can decrypt the secret, so either the host key is placed before first boot (nixos-anywhere `--extra-files`, section 2) or the first boot needs a manual connection and a second rebuild. On the Mac, treat Wi-Fi as manually provisioned (Apple's CLI takes the password as an argument, visible in process listings, which is a reason not to script it; inference).

### 6. API tokens for user programs

**wakatime config facts** (wakatime-cli [USAGE.md](https://github.com/wakatime/wakatime-cli/blob/develop/USAGE.md), [params.go](https://github.com/wakatime/wakatime-cli/blob/develop/pkg/params/params.go), develop branch on 2026-10-07)

- Config is `$WAKATIME_HOME/.wakatime.cfg` (INI, `[settings]` section; `WAKATIME_HOME` defaults to `$HOME`), shared by editor plugins. The key can come from `api_key` in the file, from `WAKATIME_API_KEY`, or from `api_key_vault_cmd` ([USAGE.md](https://github.com/wakatime/wakatime-cli/blob/develop/USAGE.md)).
- Documented semantics of `api_key_vault_cmd`: a space-separated executable and arguments, executables in `PATH` by basename, "Shell syntax not supported" ([USAGE.md](https://github.com/wakatime/wakatime-cli/blob/develop/USAGE.md)).
- Source behaviour differs: commit "Run vault command in shell instead of exec" (2026-04-20, [19422656](https://github.com/wakatime/wakatime-cli/commit/19422656)) makes it run `sh -c <cmd>` with a 2-second timeout, trimming the output; v2.26.0 (the version nixpkgs carries per `nix eval`) contains that commit per the GitHub compare API. The docs still say shell syntax is unsupported, so a command that works under both interpretations (an absolute path with simple arguments) is safest.
- Resolution order in source: `--key` flag, then `api_key` in config, then the vault command, then `WAKATIME_API_KEY`; a non-empty value must match the API key format. The USAGE.md statement that a config `api_key` beats the env var matches this order.

**Options**

- sops-nix template writing the whole file: a template with `[settings]\napi_key = ${config.sops.placeholder.wakatime-api-key}` and `path = "${config.home.homeDirectory}/.wakatime.cfg"` in HM (a symlink to the rendered file; HM default rendered location `~/.config/sops-nix/secrets/rendered/<name>`), or the nix-darwin level template with `owner`/`mode` and a `path` into the home directory ([HM templates](https://github.com/Mic92/sops-nix/blob/master/modules/home-manager/templates.nix), [darwin templates](https://github.com/Mic92/sops-nix/blob/master/modules/nix-darwin/templates/default.nix), [main.go](https://github.com/Mic92/sops-nix/blob/master/pkgs/sops-install-secrets/main.go)). The rendered file is on a RAM disk or temp directory and is recreated at login or activation. Unverified: whether Emacs's wakatime-mode or other plugins try to write to `~/.wakatime.cfg` (it would hit a read-only symlink).
- Secret file plus `api_key_vault_cmd`: keep `~/.wakatime.cfg` non-secret (manageable with `home.file`) and set `api_key_vault_cmd = cat <absolute path of the decrypted secret>`, using the sops-nix path (`~/.config/sops-nix/secrets/<name>` for HM) or the agenix path ([sops-nix README](https://github.com/Mic92/sops-nix/blob/master/README.md), [agenix reference](https://github.com/ryantm/agenix/blob/main/doc/reference.md)). No template needed, so it also works with agenix.
- Runtime fetch with `rbw`: `api_key_vault_cmd = rbw get wakatime`. `rbw get` needs the agent unlocked (pinentry otherwise) and the vault command has a 2-second timeout ([README](https://github.com/doy/rbw/blob/main/README.md), [params.go](https://github.com/wakatime/wakatime-cli/blob/develop/pkg/params/params.go)). When locked, every heartbeat fails.
- `WAKATIME_API_KEY` in the environment: lowest precedence in source, and it leaks to child processes (inference).

**Implications for this repo:** The `api_key_vault_cmd = cat <secret path>` route is the smallest change: the secret stays one opaque value, the config file stays declarative and committed, and nothing breaks if the decrypted file is briefly absent beyond a missed heartbeat. A sops template for the whole file works equally well and keeps the key in one rendered file but is tied to sops. The `rbw` route is the least reliable for an editor-driven tool because of the 2-second limit and the unlock dependency. If the key is decrypted at the HM level on macOS, the open launchd-agent issues in section 1 apply; if decrypted at the nix-darwin level, they do not.
