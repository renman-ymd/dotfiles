### 1. Web-app windows (own window, no tabs, no URL bar, nothing opened beside it)

**Findings**

*Chromium family, `--app=<url>`* (Chromium `main`, read from the `chromium/chromium` mirror):

- **What it is.** `--app` is the "application mode" switch ([chrome_switches.h](https://github.com/chromium/chromium/blob/main/chrome/common/chrome_switches.h)). Startup accepts only web-safe schemes or `file:`; an empty or invalid value is ignored ([startup_browser_creator.cc](https://github.com/chromium/chromium/blob/main/chrome/browser/ui/startup/startup_browser_creator.cc)). It opens a window with no app id, a "URL app" in the code's words ([application_launch.cc](https://github.com/chromium/chromium/blob/main/chrome/browser/ui/extensions/application_launch.cc)).
- **Chrome in that window.** For a TYPE_APP window with no app controller, the window-feature table supports the title bar only. Tab strip, toolbar, location bar and bookmark bar are all off. The toolbar and location bar come back only for installed web apps, which have an app controller ([window_feature_controller.cc](https://github.com/chromium/chromium/blob/main/chrome/browser/ui/window_feature_controller/window_feature_controller.cc)). Analysis: so `--app` meets "no tabs, no URL bar" on the surface.
- **It is not a hard lock.** Reading [browser_navigator.cc](https://github.com/chromium/chromium/blob/main/chrome/browser/ui/navigator/browser_navigator.cc) and [browser_commands.cc](https://github.com/chromium/chromium/blob/main/chrome/browser/ui/browser_commands.cc):
  - A plain link click (current-tab disposition) navigates inside the same window, to any origin. The scope check (`IsUrlInAppScope`) only applies when an app controller exists, so a `--app` window has no origin scope.
  - Tab-type dispositions (`target=_blank`, ctrl/middle-click) from a window that cannot host tabs go to `GetOrCreateBrowser`: a normal tabbed window of the same profile is found or created.
  - Ctrl+T does the same through `NewTab`, which opens the blank tab in a tabbed window of the profile.
  - `window.open` popups become app-styled popups; a new-window disposition creates a full normal browser window.
  - Conclusion: nothing can be opened as a tab inside the app window, but links and shortcuts can still pop a full normal window of the same profile beside it. External links are not forwarded to the default browser. A project that wraps this pattern says so itself ([nix-chromium-webapps README](https://github.com/chobbledotcom/nix-chromium-webapps)).
- **Isolation.** Helpers pair `--app` with a dedicated `--user-data-dir=<dir>` per site ([module.nix](https://github.com/chobbledotcom/nix-chromium-webapps/blob/main/module.nix)). Unverified: how `--user-data-dir` compares with `--profile-directory` for process and window grouping; I read no source on that.
- **Installed PWAs are a different thing** (they get an app controller, so scope handling and a minimal toolbar for out-of-scope pages). Chrome offers "Install page as app" on Windows, Mac and Linux ([Chrome Help](https://support.google.com/chrome/answer/9658361)); the page does not say whether the window drops the address bar. A declarative route exists: policy `WebAppInstallForceList` force-installs sites, with per-item `default_launch_container` (`window` or `tab`), `create_desktop_shortcut` (Linux and Windows), `custom_name` and `custom_icon`. It is per-profile, supported on Chrome 75+ ([policy definition](https://github.com/chromium/chromium/blob/main/components/policy/resources/templates/policy_definitions/Miscellaneous/WebAppInstallForceList.yaml)). Microsoft's Teams PWA page names it for Edge and Chrome ([Learn](https://learn.microsoft.com/en-us/microsoftteams/teams-progressive-web-apps), ms.date 2026-03-27). NixOS writes managed policies from `programs.chromium.extraOpts` to `/etc/chromium/policies/managed/extra.json` ([module](https://github.com/NixOS/nixpkgs/blob/b6c98e9e6633ee64753b594ff4a5febf0367fc00/nixos/modules/programs/chromium.nix)); that applies to every profile of the browser, not one site. Unverified: whether a policy-installed window behaves well under Hyprland; how to deliver the policy on macOS (the Chrome Help page above does not cover it).
- **Chromium-family browsers per OS (pinned nixpkgs, `meta.platforms`):** `chromium` and `ungoogled-chromium` are Linux-only (153.0.8010.52). `google-chrome` (153.0.8010.53, unfree) and `brave` (1.95.104) exist for aarch64-darwin and Linux. Homebrew casks: `google-chrome` 155.0.8059.40, `brave-browser` 1.97.56.0, `helium-browser` 0.19.2.1; the Homebrew `chromium` cask is disabled ([cask API](https://formulae.brew.sh/api/cask/chromium.json)).

*Firefox and Zen:*

- **Firefox "web apps" (source name: Taskbar Tabs).** Shipped in Firefox 143 (2025-09-16), Windows only ([143 release notes](https://www.firefox.com/en-US/firefox/143.0/releasenotes/)). Mozilla's in-tree docs say: Windows on by default; Linux available but disabled by default (unsandboxed and Flatpak); macOS not available, because macOS ties one visible app to one process while web apps share the browser's process ([docs index.md](https://github.com/mozilla-firefox/firefox/blob/main/browser/components/taskbartabs/docs/index.md)). The pref `browser.taskbarTabs.enabled` defaults to true on Windows and false elsewhere ([firefox.js](https://github.com/mozilla-firefox/firefox/blob/main/browser/app/profile/firefox.js)).
- **Linux status.** Support landed for Firefox 150 ([bug 1982733](https://bugzilla.mozilla.org/show_bug.cgi?id=1982733), fixed, 150 branch). "Enable by default on Linux" ([bug 2021459](https://bugzilla.mozilla.org/show_bug.cgi?id=2021459)) is still NEW. On 2026-09-16 its author wrote that she probably will not work on it any more and listed open problems: GNOME desktop-entry handling ([bug 2021458](https://bugzilla.mozilla.org/show_bug.cgi?id=2021458), NEW), the DynamicLauncher portal on Kubuntu, and Snap. The NixOS problem (shortcuts embed a store path that breaks on update) is fixed ([bug 2021897](https://bugzilla.mozilla.org/show_bug.cgi?id=2021897), 2026-04-22).
- **macOS status.** [Bug 1982734](https://bugzilla.mozilla.org/show_bug.cgi?id=1982734) (macOS meta) is NEW, unassigned; its blocker "implement createIcon for macOS" ([bug 1986113](https://bugzilla.mozilla.org/show_bug.cgi?id=1986113)) is NEW.
- **It would not meet the requirement even where on.** The docs say these windows "by design" still look like a browser. A URL bar stays visible, with its event handling disabled ([bug 1958142](https://bugzilla.mozilla.org/show_bug.cgi?id=1958142)); a later report complains it is fixed and very short ([bug 2030814](https://bugzilla.mozilla.org/show_bug.cgi?id=2030814), closed as a duplicate). New tabs are moved into a separate normal window ([bug 1945000](https://bugzilla.mozilla.org/show_bug.cgi?id=1945000)). Add-ons can still open a tab inside the window ([bug 1986426](https://bugzilla.mozilla.org/show_bug.cgi?id=1986426), NEW). The meta bug is [1915736](https://bugzilla.mozilla.org/show_bug.cgi?id=1915736).
- **Zen.** The 1.23.2b tag (2026-10-09) pins Firefox 157.0.1 ([surfer.json](https://github.com/zen-browser/desktop/blob/1.23.2b/surfer.json)), and 157.0 is Firefox stable per [Mozilla product-details](https://product-details.mozilla.org/1.0/firefox_versions.json) (LATEST_FIREFOX_VERSION 157.0.1), so the Linux code is present. Zen has no web-app UI of its own: a native-PWA request ([discussion 14454](https://github.com/zen-browser/desktop/discussions/14454), opened 2026-07-02) is open, an earlier one ([#285](https://github.com/zen-browser/desktop/issues/285)) was closed as not planned on 2026-01-28. Users report flipping the hidden pref works with rough edges, for example PWA windows inheriting the sidebar and tab layout ([#14314](https://github.com/zen-browser/desktop/issues/14314), open, updated 2026-10-10).
- **PWAsForFirefox (`firefoxpwa`).** An out-of-tree tool with its own modified Firefox runtime; installed apps have no tabs and no address bar ([README](https://github.com/filips123/PWAsForFirefox)). v2.20.1 on 2026-10-09, MPL-2.0. Its README says it patches the browser UI at runtime with JS and CSS, which Mozilla does not support and Firefox updates can break. It is a separate Firefox, not Zen. macOS: Homebrew formula; known limit: apps launched while another is running merge into it unless each has its own profile ([limitations](https://pwasforfirefox.filips.si/about/current-limitations/)). Nix: nixpkgs `firefoxpwa` 2.19.0 is Linux-only (platforms list has no darwin; it bundles the nixpkgs Firefox as runtime, [package](https://github.com/NixOS/nixpkgs/blob/b6c98e9e6633ee64753b594ff4a5febf0367fc00/pkgs/by-name/fi/firefoxpwa-unwrapped/package.nix)).

*Safari web apps, macOS 14+:*

- **Apple's page** ([Use Safari web apps on Mac](https://support.apple.com/en-us/104996)): macOS Sonoma 14 or later; File > Add to Dock (or Share > Add to Dock); saved in `~/Applications`; the window has a streamlined toolbar with back/forward, Share and extension buttons; no history, cookies or data shared with Safari; settings let you change name, URL and icon, and hide navigation controls. The page does not mention tabs and does not say how links to other sites are handled; nothing on automation.
- **Secondary** ([Eclectic Light, 2023-10-05, Sonoma-era](https://eclecticlight.co/2023/10/05/how-do-sonomas-web-apps-work/)): the bundle holds no executable, is confined to its origin domain, and links leaving that domain (and all downloads) open in Safari. A hand-built bundle is refused by LaunchServices unless registered, so scripted creation is not practical. Unknown: whether this still holds on macOS 26 or 27.
- **Declarative?** No supported way found. Creation is through the Safari UI; GUI scripting is a guess I did not test. The bundles live in `~/Applications` outside Nix.

*Declarative Nix building blocks* (Home Manager at the pinned rev):

- **`xdg.desktopEntries.<name>`** has options `name`, `exec`, `icon`, `comment`, `terminal`, `genericName`, `mimeType`, `categories`, `startupNotify`, `noDisplay`, `prefersNonDefaultGPU`, `settings` (free-form extra keys, so `StartupWMClass` fits), `actions`, `type`. It asserts Linux ([desktop-entries.nix](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/misc/xdg/desktop-entries.nix)). So `exec = "chromium --app=URL --user-data-dir=..."` is expressible directly.
- **`programs.firefoxpwa`** declares profiles and sites keyed by ULID, writes `firefoxpwa/config.json`, and generates desktop entries only on Linux by default (`desktopEntry.enable` defaults to `isLinux`) ([firefoxpwa.nix](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/programs/firefoxpwa.nix)).
- **`programs.chromium`** (HM) offers `package`, `commandLineArgs`, `extensions`, `nativeMessagingHosts`, `dictionaries`; it is not a web-app generator ([chromium.nix](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/programs/chromium.nix)).
- **macOS app placement:** `targets.darwin.copyApps` (default directory `Applications/Home Manager Apps`) and `linkApps` exist ([copyapps.nix](https://github.com/nix-community/home-manager/blob/0b2f1129177f70c5f0f5d88bb53c49ca47d0bfc0/modules/targets/darwin/copyapps.nix)), but they place a `.app` that some package builds; nothing builds a web-app `.app` for you.
- **Helper flakes.** Only one small HM module found: [chobbledotcom/nix-chromium-webapps](https://github.com/chobbledotcom/nix-chromium-webapps) (7 stars, no license, last push 2025-09-28) and a 0-star fork (2026-10-07). It generates `chromium --app --user-data-dir` launchers plus a `StartupWMClass=chrome-<host>__-Default` desktop entry, hard-codes `pkgs.chromium`, so Linux only. Treat it as a pattern, not a dependency. No maintained macOS `.app` generator found. [Pake](https://github.com/tw93/Pake) (Tauri, 62k stars, v3.17.3 2026-10-05) turns a URL into a native app on macOS and Linux but needs a Rust/Node build and is not in nixpkgs (init PR [#568899](https://github.com/NixOS/nixpkgs/pull/568899) open).

**Implications for this repo:**

- Zen cannot be the engine. On macOS Firefox has no web-app feature; on Linux the pref is off by default, the URL bar stays, and new tabs spill into a normal window.
- "Nothing else can be opened beside it" is not a Chromium `--app` guarantee: Ctrl+T and `target=_blank` open a normal window of the same profile. A dedicated `--user-data-dir` at least keeps that window empty of other browsing. No switch or policy found that forbids it (Unknown whether one exists). The strict options are an Electron wrapper (for example `teams-for-linux`, see Q2), or a Safari web app on macOS (links leave to Safari per the secondary source).
- Linux/Hyprland: `xdg.desktopEntries` with a Chromium `--app` command is a few lines per site and sits naturally in `modules/home.nix`; its WM class has to be read from a running instance (`hyprctl clients`) before writing window rules (Unverified: the Wayland app_id Chromium assigns).
- macOS: the Chromium route needs a Chromium-family browser (nixpkgs `chromium` is not available on aarch64-darwin at this pin, so `google-chrome`/`brave` from nixpkgs or a cask such as `helium-browser`) plus a hand-made `.app` wrapper derivation, with nothing maintained to copy. Safari's "Add to Dock" gives the cleanest result but is manual and cannot be reproduced by `darwin-rebuild`.
- A uniform cross-platform declaration is therefore not available off the shelf. The closest is one shared list of `{name, url}` consumed by two small generators (desktop entries on Linux, `.app` bundles on macOS), which would be new code.

### 2. Microsoft Teams clients

**Findings**

- **macOS, official.** Homebrew cask `microsoft-teams`, version 26261.303.5165.1465, macOS 14 or later, auto-updating, installs `Microsoft Teams.app` from `statics.teams.cdn.office.net` ([cask API](https://formulae.brew.sh/api/cask/microsoft-teams.json)). nixpkgs also has `teams` (25255.703.3981.5698, aarch64-darwin only, unfree, a repack of the same `.pkg`; [package](https://github.com/NixOS/nixpkgs/blob/b6c98e9e6633ee64753b594ff4a5febf0367fc00/pkgs/by-name/te/teams/package.nix)), which is older than the cask.
- **Linux, official.** Microsoft's client overview (updated 2026-07-21) lists Linux as unsupported: no Teams desktop client ([Learn](https://learn.microsoft.com/en-us/microsoftteams/get-clients)). Its system-requirements page (same date) adds that Linux users have Teams for Web and Teams as a PWA, and lists web support for Edge, Chrome and Firefox on Windows/macOS/Linux and Safari on macOS ([Learn](https://learn.microsoft.com/en-us/microsoftteams/teams-client-system-requirements)). The PWA page says the install is for Edge or Chrome ([Learn](https://learn.microsoft.com/en-us/microsoftteams/teams-progressive-web-apps)). Unverified: Microsoft's original 2022 retirement announcement; I only reached community and Q&A pointers about it (for example [Tech Community discussion](https://techcommunity.microsoft.com/discussions/microsoftteams/end-of-the-road-for-teams-linux-desktop-client/3630968), secondary).
- **`teams-for-linux`** ([IsmaelMartinez/teams-for-linux](https://github.com/IsmaelMartinez/teams-for-linux)): unofficial, GPL-3.0, created 2018, 5.1k stars, pushed 2026-10-11. It wraps the Teams web app in Electron (system notifications, tray, screen sharing, custom backgrounds, multiple profiles). Releases are weekly: 2.22.0 (2026-09-18), 2.23.0 (09-26), 2.24.0 (10-03), 2.25.0 (10-09). Release assets include AppImage, deb, rpm, snap, tar.gz and also macOS (dmg/zip) and Windows builds.
- **In nixpkgs:** `teams-for-linux` is 2.22.0 at the pin (2.25.0 on master), license GPL-3.0-or-later, five listed maintainers, platforms include `aarch64-darwin` and Linux. The package builds with Electron 43; on Darwin it builds a `.app` into `$out/Applications`; on Linux the wrapper adds Wayland flags when `NIXOS_OZONE_WL` is set ([package](https://github.com/NixOS/nixpkgs/blob/b6c98e9e6633ee64753b594ff4a5febf0367fc00/pkgs/by-name/te/teams-for-linux/package.nix)). `nix build --dry-run` shows the aarch64-darwin output would be fetched from the binary cache (128 MiB download), so no local build.

**Implications for this repo:**

- If "web app in its own window" is meant as the goal, `teams-for-linux` is the only packaged candidate that gives a single-window wrapper on both machines from one `home.packages` entry, and its Electron window cannot spill tabs. Costs: it is an unofficial wrapper of the web client (feature set equals Teams web) and it bumps weekly while nixpkgs lags a few releases.
- If the macOS requirement is merely "do not use the heavy client", the official cask is a one-line addition to `homebrew.casks` in `modules/darwin.nix`; Linux then needs the Q1 route or `teams-for-linux`.
- Unknown: whether a personal (consumer) Teams account is covered by Microsoft's web and PWA statements; the pages above address organisation accounts.

**Findings**

  - Mac App Store: "WhatsApp Messenger" by WhatsApp Inc., id **310633997**, bundle id `net.whatsapp.WhatsApp` ([App Store page](https://apps.apple.com/us/app/whatsapp-messenger/id310633997); iTunes lookup `https://itunes.apple.com/lookup?id=310633997&country=us` returned version 26.40.77 released 2026-10-12, free, 402 MB). The lookup record is the iPhone listing (`features: iosUniversal`, supported devices include `MacDesktop-MacDesktop`); the store page lists a Mac requirement of macOS 12.1 or later. The older Mac-only id 1147396723 returns no result. Unverified: whether the Mac App Store install is a native Mac build or the iPhone app running on the Mac.
  - `mas` documents that iOS and iPadOS apps are unsupported ([mas README](https://github.com/mas-cli/mas)), so if the listing is the iPhone app, `homebrew.masApps` may not install it. Unverified: how `mas` treats this listing.

**Implications for this repo:**

- macOS: `homebrew.casks = [ ... "whatsapp" ]` is the verified low-effort answer. The `masApps` entry is risky until someone confirms the listing is a Mac build; also the cask and a Mac App Store copy share a bundle id, so do not install both.
- Linux: no official client exists, so "official where possible" cannot be met. Choices are a Q1-style web-app window (closest to what the user asked for Teams, and loads the official web client), `zapzap` (best-maintained wrapper in nixpkgs, one minor behind upstream), or ZapFast (fast and native but carries the account-suspension warning). `karere` and `whatsie` in nixpkgs lag major rewrites.

### 4. Claude desktop on Linux

**Findings**

- **Anthropic ships an official Linux desktop app, in beta** (Chat, Cowork and Claude Code Desktop). Its docs ([Claude Desktop on Linux (beta)](https://code.claude.com/docs/en/desktop-linux)) say:
  - **Platforms:** Ubuntu 22.04+ or Debian 12+, x86_64 or arm64. Debian-based others may work but are untested. Fedora, RHEL, Arch and other non-Debian distributions are not supported; use the CLI there.
  - **Install:** an apt repository (`deb [arch=amd64,arm64 signed-by=...] https://downloads.claude.ai/claude-desktop/apt/stable stable main`), package `claude-desktop`, signing key fingerprint `31DDDE24DDFAB679F42D7BD2BAA929FF1A7ECACE`, or a downloaded `.deb` from the repo's pool. No other format is documented.
  - **Updates:** none built in; updates arrive through apt.
  - **Cowork** runs a QEMU/KVM virtual machine hosted by the app: needs hardware virtualization, `qemu-system-x86`, `ovmf`, `virtiofsd` (x86_64), access to `/dev/kvm` and `/dev/vhost-vsock` (via the `kvm` group).
  - **Not yet in the beta:** Computer Use, dictation; the Quick Entry hotkey works on X11 and needs the desktop's GlobalShortcuts portal on native Wayland.
  - Claude's [download page](https://claude.com/download) links Linux to this doc page, not to a file. A July 2026 news report dates the beta launch ([OMG! Ubuntu, updated 2026-07-13](https://www.omgubuntu.co.uk/2026/07/claude-desktop-linux-beta), secondary).
- **The package index** (`https://downloads.claude.ai/claude-desktop/apt/stable/dists/stable/main/binary-amd64/Packages`, `Release` dated 2026-10-09) lists 52 versions; newest is 2.31226.1 (amd64 `.deb`, 181,377,680 bytes, SHA256 `5a9bebdfcb1df6ce38767b373f3a7fabf77156a2ddd8a3f5d04961da5bde305e`; arm64 174,060,344 bytes). The macOS Homebrew cask `claude` is 2.31226.1 as well ([cask API](https://formulae.brew.sh/api/cask/claude.json)), so both platforms are in step. Installed size about 590 MB; Depends include GTK3, NSS, libsecret, PipeWire, xdg-desktop-portal. Unknown: the package's licence terms beyond "proprietary" (nixpkgs-style classification would be unfree).
- **nixpkgs:** no `claude-desktop` attribute at the pin, on `nixos-unstable` (`6510408d`, 2026-10-10), or on `master` (`0b7d0295`, 2026-10-12) (checked `pkgs/by-name/cl/`). An init PR is open: [NixOS/nixpkgs#537215](https://github.com/NixOS/nixpkgs/pull/537215) "claude-desktop: init at 2.26454.2", created 2026-06-30, updated 2026-10-11, adds a 307-line `package.nix` for x86_64 and aarch64 Linux, LLM-assisted label, two approvals recorded; in July review it was blocked by missing maintainer-list entries. An older PR, [#502081](https://github.com/NixOS/nixpkgs/pull/502081) (init at 1.20186.1), is also still open.
- **Community flakes that repack the official `.deb`** (all pushed 2026-09 or 2026-10; I read READMEs only, not the code):
  - [danielbodart/claude-desktop](https://github.com/danielbodart/claude-desktop): hourly updater that reads the hash from the PGP-verified apt index, releases tagged, NixOS module `programs.claude-desktop` with a `cowork` block that adds users to `kvm` and provides UEFI firmware at the FHS path the app expects; x86_64 and aarch64; licence file not recognised (NOASSERTION).
  - [poeck/claude-desktop-nix-flake](https://github.com/poeck/claude-desktop-nix-flake) (MIT, hourly checks, NixOS module, overlay), [tomsch/claude-desktop-nix](https://github.com/tomsch/claude-desktop-nix) (MIT, x86_64 only, passes `--no-sandbox` because the setuid sandbox cannot live in the store), [stslex/claude-desktop-nix](https://github.com/stslex/claude-desktop-nix) (adds an FHS-env variant with `npx`, `uvx`, `docker`, `git`; checks that `--no-sandbox` never appears).
  - Pre-official repacks that unpack the Windows or macOS app: [k3d3/claude-desktop-linux-flake](https://github.com/k3d3/claude-desktop-linux-flake) (375 stars, Apache-2.0, last push 2025-11-25), `Reginleif86/claude-cowork-nix` (archived, marked superseded), and the Debian repack [aaddrick/claude-desktop-debian](https://github.com/aaddrick/claude-desktop-debian) (5.4k stars, active; I did not check whether it still targets the Windows build). These are no longer needed.
  - Star counts are tiny for the official-`.deb` flakes (0 to 6), so none has a track record. Sandbox handling differs between them (drop the setuid helper and rely on user namespaces vs `--no-sandbox`).

**Implications for this repo:**

- The premise "no official Linux app" is outdated: there is one, packaged only for apt. On NixOS it must be repackaged: unpack the `.deb`, `autoPatchelfHook`, wrap, point the QEMU/firmware lookups at Nix paths. That work is done in several small flakes and in the open nixpkgs PR.
- Choices: (a) wait for or cherry-pick PR #537215 (an overlay from the PR branch; becomes `pkgs.claude-desktop` when merged), (b) take a flake input and follow the repo's nixpkgs, (c) vendor a ~300-line derivation pinned to the signed apt index hash. Option (c) fits the repo's pinning habits and matches what danielbodart's flake does (hash from the signed index) without trusting a one-person flake to keep updating.
- Cowork needs a NixOS-side `kvm` group membership and a VM-capable kernel; not an issue to expect on a Framework 16 laptop, but the `kvm` group and firmware path are real configuration items.
- macOS side is unchanged: the `claude` cask is current.

### 5. Spotifast

**Findings**

- **Project.** [crmne/spotifast](https://github.com/crmne/spotifast): Spotify client in Rust with egui, playback through librespot, MIT, created 2026-08-27, 7.4k stars, v0.12.0 on 2026-10-03 (0.9.1 on 2026-09-22, 0.10.0 on 09-24, 0.11.0 on 09-26, 0.12.0 on 10-03: very fast release cadence). Platforms: Linux, macOS, Windows. The project was renamed (earlier release assets are named `fastpotify-*`). Its sibling ZapFast is covered in Q3.
- **Release assets at v0.12.0** ([releases](https://github.com/crmne/spotifast/releases/tag/v0.12.0)): macOS universal DMG; Linux x86_64 and aarch64 tarballs, AppImages, `.deb`, `.rpm`; x86_64 Flatpak (side-loaded, Flathub planned); Windows installers and zips (x86_64 and arm64); checksums with a signature file; source tarball.
- **Per platform** ([download page](https://spotifast.rocks/download/)):
  - macOS: DMG, or `brew install --cask crmne/tap/spotifast` (cask file in [crmne/homebrew-tap](https://github.com/crmne/homebrew-tap/blob/main/Casks/spotifast.rb) at 0.12.0). The page says macOS builds are notarized since 0.8.0.
  - Linux: AppImage needs glibc 2.39+ and FUSE and bundles none of its own libraries; Arch AUR `spotifast-bin`; tarball needs ALSA/PulseAudio/PipeWire and Wayland or X11.
  - Nix: the repo has a `flake.nix` with `packages.default` (alias `spotifast`) for aarch64-darwin, x86_64-darwin, aarch64-linux, x86_64-linux; it builds from source with `rust-overlay` and `fetchCargoVendor`, wraps `LD_LIBRARY_PATH` on Linux (wayland, libxkbcommon, GL, X11 are `dlopen`ed), and on Darwin assembles `Spotifast.app` and ad-hoc signs it with `rcodesign` ([flake.nix](https://github.com/crmne/spotifast/blob/main/flake.nix)). The download page gives snippets for NixOS (`environment.systemPackages`), nix-darwin (add `environment.pathsToLink = [ "/Applications" ]`, app appears under `/Applications/Nix Apps`) and Home Manager (`home.packages`).
- **Not in nixpkgs.** The `spotifast` attribute is absent at the pin.
- **Spotify Premium.** Required for playback; free accounts can browse and search only ([README](https://github.com/crmne/spotifast#readme), [what-is-spotifast](https://spotifast.rocks/what-is-spotifast/)). Further limits from [what Spotify allows](https://spotifast.rocks/what-spotify-allows/): 320 kbps maximum, no lossless, no local files, no offline downloads, no crossfade, no Jam/Blend. The maintainers write that they know of no confirmed account bans but cannot predict Spotify's choices; the app is unofficial.

**Implications for this repo:**

- macOS: either the cask (needs `taps = [ ... "crmne/tap" ]` in `modules/darwin.nix`; fits the existing `cleanup = "zap"` model since the cask would be declared) or the flake package (Rust source build, Nix-managed, ad-hoc signed). The cask is a prebuilt, notarized app; the flake build is longer but identical on both machines.
- Linux: the flake is the Nix-native route (source build, no known binary cache: Unknown whether the project publishes one); AppImage/Flatpak are the non-Nix routes. As an `inputs.spotifast` it needs `inputs.nixpkgs.follows` to keep one nixpkgs, and it pulls `rust-overlay`.
- Not a replacement for Deezer or the official Spotify app if lossless or offline is wanted.
- Unknown: whether the user has Premium (blocking).

### Open questions

1. Is the real requirement for Teams and WhatsApp strict (no other window can open), or "no tabs and no URL bar in that window"? Chromium `--app` meets the second but not the first; Electron wrappers or Safari web apps meet the first.
2. Which Chromium-family browser should be the `--app` engine on each machine? nixpkgs `chromium` is Linux-only at the pin; macOS would need `google-chrome`/`brave` from nixpkgs or a cask such as `helium-browser`. Should the engine be separate from Zen (it must be)?
3. Is an unofficial WhatsApp client acceptable? Web wrappers load the official web client; ZapFast re-implements the protocol and its README warns of suspension. WhatsApp's own terms were not read.
4. Is the Mac App Store WhatsApp (id 310633997) a native Mac build or the iPhone app on the Mac? Needs a look at the listing on the user's Mac. Until then prefer the `whatsapp` cask.
5. Teams: personal (consumer) or work/school account? Microsoft's pages cover organisation accounts; consumer behaviour on the web/PWA path was not checked.
6. Spotify: does the user have Premium? Is a source build via the flake acceptable on both machines, or is the cask (macOS) plus AppImage/Flatpak (Linux) preferred?
7. Claude desktop on NixOS: wait for nixpkgs PR #537215, depend on a community flake, or vendor a derivation? None of the flakes was audited beyond its README.
8. Framework 16 GPU configuration (decides whether GeForce NOW's Xorg-versus-Wayland requirement bites) and whether the machine will have virtualization enabled for Claude's Cowork.
9. Unverified by running: Chromium `--app` behaviour (derived from `main`, nixpkgs ships 153), Hyprland app_id/class for `--app` windows, Safari web-app link handling on macOS 26 or 27, delivery of `WebAppInstallForceList` on macOS, whether `teams-for-linux` and its Electron build behave well on macOS under the repo's TCC re-sign setup.
10. Unknown: whether any Chromium switch or policy stops the spill-over normal window for `--app` windows.
11. Unknown: whether Spotifast's flake publishes a binary cache.
