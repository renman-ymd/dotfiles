All receipt-based installers write the receipt to the same path, and the DetSys and NixOS ones both name the installer copy `/nix/nix-installer`, so the file name alone does not identify which installer ran. Lix is the only one using `/nix/lix-installer`.

**macOS (all installers)**
- Admin rights needed. The official script rejects `--no-daemon` on macOS: macOS is multi-user only ([script](https://github.com/NixOS/nix/blob/2.35.2/scripts/install-nix-from-tarball.sh)).
- What the official installer does on macOS ([manual](https://nix.dev/manual/nix/latest/installation/installing-binary)): creates an APFS volume, adds `nix` to `/etc/synthetic.conf`, adds a mount line to `/etc/fstab`, and a LaunchDaemon that mounts the volume. With FileVault on, it generates a password, stores it in the System keychain and encrypts the volume. The script puts it at service = volume UUID, label "`<volume label>` encryption password", in `/Library/Keychains/System.keychain` ([create-darwin-volume.sh](https://github.com/NixOS/nix/blob/2.35.2/scripts/create-darwin-volume.sh)).
- Lix on macOS ([planner/macos](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/planner/macos/mod.rs) and the actions it calls): same volume/synthetic/fstab scheme; the volume is encrypted when FileVault is active (or an existing store volume is encrypted), with the password in `/Library/Keychains/System.keychain` under service "Nix Store" ([encrypt_apfs_volume.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/action/macos/encrypt_apfs_volume.rs)); LaunchDaemons `org.nixos.nix-daemon`, `org.nixos.darwin-store`, and (only when profile modification is on) `systems.lix.nix-installer.nix-hook`, which re-adds the shell hook after macOS upgrades ([create_nix_hook_service.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/action/macos/create_nix_hook_service.rs)); Time Machine exclusions via `tmutil addexclusion` on `/nix/store` and `/nix/var`; group `nixbld` GID 350 and users `_nixbld1`..`_nixbld32` with UIDs from 351 (flags `--nix-build-group-id`, `--nix-build-user-id-base`, `--nix-build-user-count`, default 32).
- **Managed Macs: Lix preflight aborts on a conflicting MDM profile.** Before installing, the macOS planner loads the installed configuration profiles and refuses to continue if one carries a SystemUIServer mount-control policy ("Restrictions - Media", internal hard disk options), because that policy interferes with mounting the Nix Store volume; the error lists the offending profile and points at a Determinate write-up. If the profile data cannot be loaded the check is skipped with a warning ([check_suis in macos/mod.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/planner/macos/mod.rs), [profile_queries.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/planner/macos/profile_queries.rs)). The same planner also refuses to run under Rosetta. **Unknown:** how the official script behaves under such a profile, and how endpoint-security or MDM tooling reacts to the downloaded installer binary and the new LaunchDaemons.
- **Lix edits `/etc/zshenv` even with `--no-modify-profile`**: the macOS planner pushes `ConfigureRemoteBuilding` unconditionally, while the hook service and shell-profile edits are gated on `modify_profile` ([macos/mod.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/planner/macos/mod.rs), [configure_remote_building.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/action/macos/configure_remote_building.rs)). The block is guarded to SSH sessions and is reverted on uninstall.
- Shell rc edits (Lix): inserts a `# Nix` ... `# End Nix` block that sources `/nix/var/nix/profiles/default/etc/profile.d/nix-daemon.sh` at the top of `/etc/bashrc`, `/etc/profile.d/nix.sh`, `/etc/bash.bashrc`, `/etc/zshrc`, `/etc/zsh/zshrc` (creating missing parent directories and files), plus fish `conf.d/nix.fish` where a fish prefix exists ([configure_shell_profile.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/action/common/configure_shell_profile.rs)). Official multi-user: same file list, but it copies each to `<file>.backup-before-nix` first.
- **Uninstall, Lix (receipt revert, in reverse order of the plan):** removes the injected rc blocks by exact text match (and deletes a file that ends up empty; if something rewrote the file so the block no longer matches, the block silently stays) ([create_or_insert_into_file.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/action/base/create_or_insert_into_file.rs)); unloads/removes the LaunchDaemons; removes users and group via `dscl`; deletes `/etc/nix/nix.conf` and `nix.custom.conf` outright, including any later hand edits ([create_or_merge_nix_config.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/action/base/create_or_merge_nix_config.rs)); removes the fstab line and the `synthetic.conf` entry, deletes the APFS volume, deletes the keychain item, runs `tmutil removeexclusion`. It refuses to run while nix-darwin is still installed ([quirks.md](https://git.lix.systems/lix-project/lix-installer/src/branch/main/docs/quirks.md)).
- **Uninstall, official manual (macOS):** 7 manual steps: restore `/etc/{zshrc,bashrc,bash.bashrc}.backup-before-nix`, unload and delete both LaunchDaemons, delete `_nixbld*` users and `nixbld` group, edit `/etc/fstab` with `vifs`, edit `/etc/synthetic.conf`, delete `/etc/nix` and the per-user files, `diskutil apfs deleteVolume /nix`. The manual does not mention the keychain item. It says an empty `/nix` mount stub remains until the next reboot ([uninstall.md](https://github.com/NixOS/nix/blob/2.35.2/doc/manual/source/installation/uninstall.md)). **Unknown:** whether the Lix revert, which refreshes synthetic objects and describes itself as removing `/nix` ([create_synthetic_objects.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/action/macos/create_synthetic_objects.rs)), avoids the reboot in practice.

**Non-NixOS Linux**
- Official script: `--daemon` (multi-user) needs systemd and sudo; `--no-daemon` (single-user) makes `/nix` owned by the invoking user and uses sudo only to `mkdir`/`chown /nix` ([manual](https://nix.dev/manual/nix/latest/installation/installing-binary)). The manual claims multi-user is the default on Linux with systemd; the 2.35.2 script source sets `INSTALL_MODE=no-daemon` for every non-Darwin OS and merely prints a note that multi-user is possible ([script](https://github.com/NixOS/nix/blob/2.35.2/scripts/install-nix-from-tarball.sh)). The two disagree, so pass `--daemon` or `--no-daemon` explicitly. The manual says SELinux systems get single-user.
- Official single-user uninstall is one `rm -rf` of `/nix` and the per-user dirs, plus removing the rc lines the installer appended to the first writable of `~/.bash_profile`/`~/.bash_login`/`~/.profile` and of `~/.zshenv`/`~/.zshrc`, tagged `# added by Nix installer`, and `~/.config/fish/conf.d/nix.fish` if `~/.config/fish` existed ([script](https://github.com/NixOS/nix/blob/2.35.2/scripts/install-nix-from-tarball.sh)). It also runs `nix-channel --add` and `--update` unless `--no-channel-add`, creating `~/.nix-channels`, `~/.nix-defexpr` and a nixpkgs download.
- Multi-user Linux (official, [install-systemd-multi-user.sh](https://github.com/NixOS/nix/blob/2.35.2/scripts/install-systemd-multi-user.sh)): `/etc/systemd/system/nix-daemon.service` and `.socket`, `/etc/tmpfiles.d/nix-daemon.conf` (symlinks into `/nix`), group `nixbld` GID 30000, users `nixbld1..32` UIDs from 30001, `/etc/nix/nix.conf`. Manual uninstall list: [uninstall.md](https://nix.dev/manual/nix/latest/installation/uninstall).
- Lix/DetSys/NixOS on Linux: units placed at `/etc/systemd/system/nix-daemon.{service,socket}` and `nix-daemon@.service` (copy versus symlink not checked), `/etc/tmpfiles.d/nix-daemon.conf`, SELinux policy installed when SELinux is detected and removed again with `semodule --remove nix` on uninstall ([planner/linux.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/planner/linux.rs), [provision_selinux.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/action/linux/provision_selinux.rs)). The Linux planner refuses to install when `nix-env --version` succeeds (an existing Nix on PATH), when `/etc/NIXOS` exists, and on WSL1. Uninstall needs `userdel`/`deluser` and `groupdel`/`delgroup` present, and, when the receipt says systemd with daemon start, a running systemd (`/run/systemd/system`).

**WSL2**
- systemd is off by default in `wsl.conf` and needs WSL from the Store; enabling means writing `[boot]` / `systemd=true` to `/etc/wsl.conf` then running `wsl.exe --shutdown` from Windows ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)); the announcement gives 0.67.6 as the minimum WSL version ([devblog](https://devblogs.microsoft.com/commandline/systemd-support-is-now-available-in-wsl/)). The Learn page says the `[boot]` section is only available on Windows 11 and Server 2022.
- Lix/DetSys/NixOS installers: strongly recommend enabling systemd first; otherwise pass `--init none`, which makes Nix usable only by root ("sudo -i nix ..."). They detect WSL1 as `WSL_DISTRO_NAME` set and `WSL_INTEROP` unset. **Unverified:** whether a WSL2 distro with `[interop] enabled=false` leaves `WSL_INTEROP` unset and is then misread as WSL1 and refused.
- Without systemd and without root-only Nix, the only documented path is the official script's `--no-daemon`.

**Implications for this repo:** The three receipt-based installers give a real uninstaller; the official script does not, so a removal script built around it would have to re-implement the manual's steps per OS. Pick Lix's installer (matches the personal machines' Lix, no telemetry) and keep the official script only as a documented fallback for systemd-less WSL. The fallback needs its own removal branch: single-user `rm -rf` plus rc-line stripping on `# added by Nix installer`. Lix drops Intel Macs, so an Intel work Mac needs the official script (macOS 14+) or the legacy flag. On a managed Mac, the MDM media-restriction preflight is a possible hard failure; the script should surface that error text rather than retry. Use `--no-confirm`; consider `--no-modify-profile` so no `/etc/*rc` file is touched (the kit then sources `nix-daemon.sh` itself), but note macOS still gets the `/etc/zshenv` block. Pin the installer by URL (`install.lix.systems/lix/tag/v<version>`, the form Lix's own uninstall error messages use) because the version served at the default URL is unknown and the default Lix version it carries is not stated in the docs. The removal script must run as root (Lix's uninstaller re-execs itself under `sudo --set-home`) and must delete `~/.nix-profile`, `~/.local/state/nix`, `~/.cache/nix`, `~/.local/share/nix`, `~/.config/nix` (and root's equivalents) itself, because grep of the Lix installer source finds no code that touches per-user directories.

### 2. Detecting a preinstalled Nix

- Receipt-based installers leave `/nix/receipt.json` plus an installer copy: `/nix/lix-installer` (Lix) or `/nix/nix-installer` (DetSys or NixOS) ([Lix README](https://git.lix.systems/lix-project/lix-installer/src/branch/main/README.md), [DetSys README](https://github.com/DeterminateSystems/nix-installer/blob/main/README.md), [NixOS README](https://github.com/NixOS/nix-installer/blob/main/README.md)). The receipt is JSON with `version`, `actions`, `planner` ([plan.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/plan.rs)). No documented field names the installer; the Lix receipt's planner settings carry a `nix_package_url` pointing at releases.lix.systems (inference from [settings.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/settings.rs); the receipt itself not read).
- Determinate Nix additionally leaves `/usr/local/bin/determinate-nixd` and launchd `systems.determinate.nix-daemon` ([source](https://github.com/DeterminateSystems/nix-installer/tree/main/src/action)).
- The official script writes no receipt. Its marks are `/nix/store`, `/etc/nix/nix.conf`, `<rc>.backup-before-nix` files (multi-user), `# added by Nix installer` lines in `~/.profile`-style files (single-user), the systemd symlinks above, and on macOS `/Library/LaunchDaemons/org.nixos.nix-daemon.plist` ([multi-user script](https://github.com/NixOS/nix/blob/2.35.2/scripts/install-multi-user.sh)).
- The Lix Linux planner itself uses `nix-env --version` succeeding as its "Nix already installed" test, and aborts ([linux.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/planner/linux.rs)). I found no equivalent "Nix already installed" check in the macOS planner; its pre-install checks cover Rosetta and conflicting MDM media-restriction profiles (the macOS volume/synthetic actions would likely fail on an existing `/nix`, but that behaviour is **Unknown**).
- `command -v nix` only tells you Nix is on this shell's PATH. `nix-daemon.sh` is sourced from `/etc/zshrc`-style files, so a non-interactive or non-login shell may not see an installed Nix (observation from [configure_shell_profile.rs](https://git.lix.systems/lix-project/lix-installer/src/branch/main/src/action/common/configure_shell_profile.rs): the hooks live in interactive rc files). The Lix troubleshooting guide says to source `/nix/var/nix/profiles/default/etc/profile.d/nix-daemon.sh` by hand ([troubleshooting.md](https://git.lix.systems/lix-project/lix-installer/src/branch/main/docs/troubleshooting.md)). Distro-packaged Nix (apt/dnf/pacman): **Unknown** how to detect it from primary sources.
- A system with NixOS or nix-darwin manages Nix itself (`/etc/NIXOS`, `/run/current-system`); out of scope for the kit.

**Implications for this repo:** Detection by inspection cannot prove who installed Nix. The only reliable rule is to record provenance at install time: the install script writes its own marker (installer name, installer version, SHA-256 of `/nix/receipt.json`, date) into a kit-owned location, and the removal script runs the uninstaller only if that marker exists and the receipt hash still matches. Then "Nix was there before" simply means "no marker", and Nix stays. Before installing, the script should run a pre-flight that treats any of `/nix`, `/etc/nix`, `nix` on PATH, `/nix/var/nix/profiles/default/bin/nix`, `~/.nix-profile/bin/nix` as "preinstalled", and look through the absolute paths rather than only PATH. The marker file is itself a trace, so the removal script deletes it last.

### 3. Ways to deliver tools and config through Nix

**3a. Home Manager standalone**
- First run: `nix run home-manager/master -- init --switch` (generates `~/.config/home-manager`), or against your own flake `home-manager switch --flake <uri>`; flakes need `nix-command flakes` enabled ([flakes standalone](https://github.com/nix-community/home-manager/blob/master/docs/manual/nix-flakes/standalone.md), [prerequisites](https://github.com/nix-community/home-manager/blob/master/docs/manual/nix-flakes/prerequisites.md)). The CLI's `--flake` takes a flake URI; whether a remote `github:` ref with a pinned rev works end to end is **Unverified**.
- `home.username` and `home.homeDirectory` have no default for current state versions ([home-environment.nix](https://github.com/nix-community/home-manager/blob/master/modules/home-environment.nix)). One shared config for unknown user names needs either impure evaluation (`builtins.getEnv`) or an override at call time. Not verified in a running setup.
- `home-manager uninstall` exists ([script](https://github.com/nix-community/home-manager/blob/master/home-manager/home-manager)). It asks "Really uninstall?" and reads one character (`read -n 1`); I found no non-interactive flag. It then switches to a generated empty configuration with `uninstall = true`. That option forces no packages and no files, removes `home-manager-path` from the user profile, deletes `~/.local/share/home-manager`, `~/.local/state/home-manager` (which holds the gcroots), and the `home-manager*` profile links under `~/.local/state/nix/profiles/`, and deletes all history generations ([uninstall.nix](https://github.com/nix-community/home-manager/blob/master/modules/misc/uninstall.nix)). The empty switch also removes the symlinks the previous generation created (orphan cleanup in [files.nix](https://github.com/nix-community/home-manager/blob/master/modules/files.nix)). The `HOME_MANAGER_CONFIG` variable set by `uninstall` stops the CLI from auto-detecting `~/.config/home-manager/flake.nix` ([script](https://github.com/nix-community/home-manager/blob/master/home-manager/home-manager)). The docs say your `home.nix` is left untouched.
- Existing files: activation fails rather than overwrite a non-managed file; `-b EXT` (or `home-manager.backupFileExtension`) moves the old file to `<name>.EXT` instead ([files.nix](https://github.com/nix-community/home-manager/blob/master/modules/files.nix)). Nothing in uninstall restores those `.EXT` files, because orphan cleanup only removes links.
- Leftovers after uninstall: the default profile `~/.local/state/nix/profiles/profile*` (or `~/.nix-profile`) and its generations, `~/.cache/nix`, store paths until garbage-collected, any `.EXT` backups. The `switch` and `uninstall` paths first run `nix-build --expr '{}'` and `nix-env -q` ("sanity checking Nix", in `setHomeManagerPathVariables`); by my reading of Nix's `getDefaultProfile` that is enough to create the default profile link, but I did not run it ([script](https://github.com/nix-community/home-manager/blob/master/home-manager/home-manager), [profiles.cc](https://github.com/NixOS/nix/blob/master/src/libstore/profiles.cc)). HM installs a `home-manager-path` package into that default user profile with `nix profile install` or `nix-env -i`, whichever the existing profile uses ([home-environment.nix](https://github.com/nix-community/home-manager/blob/master/modules/home-environment.nix)).
- Which files HM writes depends on the modules: `programs.git` writes `$XDG_CONFIG_HOME/git/config`, which Git reads alongside `~/.gitconfig`, so both apply and `~/.gitconfig` wins ([git-config](https://git-scm.com/docs/git-config)); `programs.zsh` writes `~/.zshenv` and `.zshrc` ([zsh module](https://github.com/nix-community/home-manager/blob/master/modules/programs/zsh/default.nix)), which will collide with an existing work `~/.zshrc`.

**3b. `nix profile` with a `buildEnv`, plus linked config**
- Upstream Nix renamed `nix profile install` to `nix profile add` in 2.30 and kept `install` as a deprecated alias ([rl-2.30](https://github.com/NixOS/nix/blob/master/doc/manual/source/release-notes/rl-2.30.md), [profile.cc](https://github.com/NixOS/nix/blob/master/src/nix/profile.cc)). Lix 2.95.2 (observed locally) lists only `install`, `list`, `remove`, `rollback`, `upgrade`, `history`, `diff-closures`, `wipe-history`; no `add`. `remove` exists in both. A script supporting both must try `add`, fall back to `install`.
- `--profile <path>` selects a profile other than the default (Lix `--help`, observed; upstream [command.cc](https://github.com/NixOS/nix/blob/master/src/libcmd/command.cc), `MixProfile`). `nix profile remove '.*'` removes everything from a profile (Lix help example). `wipe-history` deletes older generations; deleting the profile symlink and `<profile>-N-link` files removes the rest.
- Once `nix profile` has touched the default profile, `nix-env` refuses to use it until `${XDG_STATE_HOME-$HOME/.local/state}/nix/profiles/profile` is deleted ([profile.md](https://github.com/NixOS/nix/blob/master/src/nix/profile.md)). Using the default profile on a machine whose owner uses `nix-env` therefore risks breaking their workflow.
- Default profile location: `~/.nix-profile` link into `$XDG_STATE_HOME/nix/profiles/profile` unless `use-xdg-base-directories` is set, then `$XDG_STATE_HOME/nix/profile` ([profiles.cc](https://github.com/NixOS/nix/blob/master/src/libstore/profiles.cc), [globals.hh](https://github.com/NixOS/nix/blob/master/src/libstore/include/nix/store/globals.hh)).
- Removing store content afterwards: upstream `nix store delete --recursive --skip-alive <installable>` ([store-delete.md](https://github.com/NixOS/nix/blob/master/src/nix/store-delete.md)); Lix names the flags `--delete-closure` and `--skip-live` (observed locally). Both only delete paths unreachable from GC roots. **Unknown:** whether an unprivileged user may run these against a multi-user daemon.

**3c. Wrapped programs (config from the store, nothing under `~/.config`)**

| Tool | Redirect | State it still writes |

**3d. Analysis (mine, not sourced)**

| | HM standalone | `nix profile` + linked files | Wrapped programs, one dedicated profile |
|---|---|---|---|
| Traces in `$HOME` | Most: managed symlinks across `~/.config`, `~/.local/state/home-manager`, profile links, default-profile entry | Medium: links the script makes, plus a profile | Fewest, if state dirs are redirected into one kit directory; otherwise the tools' own state spreads (history, elpa, allow list) |
| Collision risk with a work user's existing dotfiles | High for `~/.zshrc`/`~/.zshenv` (HM refuses or, with `-b`, moves them), low for `git/config` (XDG file merges) | Low if links go only to unused paths | Lowest: nothing written, but wrapping `GIT_CONFIG_GLOBAL` or `JJ_CONFIG` hides the work user's own config unless the wrapper chains to it |
| Removal | One built-in command, plus manual restore of `-b` backups and profile cleanup | Script must undo every link; `nix profile remove` for the env | `rm -rf` kit dir plus profile removal; no files to restore |
| Maintenance | Lowest: HM modules track tool changes | Medium: hand-maintained paths | Highest: each tool's env var or flag must be tracked (e.g. delta not following `GIT_CONFIG_GLOBAL`, Nushell history living in the config home) |
| Reuse of the personal setup | Highest: the same `programs.*` modules can be shared; `configs/` raw files are linked via `xdg.configFile` | Medium: reuse `configs/` files | Lower: wrapper libraries have their own module options, not HM's; raw files in `configs/` and attrsets like the jj settings can be reused as data |

**Implications for this repo:** The personal `modules/home.nix` already holds the content (jj settings attrset, nushell `extraEnv`/`extraConfig`, starship/bat/emacs files under `configs/`), so a second Home Manager entry point (`homeConfigurations.work`) built from a trimmed module list reuses the most. Its danger on a work machine is Home Manager owning shell rc files and the default profile; the work module list must leave out `programs.zsh` (it writes `~/.zshenv`/`.zshrc`) and anything that writes outside XDG paths, and must not set `backupFileExtension`, so a collision aborts instead of silently relocating a work file that the removal script would never restore. The personal config also carries identity and signing data (jj `user.name`, `user.email`, `signing.key`, git signing) that must not travel; jj's `JJ_USER`/`JJ_EMAIL` environment variables allow identity to come from the machine. The wrapper route gives the cleanest removal but needs three extra decisions: relocating Nushell/Emacs/direnv state under one kit directory, chaining `JJ_CONFIG` as `<store file>:<existing user config>` (the doc allows several paths), and handling delta (flag-based wrapper or `XDG_CONFIG_HOME`, since `GIT_CONFIG_GLOBAL` is, by source reading, not seen by libgit2). Recommended shape, as my own judgement: Lix installer; tools shipped as a `buildEnv`/flake package installed into a dedicated `--profile` (never the default one); config delivered through wrappers where a clean env var exists (jj, git, starship, nushell, bat, direnv, emacs) and with state redirected into one kit directory. That keeps the whole footprint to `/nix`, one profile directory and one kit directory. Fall back to Home Manager only if the wrapper maintenance proves too costly; HM's uninstall then needs the extra cleanup listed above. Any library choice should be lassulus/wrappers or nix-wrapper-modules (both active) over wrapper-manager (mid-migration to Codeberg); but plain `symlinkJoin`/`wrapProgram` avoids the dependency altogether. The Emacs light config uses `use-package-always-ensure` against MELPA/GNU ELPA, so first launch downloads packages into `elpa/` and needs network access; a work kit must either pre-build packages in Nix (`emacsWithPackages`) or accept that state and its proxy needs.

### 5. Bash script constraints

- macOS `/bin/bash` is 3.2.57 and has no `declare -A` (observed locally on macOS 26.5.2: `declare: -A: invalid option`), and `/bin/sh` reports itself as bash 3.2.57 (observed). The user login shell is `/bin/zsh` (observed via `dscl`). Apple's page confirms zsh is the default for new accounts since macOS 10.15 but does not state the bash version ([Apple](https://support.apple.com/en-us/102360)).
- The scripts that ship with the tools are plain `#!/bin/sh`: the official first stage and installer, and Lix's bootstrap (which relies on the common `local` extension and handles zsh) ([Nix install script](https://releases.nixos.org/nix/nix-2.35.2/install), [lix-installer.sh](https://git.lix.systems/lix-project/lix-installer/src/branch/main/lix-installer.sh)).
- No git needed to bootstrap: `github:` flake references are downloaded as tarballs "rather than through Git" ([flake.md](https://github.com/NixOS/nix/blob/master/src/nix/flake.md)). Upstream resolves a branch or tag through `https://api.github.com/repos/<owner>/<repo>/commits/<ref>` and downloads `https://github.com/<owner>/<repo>/archive/<rev>.tar.gz` when no token is configured; with a `rev` in the reference the API call is skipped ([github.cc](https://github.com/NixOS/nix/blob/master/src/libfetchers/github.cc)). Lix `main` does the same ([github.cc](https://git.lix.systems/lix-project/lix/src/branch/main/lix/libfetchers/github.cc)). Unauthenticated GitHub API calls are limited to 60 per hour per IP ([GitHub docs](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)); I hit this limit from this machine's IP while researching, which a shared corporate NAT would reproduce. Nix's `access-tokens` setting exists ([fetch-settings.hh](https://github.com/NixOS/nix/blob/master/src/libfetchers/include/nix/fetchers/fetch-settings.hh)), but the kit must not carry a personal token.
- A local directory flake is treated as a `git+file` input when it sits in a Git repository, otherwise as `path:` ([flake.md](https://github.com/NixOS/nix/blob/master/src/nix/flake.md)); a downloaded tarball directory has no `.git`. jj needs the `git` binary for remote operations ([git-compatibility.md](https://github.com/jj-vcs/jj/blob/v0.45.1/docs/git-compatibility.md)) so Git belongs in the kit's tool set.
- `curl | sh`: the nixos.org first stage wraps itself in braces so a truncated download cannot execute, and verifies the tarball's SHA-256 against a hash embedded in the script ([script](https://releases.nixos.org/nix/nix-2.35.2/install)). The Lix bootstrap downloads `lix-installer-<arch>` from `install.lix.systems` into a temp directory, marks it executable and runs it (it errors out if the directory is `noexec`); I found no checksum verification in it (TLS only). When piped and without `--no-confirm` it reconnects the installer's stdin to `/dev/tty`, and refuses to proceed if there is no terminal ([lix-installer.sh](https://git.lix.systems/lix-project/lix-installer/src/branch/main/lix-installer.sh)). Installers escalate through `sudo` themselves (Lix: `sudo --set-home`, official: `NIX_BECOME`).
- `curl`/`wget` and `tar` (plus `xz` on Linux) must exist for the official script; the Lix bootstrap needs `uname`, `mktemp`, `chmod`, `mkdir`, `rm`, `rmdir` and a downloader.
- **Unverified:** that `/usr/bin/git` on a macOS without Command Line Tools triggers an install prompt (common knowledge, no primary source read).

**Implications for this repo:** Write the script in POSIX `sh` (or bash 3.2 syntax: no associative arrays, no `mapfile`, no `${var,,}`), start it with `#!/bin/sh`, and test it under `/bin/bash` 3.2, `dash` and `zsh --emulate sh`. Prefer download-then-run over `curl | sh` for the kit's own script so that it can be read, hashed and pinned; the pinned `rev` must be a full commit hash so the kit's flake and its `flake.lock` inputs are fetched as `archive/<rev>.tar.gz` without the rate-limited API. Download the Lix installer by version tag, verify a SHA-256 the script carries (Lix gives none), and run it with `--no-confirm`. Keep Git in the tool set for jj but do not depend on it before Nix is up. The script must source `nix-daemon.sh` itself right after installing, since the rc hooks only reach new interactive shells.
