## The streaming box's USB display adapter

Research date: 2026-10-12. Everything below was read on that day from the linked sources (GitHub/GitLab "master"/"main" links drift). Conventions: **Unverified:** means a claim I could not confirm from a primary source (or only from a forum). **Unknown:** means I looked and found nothing.

How the NixOS facts were checked: besides reading nixpkgs source, I ran `nix eval` (evaluation only, no builds) against the nixpkgs revision this repo pins, `b6c98e9e6633ee64753b594ff4a5febf0367fc00` (nixpkgs-unstable, 2026-09-22, see `flake.lock`). Nothing was run on real hardware, so "evaluates" never means "works".

Two access limits to know about. (1) gitlab.freedesktop.org and wiki.archlinux.org put an Anubis bot challenge in front of their web pages; I did not try to get past it. I read wlroots through a git clone and the public GitLab issue-list API instead, which means the **comment threads** of wlroots issues are unread (the wlroots issue #1823 thread I read is the GitHub-era part, see Q3). (2) I did not download the Synaptics driver zip (a download needs the user's consent), so I could not check it against the nixpkgs hash; I only sent HEAD requests.

### 1. Chipset families, Linux drivers, and how to tell them apart

**Findings**

| Family | USB vendor ID | Linux driver | Notes |
|---|---|---|---|
| DisplayLink, USB 2.0 generation (DL-1x5, DL-1x0) | `17e9` | In-kernel DRM driver `udl` | Synaptics' own release notes say these devices use the open `udl` driver, not their package ([6.4 release notes](https://www.synaptics.com/sites/default/files/release_notes/2026-10/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.4-Release%20Notes.txt), section G). |
| DisplayLink, USB 3.0 generation and later (DL-3xxx, DL-41xx, DL-5xxx, DL-6xxx, DL-7xxx) | `17e9` | Out-of-tree `evdi` kernel module (GPL, open) plus the proprietary `DisplayLinkManager` daemon (runs as root) | Same release notes, sections E, G, I. "USB 3.0 to HDMI" generic adapters are usually here. |
| Silicon Motion SM768 "SMI USB Display" | `090c` | Vendor-only: a `.run` installer that builds `evdi` via DKMS plus a vendor daemon | Ubuntu 20.04+, x86 only, HDMI audio claimed ([SMI manual, May 2024](https://www.siliconmotion.com/downloads/video/SiliconMotion%20USB%20Graphics%20Software%20for%20Ubuntu%20User%20Manual.pdf)). |
| Fresco Logic FL2000 / FL2000DX | `1d5c` (product `2000`) | No mainline driver. An old vendor kernel driver (README says tested on kernel 3.10, no desktop integration) and a community DRM driver `fl2000_drm` | USB 3.0 only; the community driver lists HDMI audio and USB 2.0 as unimplemented ([vendor README](https://github.com/FrescoLogic/FL2000), [fl2000_drm wiki](https://github.com/klogg/fl2000_drm/wiki/01.-Home)). |
| Magic Control Technology (MCT) "Trigger" | `0711` | Vendor-only Ubuntu `.run` driver | One 2026 forum report: product `0711:5601` (Trigger VI T6), driver lacks HDMI audio on Linux ([Mint forum](https://forums.linuxmint.com/viewtopic.php?t=467345), forum pointer only). Old VGA-only MCT dongles are also in [usb.ids](http://www.linux-usb.org/usb.ids). |

- **Vendor IDs verified** against usb.ids (version 2026.06.26) ([usb.ids](http://www.linux-usb.org/usb.ids)): `17e9` DisplayLink, `090c` Silicon Motion, Inc. - Taiwan, `1d5c` Fresco Logic (`1d5c:2000` FL2000/FL2000DX VGA/DVI/HDMI Adapter), `0711` Magic Control Technology Corp. usb.ids has no SM768 product entry under `090c`; a forum post (not fetched, HTTP 403) is said to show `090c:0768` ("SMI USB Display"), so treat that product ID as Unverified.
- **udl vs evdi can be told apart from the interface descriptor, not reliably from bcdUSB.** The kernel `udl` driver binds to vendor `17e9`, interface class `0xff`, subclass `0x00`, protocol `0x00`, and its source comment says this is the pattern of "all known USB 2.0 era graphics chips", leaving higher protocol numbers for future incompatible chips ([udl_drv.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/udl/udl_drv.c)). The nixpkgs udev rule that starts the DisplayLink daemon matches vendor `17e9`, class `ff`, **protocol `03`** ([99-displaylink.rules](https://github.com/NixOS/nixpkgs/blob/master/pkgs/os-specific/linux/displaylink/99-displaylink.rules)). So: protocol 0 means `udl`; protocol 3 means the evdi plus daemon stack. (Analysis: bcdUSB is a poor discriminator because USB 3.0 chips fall back to a 2.x descriptor on a USB 2.0 port.)
- **udl limits.** Max mode 2048x2048 and a per-device pixel cap (default 2,080,000 pixels, enough for 1920x1080) read from the device's vendor descriptor ([udl_modeset.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/udl/udl_modeset.c), [udl_main.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/udl/udl_main.c)). `udl` is video-only; it registers with `DRIVER_MODESET | DRIVER_GEM | DRIVER_ATOMIC` and no render capability ([udl_drv.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/udl/udl_drv.c)). `evdi` likewise has no `DRIVER_RENDER` ([evdi_drm_drv.c](https://github.com/DisplayLink/evdi/blob/main/module/evdi_drm_drv.c)); the evdi README calls itself "not a complete driver" without the userspace daemon ([evdi README](https://github.com/DisplayLink/evdi/blob/main/README.md)).
- **DisplayLink current versions.** Synaptics' Ubuntu page lists driver 6.4 (2026-09-24) as latest and 6.3 as legacy ([download page](https://www.synaptics.com/products/displaylink-graphics/downloads/ubuntu)). 6.4 bundles evdi 1.15.1 and states a supported kernel range of 4.15 to 7.3.0-rc3 ([6.4 notes](https://www.synaptics.com/sites/default/files/release_notes/2026-10/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.4-Release%20Notes.txt)). 6.3 bundles evdi 1.14.14-5 ([6.3 notes](https://www.synaptics.com/sites/default/files/release_notes/2026-06/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.3-Release%20Notes.txt)). The 6.2 notes say the daemon is compatible with community evdi 1.12.0 and newer ([6.2 notes](https://www.synaptics.com/sites/default/files/release_notes/2025-09/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.2-Release%20Notes.txt)).
- **Other chipsets:** Unknown. I found no other USB-A-to-HDMI display chipset family with a Linux story in primary sources. (A USB-C adapter using DisplayPort Alt Mode would be a different thing and needs no driver, but the question says USB-A.)

**Implications for this repo:** Which branch applies is decided entirely by one `lsusb` read on the box (commands in Open questions). Branch A (`udl`) needs nothing but the kernel module. Branch B (DisplayLink 3.0 generation) needs the unfree driver, the manual prefetch and the evdi module (Q2). Branches SMI, FL2000 and MCT have no nixpkgs package (Q2); I would treat them as "buy a different adapter" unless Renaud insists. Inference worth testing: since the adapter reportedly worked on antiX with only Intel graphics and then also after hand-installed NVIDIA drivers, and since DisplayLink documents the closed NVIDIA driver as incompatible with its daemon (Q4), the adapter may be a `udl`-class device or the daemon may be involved in a way Renaud does not remember. Only the `lsusb -t` driver column and `lsmod` settle it.

### 2. NixOS support: modules, packages, the manual download

**Findings**

- **Module.** `services.xserver.videoDrivers = [ "displaylink" ]` (the NixOS wiki adds `"modesetting"`) switches on `nixos/modules/hardware/video/displaylink.nix`, which: adds `evdi` to `boot.extraModulePackages` and `boot.kernelModules`, installs the package's udev rule, writes an X11 `OutputClass` file and an `xrandr --setprovideroutputsource 1 0` session command (X-only), defines `systemd.services.dlm` (runs `DisplayLinkManager`, `After=display-manager.service`, `Conflicts=getty@tty7`, no `wantedBy`), and adds suspend/resume hooks ([module](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/hardware/video/displaylink.nix)). `dlm.service` is started by udev (`SYSTEMD_WANTS`) when a protocol-3 `17e9` device appears, not at boot unconditionally ([udev rule](https://github.com/NixOS/nixpkgs/blob/master/pkgs/os-specific/linux/displaylink/99-displaylink.rules), unchanged since 2020 per [its history](https://github.com/NixOS/nixpkgs/commits/master/pkgs/os-specific/linux/displaylink/99-displaylink.rules)).
- **Package still needs a manual download.** `pkgs.displaylink` uses `requireFile` with a fixed hash and `license = unfree`, `hydraPlatforms = []` (never in the binary cache) ([package, master](https://github.com/NixOS/nixpkgs/blob/master/pkgs/os-specific/linux/displaylink/default.nix)).
  - **At the repo's pinned nixpkgs (2026-09-22): version 6.2.0-30**, file name `displaylink-620.zip`, instructions: download from the Synaptics 6.2 page, rename, `nix-prefetch-url file://$PWD/displaylink-620.zip`, or fetch directly with `nix-prefetch-url --name displaylink-620.zip 'https://www.synaptics.com/sites/default/files/exe_files/2025-09/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.2-EXE.zip'` ([package at pinned rev](https://github.com/NixOS/nixpkgs/blob/b6c98e9e6633ee64753b594ff4a5febf0367fc00/pkgs/os-specific/linux/displaylink/default.nix)).
  - **On master today: 6.3.0-48** (bumped 2026-09-26, [PR #567247](https://github.com/NixOS/nixpkgs/pull/567247)), file name `displaylink-630.zip`, direct URL `https://www.synaptics.com/sites/default/files/exe_files/2026-06/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.3-EXE.zip`. So the next `flake.lock` bump will change the required file and break the build until the new zip is prefetched.
  - Both URLs answered HTTP 200 (19.8 MB zips) on 2026-10-12 ([6.2 URL](https://www.synaptics.com/sites/default/files/exe_files/2025-09/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.2-EXE.zip), [6.3 URL](https://www.synaptics.com/sites/default/files/exe_files/2026-06/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.3-EXE.zip)). The 6.2 file's `Last-Modified` header is 2026-02-12, later than the nixpkgs 6.2 bump (2025-10-02). Whether the bytes still match the nixpkgs hash: Unknown (not downloaded).
  - The package keeps a pin so the zip is not garbage-collected once used ("workspace_dependencies.pin" in the install phase, same file).
  - The NixOS wiki gives the same procedure ([wiki](https://wiki.nixos.org/wiki/Displaylink)).
- **Where the file must live:** `nix-prefetch-url` adds it to the store of the machine it runs on, so it has to be on whichever machine builds the closure (Framework when using `--target-host`, or the box when building there). Because the derivation is unfree and uncached, it is never substituted. (Analysis from how fixed-output derivations and `requireFile` work; not tested.)
- **evdi.** `config.boot.kernelPackages.evdi` is evdi 1.15.1 at the pinned rev, and `cache.nixos.org` has the build for the default kernel 6.18.53 (narinfo returned 200), so no local compile ([evdi package](https://github.com/NixOS/nixpkgs/blob/master/pkgs/os-specific/linux/evdi/default.nix)). Open nixpkgs issues: [#418072](https://github.com/NixOS/nixpkgs/issues/418072) (build failure on kernel 6.15, old), [#299141](https://github.com/NixOS/nixpkgs/issues/299141) (gnome-shell cannot load evdi, GNOME only).
- **Works without X11 (evaluation check).** I evaluated a config with `services.cage.enable = true`, `services.xserver.videoDrivers = [ "displaylink" ]` and no X server: `services.xserver.enable` is false, there are zero failing assertions and zero warnings, `evdi` is in `boot.extraModulePackages` and `boot.kernelModules`, the `displaylink-6.2.0-30` package is in `services.udev.packages`, and `dlm.service` exists with `After=display-manager.service` (a unit that does not exist under Cage, which is harmless) and empty `wantedBy`. The X11 file `/etc/X11/xorg.conf.d/40-displaylink.conf` is still written but unused. The NixOS wiki states that the module "should also work for wlroots compositors" and gives a Wayland section ([wiki](https://wiki.nixos.org/wiki/Displaylink), last edit 2026-04-15 per its [history](https://wiki.nixos.org/w/index.php?title=Displaylink&action=history)).
- **Wiki advice that is stale or inconsistent:** it tells sway users to add `systemd.services.dlm.wantedBy = [ "multi-user.target" ]` "only for NixOS 25.05 and earlier", but the module and udev rule are identical in [release-25.05](https://github.com/NixOS/nixpkgs/blob/release-25.05/nixos/modules/hardware/video/displaylink.nix); and it mentions a `displaylink-server` unit that nixpkgs does not define (the KDE example defines its own). Treat the wiki as a pointer.
- **Known NixOS-side wrinkles:** `dlm` ignores SIGTERM and stalls shutdown for the 90 s default stop timeout (open [PR #553315](https://github.com/NixOS/nixpkgs/pull/553315) proposes `TimeoutStopSec = 5`); the suspend hook can hang when no display is attached ([issue #281104](https://github.com/NixOS/nixpkgs/issues/281104), open); in February 2026 the `videoDrivers` assertion broke the option and was fixed by adding `displaylink` to `externallyConfiguredDrivers` ([issue #491861](https://github.com/NixOS/nixpkgs/issues/491861), [PR #491981](https://github.com/NixOS/nixpkgs/pull/491981)).
- **SiliconMotion in nixpkgs: nothing for USB.** `xf86-video-siliconmotion` is the old X driver for the PCI SM50x chips; `macos-instantview` is the macOS app; I found no package or module for the Linux `SMIUSBDisplay` installer, for `fl2000_drm`, or for MCT drivers (GitHub code search on nixpkgs for those names returned nothing relevant). `udl` is in the kernel; nixpkgs builds kernels with `autoModules = true` ([generic.nix](https://github.com/NixOS/nixpkgs/blob/master/pkgs/os-specific/linux/kernel/generic.nix)), so `CONFIG_DRM_UDL` is very likely a module. Unverified: I could not read the final `.config`; run `modinfo udl` on a NixOS boot to confirm.

**Implications for this repo:**
- A DisplayLink-family adapter is supportable, but the config carries an unfree, hand-fetched input: it needs `nixpkgs.config.allowUnfreePredicate` naming `displaylink`, and a documented one-time `nix-prefetch-url` step on the builder (and a repeat every time nixpkgs bumps the package). A `flake: update inputs` commit can fail the box's build for this reason alone. Options: pin `displaylink` to a fixed version via an overlay so lock bumps do not move it, or keep the zip in a private substituter. Both are Renaud's call.
- Wayland-only is fine at evaluation level. The sketch below evaluated cleanly against the pinned nixpkgs (assertions: none failing). It is not a tested config.

```nix
nixpkgs.config.allowUnfreePredicate = pkg: builtins.elem (lib.getName pkg) [ "displaylink" ];
services.xserver.videoDrivers = [ "displaylink" ];     # only switches the module on; no X server runs
systemd.services.dlm.wantedBy = [ "multi-user.target" ]; # optional: start the daemon at boot, not only on udev add
systemd.services.dlm.serviceConfig.TimeoutStopSec = 5;   # avoids the 90 s stop stall (PR 553315)
```

### 3. Wayland, wlroots and Cage with these adapters

**Findings**

- **DisplayLink's own position:** the only Wayland compositor they name is Mutter (minimum 3.32); the Ubuntu known-issues page says Wayland is supported since driver 3.32 and Ubuntu 20.04 ([6.4 notes](https://www.synaptics.com/sites/default/files/release_notes/2026-10/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.4-Release%20Notes.txt), section D; [known issues](https://support.displaylink.com/knowledgebase/articles/641668)). wlroots compositors are not mentioned anywhere on the vendor side.
- **History: wlroots could not do it for years.** The DisplayLink feature request is [wlroots #1823](https://gitlab.freedesktop.org/wlroots/wlroots/-/issues/1823) (opened 2019-09-15, closed 2024-11-08). The early GitHub-era comments ([mirror](https://github.com/swaywm/wlroots/issues/1823)) say the missing piece was supporting display-only devices without rendering, that a contributor's hack (skip the cross-GPU copy and scan out the primary GPU's buffers directly) lit a DisplayLink dock under sway, and that a maintainer called evdi mainly a vehicle for a proprietary driver, so special support did not belong in wlroots.
- **The fix is upstream since wlroots 0.19.0 (2024-11).** Commit `0108506c` "backend/drm: Allow proceeding with render-less mgpu" (Kenny Levinsen, 2024-11-07): when a secondary DRM device has no usable renderer, wlroots continues and scans out the primary GPU's buffers directly (implicit modifiers are stripped); the commit message says this helps GUD and DisplayLink ([commit](https://gitlab.freedesktop.org/wlroots/wlroots/-/commit/0108506c770753604d6b77d24d1aa7f68feb7a23); contained in tags 0.19.0 and later). The same author wrote on 2024-11-08, in the sway issue that tracked the earlier breakage, that DisplayLink "should now work with wlroots master" ([sway #8105](https://github.com/swaywm/sway/issues/8105)). I read the code path in wlroots 0.20.2 (`init_mgpu_renderer`, log line "falling back to scanning out from primary GPU") ([backend.c](https://gitlab.freedesktop.org/wlroots/wlroots/-/blob/0.20.2/backend/drm/backend.c)). nixpkgs' Cage 0.3.1 is built against `wlroots_0_20` (version 0.20.2 in nixpkgs master) ([cage package](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/ca/cage/package.nix), [Cage meson.build v0.3.1](https://github.com/cage-kiosk/cage/blob/v0.3.1/meson.build)), so the fix is included.
- **`WLR_EVDI_RENDER_DEVICE` is not a wlroots variable.** It appears only in the NixOS wiki's sway recipe, paired with an out-of-tree wlroots patch (`DisplayLink_v2.patch`, "wlroots 0.17 or 0.18") ([wiki](https://wiki.nixos.org/wiki/Displaylink)). It is absent from [env_vars.md](https://gitlab.freedesktop.org/wlroots/wlroots/-/blob/0.20.2/docs/env_vars.md), and a search of wlroots master and Cage master for "evdi" finds nothing. Unverified: whether that old patch still applies; it should be unnecessary on 0.19+. (The wiki's `--unsupported-gpu` flag is a sway option and has no Cage equivalent.)
- **The env vars that do exist** ([env_vars.md](https://gitlab.freedesktop.org/wlroots/wlroots/-/blob/0.20.2/docs/env_vars.md)):
  - `WLR_DRM_DEVICES`: explicit colon-separated list, first existing entry is primary; when it is set, wlroots **does not watch for hot-plugged cards** (`drm_backend_monitor_create` is only called when it is unset, [backend.c line 271](https://gitlab.freedesktop.org/wlroots/wlroots/-/blob/0.20.2/backend/backend.c)), and missing entries are skipped with an error ([session.c](https://gitlab.freedesktop.org/wlroots/wlroots/-/blob/0.20.2/backend/session/session.c)).
  - `WLR_RENDER_DRM_DEVICE`: must be a render node (`renderD*`), picks the GPU used for rendering ([wlr_renderer.c](https://gitlab.freedesktop.org/wlroots/wlroots/-/blob/0.20.2/render/wlr_renderer.c)).
  - `WLR_DRM_NO_MODIFIERS=1` (always allocate planes without modifiers; helps certain modeset failures) and `WLR_SCENE_DISABLE_DIRECT_SCANOUT=1`.
- **Primary GPU selection without the variables:** the card with `boot_display=1` or whose PCI parent has `boot_vga=1` is first; every other KMS card becomes a secondary backend with a hotplug monitor for cards that appear later ([session.c](https://gitlab.freedesktop.org/wlroots/wlroots/-/blob/0.20.2/backend/session/session.c), [monitor.c](https://gitlab.freedesktop.org/wlroots/wlroots/-/blob/0.20.2/backend/drm/monitor.c)). So an evdi or udl card that shows up after Cage started (because the daemon starts late) is picked up.
- **Known breakages and risks, evdi side:**
  - Arch forum, Sept to Oct 2025: sway 1.11 (wlroots 0.19) on a ThinkPad with Intel graphics and a DisplayLink dock crashed at startup (EGL `eglQueryDevicesEXT` failure while creating the multi-GPU renderer on the render-less evdi card); X11 and Hyprland worked; on 2025-10-11 the poster reported it working after unspecified package updates ([thread, forum pointer](https://bbs.archlinux.org/viewtopic.php?id=308317)). Unknown: which change fixed it, and whether it is in 0.20.2.
  - [evdi #540](https://github.com/DisplayLink/evdi/issues/540) (2025-11): a Wayland greeter followed by the user compositor left the DisplayLink screen showing noise; reloading the evdi module while no graphical session is active fixed it, restarting the daemon did not. Relevant if Cage ever restarts on the box.
  - [evdi #484](https://github.com/DisplayLink/evdi/issues/484): blank DisplayLink screens on Wayland with the proprietary NVIDIA driver (GNOME, KDE, Hyprland); reporter says it works with AMD or Intel iGPUs.
  - [sway #8105](https://github.com/swaywm/sway/issues/8105) (2024): one tester saw high CPU in `DisplayLinkManager` when a maximized window used direct scan-out onto the DisplayLink output; the hack he tested avoided direct scan-out. Unknown whether current wlroots does this; `WLR_SCENE_DISABLE_DIRECT_SCANOUT=1` is the documented switch if it shows up. A Crunchyroll kiosk is exactly a maximized, constantly changing window.
  - [evdi module README](https://github.com/DisplayLink/evdi/blob/main/module/README.md) says distro installers set `initial_device_count=` (a workaround for X servers that build static GPU lists at startup) and a `softdep` so evdi loads after the primary GPU driver (so a compositor will not take evdi as the primary GPU). nixpkgs' module does neither.
- **udl and wlroots:** `udl` has no render node and registers only a primary plane (no cursor plane) ([udl_modeset.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/udl/udl_modeset.c)), so it should go through the same render-less secondary path as evdi (analysis from the driver features above). I found no report of `udl` under Cage or sway. The wlroots issue titled "Support devices without hardware cursors" ([#1584](https://gitlab.freedesktop.org/wlroots/wlroots/-/issues/1584), closed; thread unread, so I do not know which device it concerned) suggests that case is handled. Unverified end to end.
- **SiliconMotion SM768, FL2000, MCT:** the SMI stack uses evdi, so the render-less path would apply (inference); no report with wlroots found. FL2000's community driver is an ordinary DRM driver by design (its wiki cites `udl` as a model), no compositor reports found. Unknown for all three.
- **Cage-specific:** no Cage issue mentions DisplayLink, evdi or udl (GitHub issue search on `cage-kiosk/cage` returned nothing). Cage creates one renderer and one allocator from the multi backend (`wlr_renderer_autocreate`, `wlr_allocator_autocreate` in [cage.c v0.3.1](https://github.com/cage-kiosk/cage/blob/v0.3.1/cage.c); the multi backend hands out the first DRM fd, which is the primary GPU, [multi/backend.c](https://gitlab.freedesktop.org/wlroots/wlroots/-/blob/0.20.2/backend/multi/backend.c)) and calls `wlr_output_init_render` for every new output, so secondary-GPU outputs follow the wlroots path above ([output.c at v0.3.1](https://github.com/cage-kiosk/cage/blob/v0.3.1/output.c)). Cage issues about multi-GPU: [#411](https://github.com/cage-kiosk/cage/issues/411) (two NVIDIA GPUs, `-m last`, black screen with a "failed to import source buffer into multi-gpu renderer" loop, Cage 0.1.5/0.2.0), [#440](https://github.com/cage-kiosk/cage/issues/440) (two virtio cards; maintainer: `-m` does not choose GPUs, use `WLR_DRM_DEVICES`).

**Implications for this repo:** On paper, DisplayLink-class adapters (evdi) and `udl` adapters can be driven by Cage 0.3.1 on wlroots 0.20.2 with the Intel iGPU as primary. The evidence is a 2024 upstream design fix plus one late-2025 field report on a different compositor, no direct report for Cage; call it "plausible, untested". Concrete consequences: (a) do not set `WLR_DRM_DEVICES` unless the adapter is already enumerated when Cage starts, because it disables hotplug (see Q4 for the trade); (b) keep `WLR_RENDER_DRM_DEVICE` as a lever; (c) plan the first boot with the real adapter as a test, with the X11 fallback of Q7 ready; (d) if Cage restarts, expect evdi #540-style corruption and consider restarting `dlm` or reloading evdi as a recovery action.

### 4. Which GPU renders, and what to do with the old NVIDIA

**Findings**

- **The USB display is its own DRM device, not part of either PCI GPU.** In the wlroots design the compositor renders on the primary GPU's renderer; the USB device only receives the finished frames (Q3). evdi shows up in X as a "Sink Output" provider, a PRIME-style output sink that needs a source provider, not an NVIDIA-specific mechanism ([evdi module README](https://github.com/DisplayLink/evdi/blob/main/module/README.md)). So NVIDIA Optimus handling (PRIME offload/sync) is not part of the USB path; Optimus matters only as: which of the two PCI GPUs is the primary/render device, and what happens to the other.
- **The NVIDIA legacy branches cannot do the Wayland job.** GBM support arrived in the 495 branch: the 495.29.05 README has a chapter "GBM and GBM-based Wayland Compositors" ([495.29.05 gbm.html](https://download.nvidia.com/XFree86/Linux-x86_64/495.29.05/README/gbm.html)); the same URL for 470.256.02 returns 404 ([470.256.02 gbm.html](https://download.nvidia.com/XFree86/Linux-x86_64/470.256.02/README/gbm.html)). Mapping of old GPUs to branches: 470.xx for Kepler, 390.xx for Fermi, 340.xx for the G8x/G9x/GT200 generation ([NVIDIA legacy page](https://www.nvidia.com/en-us/drivers/unix/legacy-gpu/); nixpkgs comment "last one supporting Kepler" for 470, [nvidia-x11/default.nix](https://github.com/NixOS/nixpkgs/blob/master/pkgs/os-specific/linux/nvidia-x11/default.nix)). 
- **nixpkgs state of the legacy drivers:** `legacy_470` (470.256.02) is patched through Linux 7.0; `legacy_390` is marked broken for kernel 6.18 and newer (the pinned nixpkgs' default kernel is 6.18.53); `legacy_340` is marked broken for kernel 6.7 and newer ([same file](https://github.com/NixOS/nixpkgs/blob/master/pkgs/os-specific/linux/nvidia-x11/default.nix)).
- **DisplayLink says the closed NVIDIA/AMD drivers are incompatible with its driver** and recommends the open ones ([known issues](https://support.displaylink.com/knowledgebase/articles/641668), Ubuntu page, possibly stale), and evdi #484 reports blank screens with proprietary NVIDIA on Wayland ([issue](https://github.com/DisplayLink/evdi/issues/484)). Cage #411 shows a multi-GPU black-screen failure involving two NVIDIA GPUs.
- **Leaving the NVIDIA unused:**
  - With no NVIDIA driver loaded, there is no DRM card for it; wlroots only sees the Intel card and the USB card. `boot.blacklistedKernelModules = [ "nouveau" ]` is the standard NixOS way; the evaluation check above accepted it.
  - If `nouveau` is left loaded, it registers its own DRM card, wlroots adds it as another secondary backend (and builds a multi-GPU renderer on it), and any connector wired to the NVIDIA GPU can become an extra Cage output. That is the case where pinning `WLR_DRM_DEVICES` helps, at the cost of hotplug (Q3).
  - Power: nouveau's runtime PM parameter defaults to "Optimus only" (`runpm` -1 in [nouveau_drm.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/nouveau/nouveau_drm.c)), so a loaded nouveau can power the dGPU down on Optimus hardware. With nouveau blacklisted and no other driver, the dGPU stays in whatever state firmware left it. How much heat or power that costs on this laptop: Unknown (needs measuring).
  - Mesa's GBM and EGL work on nouveau-supported old NVIDIA GPUs (expected from how Mesa works; Unverified for this card).
- **X11 side of the same question:** `modesetting` on the Intel GPU is what the module's X config uses (`MatchDriver evdi`, `Driver modesetting`, `AccelMethod none`) ([module](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/hardware/video/displaylink.nix)).

**Implications for this repo:** The Intel iGPU should render and be the primary; the NVIDIA GPU should be unused. Whether to blacklist `nouveau` (clean, hotplug works, dGPU power unknown) or leave it loaded and pin `WLR_DRM_DEVICES` (nouveau may power-save, hotplug lost) is the one real design choice here, and it depends on facts only the hardware gives (does a NVIDIA-wired port exist, how hot is the dGPU). My default: blacklist `nouveau`, leave `WLR_DRM_DEVICES` unset, and add `WLR_RENDER_DRM_DEVICE` pointing at the Intel render node by-path once its PCI address is known. Do not use `hardware.nvidia` at all, which also removes the legacy-driver build breakage. On the box today (antiX) the "NVIDIA drivers installed by hand" is a configuration that this plan deliberately does not reproduce; the claim that the adapter worked with Intel alone is the basis for the plan.

### 5. Audio

**Findings**

- **DisplayLink audio is a standard USB audio device.** Synaptics' notes say the stock distribution drivers handle DisplayLink's audio and Ethernet interfaces ([6.4 notes](https://www.synaptics.com/sites/default/files/release_notes/2026-10/DisplayLink%20USB%20Graphics%20Software%20for%20Ubuntu6.4-Release%20Notes.txt), section A) and the known-issues page says audio relies on the system drivers ([KB](https://support.displaylink.com/knowledgebase/articles/641668)). That is `snd-usb-audio` (USB Audio Class). Whether a given cheap HDMI adapter actually exposes the audio interface: Unknown, it is a property of the product, not of the chip family. The `udl` driver itself carries video only ([udl source](https://github.com/torvalds/linux/tree/master/drivers/gpu/drm/udl)).
- **Other families:** SMI states it supports HDMI audio output ([manual](https://www.siliconmotion.com/downloads/video/SiliconMotion%20USB%20Graphics%20Software%20for%20Ubuntu%20User%20Manual.pdf)); `fl2000_drm` lists HDMI audio as not implemented ([wiki](https://github.com/klogg/fl2000_drm/wiki/01.-Home)); the MCT report says no HDMI audio ([forum pointer](https://forums.linuxmint.com/viewtopic.php?t=467345)).
- **Device access under Cage:** systemd tags sound devices with `uaccess`, so the logged-in `kiosk` user (a logind session via Cage's PAM stack) gets access without group membership ([70-uaccess.rules.in](https://github.com/systemd/systemd/blob/main/rules.d/70-uaccess.rules.in)).
- **PipeWire in the Cage session:** at the pinned rev, `services.pipewire.enable = true` wires `pipewire.socket` and `pipewire-pulse.socket` to `sockets.target` and WirePlumber to `pipewire.service` as user units (checked by evaluation), so they start with the `kiosk` user's session; versions at the pin: PipeWire 1.6.8, WirePlumber 0.5.17.
- **WirePlumber picks USB audio first by default, but not deterministically across the board.** The ALSA monitor script adds 100 to the priority of nodes whose `device.bus` is `usb`, relative to analog (+9) and IEC958 (+8) bonuses, and PCI HDMI sinks on device numbers other than 0 start from 744 ([alsa.lua, 0.5.17](https://gitlab.freedesktop.org/pipewire/wireplumber/-/blob/0.5.17/src/scripts/monitors/alsa.lua)). So a USB sink normally outranks the internal analog sink (about 1100 against 1009) and the Intel HDMI sinks. The WirePlumber docs state that a saved `wpctl set-default` choice overrides priorities, and give the declarative example: a rule on `node.name = "~alsa_output.usb-.*"` setting `priority.session = 3000` ([priorities docs](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/priorities.html)).
- **NixOS option for it:** `services.pipewire.wireplumber.extraConfig`, an attrset of file name to config sections, written to `share/wireplumber/wireplumber.conf.d/<name>.conf` ([module](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/services/desktops/pipewire/wireplumber.nix)). This evaluated:

```nix
services.pipewire.wireplumber.extraConfig."51-usb-audio-default"."monitor.alsa.rules" = [
  {
    matches = [ { "node.name" = "~alsa_output.usb-.*"; } ];
    actions.update-props."priority.session" = 3000;
  }
];
```

**Implications for this repo:** If the adapter has an audio interface, no special PipeWire config is needed for it to appear; the rule above makes the choice deterministic and survives a changed ALSA card order. If it has none, audio needs another path (the laptop's own HDMI audio is not available through the USB display, and the 3.5 mm jack would be the obvious alternative). That is a hardware fact to read off `aplay -l` on antiX.

### 6. Cage on a laptop: which output, and the lid

**Findings**

- **Cage multi-output modes (verified in the v0.3.1 man page and source):** `-m extend` (the default, per the usage text in `cage.c` at v0.3.1) extends the display across all connected outputs; `-m last` uses only the last connected output ([man page v0.3.1](https://github.com/cage-kiosk/cage/blob/v0.3.1/cage.1.scd), [cage.c v0.3.1](https://github.com/cage-kiosk/cage/blob/v0.3.1/cage.c)). In extend mode the app is sized to the bounding box of the output layout, so a laptop panel plus an external display makes one window spanning both ([Cage wiki: Configuration](https://github.com/cage-kiosk/cage/wiki/Configuration)).
- **How `last` works:** each new output is inserted at the head of the list; if more than one exists, the previously newest one is disabled; when an output disappears, the previous one is re-enabled ([output.c at v0.3.1](https://github.com/cage-kiosk/cage/blob/v0.3.1/output.c)). So with the internal panel enumerated first and the USB output appearing later, the kiosk lands on the USB output, and falls back to the internal panel if the adapter drops. Unknown: the enumeration order when the adapter is already present at Cage start (the primary GPU's backend starts first in the code I read, so the internal panel most likely comes first; not tested).
- **Upstream is moving away from `-m`.** [Cage #466](https://github.com/cage-kiosk/cage/issues/466) (open) proposes dropping `-m` in favour of wlr-output-management tools (kanshi, wlr-randr); a maintainer repeated that on [PR #523](https://github.com/cage-kiosk/cage/pull/523) (a `-o <name>` flag, open); [#515](https://github.com/cage-kiosk/cage/issues/515) (open) is a segfault during teardown with `-m last` (a fix is proposed in [PR #525](https://github.com/cage-kiosk/cage/pull/525)), harmless at shutdown for a kiosk but a sign the path gets little attention. nixpkgs' Cage 0.3.1 still has `-m last`. nixpkgs also packages `wlr-randr` 0.5.0 and `kanshi` 1.9.0 at the pinned rev; Cage implements the output-management protocol (calls `wlr_output_manager_v1_set_configuration` in output.c).
- **Kernel-level alternative:** `video=<connector>:d` disables a connector from boot, for DRM drivers ([kernel modedb docs](https://docs.kernel.org/fb/modedb.html)); the connector name (`eDP-1`, `LVDS-1`) is read from `/sys/class/drm`. The evaluation check accepted `boot.kernelParams = [ "video=eDP-1:d" ]`. Trade-off: with the panel disabled and the adapter unplugged, Cage has zero outputs ([Cage #532](https://github.com/cage-kiosk/cage/issues/532), open, discusses keeping view sizes when outputs vanish).
- **NixOS Cage module knobs:** `services.cage.extraArguments` (list of strings passed to Cage) and `services.cage.environment` (env of the unit) exist; the unit runs `cage <extraArguments> -- <program>` on tty1 as `services.cage.user` ([cage.nix](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/services/wayland/cage.nix)).
- **Lid and AC, option names on current nixos-unstable (verified by source and evaluation at the pinned rev):** the old flat options were renamed; use `services.logind.settings.Login.HandleLidSwitch`, `...HandleLidSwitchExternalPower`, `...HandleLidSwitchDocked` (the module has `mkRenamedOptionModule` entries from `services.logind.lidSwitch`, `lidSwitchExternalPower`, `lidSwitchDocked`; `services.logind.extraConfig` was removed) ([logind.nix](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/system/boot/systemd/logind.nix)). Semantics from logind.conf(5): `HandleLidSwitch` defaults to `suspend`; `HandleLidSwitchExternalPower` is ignored unless explicitly set; `HandleLidSwitchDocked` defaults to `ignore` and applies when docked or when more than one display is connected ([logind.conf.xml](https://github.com/systemd/systemd/blob/main/man/logind.conf.xml)). Setting `HandleLidSwitch = "ignore"` alone therefore covers battery and AC; setting all three is explicit and costs nothing. The rendered `/etc/systemd/logind.conf` came out as `HandleLidSwitch=ignore`, `HandleLidSwitchDocked=ignore`, `HandleLidSwitchExternalPower=ignore`, `KillUserProcesses=false`.
- **Blocking suspend entirely:** `systemd.sleep.settings.Sleep.AllowSuspend = "no"` (plus `AllowHibernation`, `AllowSuspendThenHibernate`, `AllowHybridSleep`) evaluates and renders `/etc/systemd/sleep.conf` with those keys. This also avoids the DisplayLink pre-sleep hook issue (Q2).

**Implications for this repo:** To show the kiosk on the USB display and not the panel, the simplest working set is `services.cage.extraArguments = [ "-m" "last" ]`, with the kernel `video=<panel>:d` parameter as the belt-and-braces alternative (decide based on whether having the panel as a fallback is wanted). Lid-closed operation needs only `HandleLidSwitch = "ignore"`; the sleep settings are cheap insurance. Closed-lid thermals on an 8 GB old laptop are an operational question the repo cannot answer (Unknown). Eval-checked sketch:

```nix
services.cage.extraArguments = [ "-m" "last" ];
services.logind.settings.Login = {
  HandleLidSwitch = "ignore";
  HandleLidSwitchExternalPower = "ignore";
  HandleLidSwitchDocked = "ignore";
};
systemd.sleep.settings.Sleep = {
  AllowSuspend = "no"; AllowHibernation = "no";
  AllowSuspendThenHibernate = "no"; AllowHybridSleep = "no";
};
```

### 7. Fallback if Cage cannot drive the adapter

**Findings**

- **Why X11 is the safer path for DisplayLink:** it is the original, documented target (the NixOS module's X pieces, DisplayLink's known-issues page, evdi README with `xrandr --listproviders` examples) and the reports in Q3 were all Wayland-compositor-specific. Caveats on the X side: evdi README says Xorg builds static GPU lists and wants `initial_device_count` (so `boot.extraModprobeConfig = "options evdi initial_device_count=1"`; the option accepts it, name from [module README](https://github.com/DisplayLink/evdi/blob/main/module/README.md)); the module hardcodes `xrandr --setprovideroutputsource 1 0` in `services.xserver.displayManager.sessionCommands` (provider numbers must match `xrandr --listproviders`); the proprietary NVIDIA driver is out of the picture (Q4). The evdi output is named like `DVI-I-1-1` in xrandr (README example).
- **Option names verified by evaluation at the pinned rev** (a kiosk session with auto-login; xserver enabled, `displaylink` and `modesetting` as video drivers, zero failing assertions):
  - `services.xserver.enable = true;`, `services.xserver.videoDrivers = [ "displaylink" "modesetting" ];`
  - `services.displayManager.autoLogin = { enable = true; user = "kiosk"; };` and `services.displayManager.defaultSession = "kiosk";` (current location; nixpkgs' own removal message for the LightDM-specific auto-login options points to `services.displayManager.autoLogin`, [rename.nix](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/rename.nix)).
  - A custom session via `services.xserver.displayManager.session = [ { manage = "desktop"; name = "kiosk"; start = '' <command> & waitPID=$! ''; } ];` (documented option, [display-managers/default.nix](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/services/x11/display-managers/default.nix)); it needs a display manager that supports X sessions, here `services.xserver.displayManager.lightdm.enable = true;`.
  - A window manager if one is wanted: `services.xserver.windowManager.openbox.enable = true;` (also evaluated).
  - Lighter alternative: `services.xserver.displayManager.startx.enable` with `generateScript` for a manual `startx` ([startx.nix](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/services/x11/display-managers/startx.nix)); this one I did not evaluate, and it needs a tty auto-login on top.
  - To pick the output in the session script: `xrandr --output <panel> --off --output <evdi output> --auto` (xrandr 1.5.4 in nixpkgs).
- **Mutter route, as the only compositor DisplayLink officially names for Wayland:** nixpkgs has no GNOME Kiosk package (no `gnome-kiosk` in the tree listing), so this means a full GNOME session with auto-login and an autostart browser. Unverified as a kiosk, and heavy for 8 GB. nixpkgs also has `weston`, `cagebreak` and `labwc` ([tree](https://github.com/NixOS/nixpkgs/tree/master/pkgs/by-name)); the Arch thread reported Weston started but did not drive the DisplayLink outputs ([thread](https://bbs.archlinux.org/viewtopic.php?id=308317)).

**Implications for this repo:** Keep the X11 kiosk as a documented plan B in the host's comments or a secondary specialisation, not as code that runs by default. It is cheap to write (about ten lines using the verified options above) and avoids every wlroots-specific unknown, at the price of a DM plus X on an old laptop, and X11 has its own Widevine and compositing questions for the browser that are outside this note.

### Open questions

Run on the box (antiX today; plain single commands with pipes, so they work in bash and in Nushell; `sudo` where noted). Paste the full output back:

1. `lsusb` (all lines; the adapter is probably one with vendor `17e9`, `090c`, `1d5c` or `0711`).
2. `lsusb -t` (the driver column per interface: `udl` means the kernel path; `snd-usb-audio` on another interface means the adapter carries audio).
3. `sudo lsusb -v -d 17e9:` (replace `17e9` with the vendor found in 1): interface class/subclass/protocol decide `udl` (protocol 0) vs evdi plus daemon (protocol 3).
4. `lsmod | grep -E "udl|evdi|nvidia|nouveau|i915"` and `dpkg -l | grep -i -E "displaylink|evdi|nvidia"`: tells whether something DisplayLink-related was ever installed on antiX, which drivers are really in use, and which NVIDIA branch was hand-installed.
5. `lspci -nn | grep -i -E "vga|3d|display"`: the Intel and NVIDIA device IDs (maps the NVIDIA to its legacy branch).
6. `cat /sys/class/dmi/id/product_name` and `ls /sys/class/drm`: the laptop model, and the connector names (internal panel `eDP-1` or `LVDS-1`, any HDMI/VGA/DP ports and which `cardN` they hang on).
7. `ls -l /dev/dri/by-path`: the Intel render node's PCI path for `WLR_RENDER_DRM_DEVICE`, and the USB card's entry.
8. `aplay -l`: is there a USB audio card from the adapter.
9. `xrandr --listproviders` and `xrandr` (while the projector is up): resolution and refresh rate in use, output name for the USB display, whether a provider is a "Sink Output".
10. `ps aux | grep -i displaylink`: is the DisplayLink daemon running on antiX.
