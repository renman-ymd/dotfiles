## Helium for the streaming box

All facts below were read on 2026-10-12 from the sources linked inline (GitHub API reads of default branches, so "main" links will drift). Items marked "Unverified:" or "Unknown:" could not be settled from primary sources.

### 1. What Helium is

**Findings**

- **Base.** Helium is a Chromium-based browser built from a fork of ungoogled-chromium that the README calls "heavily modified for Helium". It also carries patches from Inox, Debian, Bromite, Iridium and Brave ([README](https://github.com/imputnet/helium#credits)). It tracks Chromium closely: `chromium_version.txt` on main is 155.0.8059.39 ([file](https://github.com/imputnet/helium/blob/main/chromium_version.txt)), and release 0.19.1 (2026-10-07) is the "update to chromium 155.0.8059.39" release ([release notes](https://github.com/imputnet/helium/releases/tag/0.19.1)). The homepage says all Google service dependencies are removed ([helium.computer](https://helium.computer/)).
- **Maintainer.** The GitHub org is `imputnet`, described as "two guys behind helium, cobalt, and meow.camera" with blog imput.net ([org](https://github.com/imputnet)). The humans who answer issues and decide things are `wukko` and `dumbmoron` (for example [helium#2389](https://github.com/imputnet/helium/issues/2389), [helium#2643](https://github.com/imputnet/helium/issues/2643)). Funding is crowdfunded sponsorship per the homepage FAQ.
- **Status.** The README flags Helium as beta ([README](https://github.com/imputnet/helium#downloads)). The repo was created 2025-02-15. The Linux packaging repo has 106 tagged releases since 2025-08-24, 25 of them in the last 90 days ([releases](https://github.com/imputnet/helium-linux/releases)), so several per week. The Helium version number is its own (0.19.2.1), not Chromium's.
- **Latest Linux release today:** `0.19.2.1`, published 2026-10-08 ([release](https://github.com/imputnet/helium-linux/releases/tag/0.19.2.1)). Its changelog lists browser-level exceptions for some Google services, restored DBSC flags and a revision bump. CI builds it (author `github-actions[bot]`). Assets for x86_64: `helium-0.19.2.1-x86_64_linux.tar.xz` (121.6 MB, with a detached `.asc`), `helium-0.19.2.1-x86_64.AppImage` (158.5 MB), `helium-bin_0.19.2.1-1_amd64.deb` (127 MB); arm64 equivalents exist.
- **License.** GPL-3.0 for everything unique to Helium. Imported code keeps its own license (for example BSD-3-Clause for ungoogled-chromium material) ([README](https://github.com/imputnet/helium#license), [helium-linux README](https://github.com/imputnet/helium-linux#license)).
- **Platforms and Linux formats.** macOS 13+, Windows 10+, Linux on x86_64 and arm64 ([download page](https://helium.computer/download)). Official Linux formats per the [helium-linux README](https://github.com/imputnet/helium-linux#downloads): Fedora COPR (`helium-bin`), a Debian/Ubuntu apt repo at `pkg.helium.computer` (`helium-bin`), AppImage, and a binary tarball. The README says other packaging is not officially maintained, and says Flatpak will not be supported because it weakens Chromium's sandbox. Tarballs, AppImages and the apt repo are PGP-signed (key fingerprint `BE67 7C19 89D3 5EAB 2C5F 26C9 3516 01AD 01D6 378E`).
- **Linux build flags** worth knowing ([flags.linux.gn](https://github.com/imputnet/helium-linux/blob/main/flags.linux.gn)): `proprietary_codecs=true` with `ffmpeg_branding="Chrome"` (H.264/AAC present), `use_vaapi=true`, `rtc_use_pipewire=true`.
- **Tarball layout.** The launcher is `helium-wrapper`, which sets `LD_LIBRARY_PATH` and `exec`s the `helium` binary, passing all arguments through ([wrapper](https://github.com/imputnet/helium-linux/blob/main/package/helium-wrapper.sh)). The AppImage wrapper additionally tries to create an AppArmor profile through `pkexec`/`sudo` on AppArmor systems ([wrapper](https://github.com/imputnet/helium-linux/blob/main/package/helium-wrapper-appimage.sh)).

**Implications for this repo:** Helium is a real, actively shipped Chromium fork with a fast release cadence and an official x86_64 tarball, which is the easiest thing to wrap in Nix. It is beta, maintained by two people, and tracks Chromium within days, so on an exposed-to-the-web kiosk it would need a regular version/hash bump (analysis). Its selling points (ad/tracker blocking, privacy, vertical tabs, bangs) do not matter on a projector kiosk; the only things that matter here are Widevine, kiosk and Wayland behaviour, and footprint, covered below.

### 2. Packaging: nixpkgs and community flakes

**Findings**

- **Not in nixpkgs.** `pkgs/by-name/he/` has no `helium*` entry on `master`, `nixos-unstable` or `nixos-26.05` (checked via the [contents API](https://github.com/NixOS/nixpkgs/tree/master/pkgs/by-name/he)), and `pkgs/top-level/all-packages.nix` on master has no match for "helium". I did not query search.nixos.org (JS-driven; not read). Unverified: that nothing exists under a different attribute name outside `by-name`.
- **One open nixpkgs PR:** [NixOS/nixpkgs#498572](https://github.com/NixOS/nixpkgs/pull/498572), "helium: init at 0.15.6", opened 2026-03-10. It builds Helium from source through the existing Chromium/ungoogled infrastructure (adds `variants/helium`). As of its last update (2026-08-31) it has a merge-conflict label, no review decision, and the author reports 15-hour local builds and no binary cache. It is stuck at 0.15.6 while upstream is at 0.19.2. Earlier init PRs were closed: #450560 was the from-source predecessor of #498572 (per its description), #518351 and #536771 (AppImage-based) were closed because #498572 already existed, and I did not read why #444577 and #468671 were closed. In [#550859](https://github.com/NixOS/nixpkgs/pull/550859) a commenter says all attempts stall on needing a committer because browsers get stricter review.
- **Community flakes** (all pushed 2026-10-09 or 2026-10-11, all at 0.19.2.1, i.e. current):

  | Flake | Packaging method | Extras | Stars / license |
  |---|---|---|---|
  | [amaanq/helium-flake](https://github.com/amaanq/helium-flake) | official `tar.xz` + `autoPatchelfHook` + `makeWrapper` | `versions.json` auto-updated; `helium-widevine` variant (see Q3); honours `NIXOS_OZONE_WL` | 46, GPL-3.0 |
  | [oxcl/nix-flake-helium-browser](https://github.com/oxcl/nix-flake-helium-browser) | official `.deb` extracted + `patchelf` + `wrapGAppsHook` | NixOS module `programs.helium` (flags, policies to `/etc/chromium/policies/managed/`), Home Manager module, overlay; x86_64 and aarch64 | 104 |
  | [schembriaiden/helium-browser-nix-flake](https://github.com/schembriaiden/helium-browser-nix-flake) | official `tar.xz` + `autoPatchelfHook` | overlay, follows `nixos-unstable` | 115, MIT |

  Others exist (`FKouhai/helium2nix`, `cjavad/nixpille-helium`, `J0schu/helium.nix` and `AARayane/logpose`, which say they package the AppImage). I did not read those. The first three were bumped to 0.19.2.1 on 2026-10-09, about a day after the upstream tag (commit history); oxcl advertises auto-updates, and I did not inspect the others' CI.
- **How hard to package yourself.** Three independent flakes already do it with the same recipe: fetch the release tarball, `autoPatchelfHook` with a list of ~30 runtime libs (glib, gtk3, nss, nspr, cups, alsa-lib, libdrm, mesa, pipewire, libva, wayland, ...), ignore the missing Qt5/Qt6 shim libs (`libQt5Core.so.5` and so on), wrap `helium-wrapper` with an `LD_LIBRARY_PATH` for libGL/libva/pipewire/libpulseaudio, copy the `.desktop` file and icon. amaanq's `package.nix` is about 170 lines ([source](https://github.com/amaanq/helium-flake/blob/main/package.nix)). `appimageTools.wrapType2` is the alternative the question raised; I found no first-hand evidence that anyone does this for Helium, and the tarball route has more precedent. Unverified: whether the AppImage is type 2.

**Implications for this repo:** There is no `pkgs.helium`. The realistic options are (a) add a community flake as an input (`inputs.nixpkgs.follows = "nixpkgs"`), with an overlay or direct package reference, or (b) vendor a ~170-line `package.nix` pinned to a release hash (the repo already has the habit of pinning; a vendored derivation avoids trusting a third-party flake with code that runs as a browser). Neither is cached by Hydra, but both only fetch a prebuilt tarball, so there is no compile. Option (b) needs a hash bump per update, option (a) delegates that to the flake author (analysis). Helium itself is GPL-3.0 (no `allowUnfree` needed), but Widevine (Q3) is unfree.

### 3. Widevine / DRM in Helium on Linux

**Findings**

- **Official position: no Widevine.** The homepage FAQ says Helium does not support Widevine DRM and some streaming services will not play, blaming Google's licensing restrictions and the recurring fees charged by third-party partners ([FAQ](https://helium.computer/)). The maintainers contacted Widevine in 2025; the reply sent them to Widevine's "3PL" integrator partners ([helium#116 comment, 2025-10-09](https://github.com/imputnet/helium/issues/116)). They said earlier they might look into it if someone funds roughly ten thousand dollars or more. As of 2026-08-25 a maintainer says nothing has changed ([helium#2389](https://github.com/imputnet/helium/issues/2389)), and on 2026-10-04 a maintainer says Widevine is not supported "at the moment" and so they would not investigate a sideload bug (a macOS report) ([helium#2643](https://github.com/imputnet/helium/issues/2643)). The tracking issue [#116](https://github.com/imputnet/helium/issues/116) is open but locked; #2389, #2643, #911 and others are closed as duplicates of it.
- **The CDM is not bundled and not downloaded.**
  - Helium builds with `enable_widevine=true` ([flags.gn](https://github.com/imputnet/helium/blob/main/flags.gn)), so the loader is compiled in. Upstream, `bundle_widevine_cdm` is true only for Chrome-branded builds ([widevine.gni](https://github.com/chromium/chromium/blob/main/third_party/widevine/cdm/widevine.gni)), and neither Helium flags file overrides it.
  - Helium's `component-updates.patch` blocks every component except two IDs: CRLSet and WidevineCdm (`oimompecagnajdejgnnjijobebaeigek`). It also redirects component update traffic to Helium's own proxy (`/com`) rather than Google, and only when the user has consented to Helium services ([patch](https://github.com/imputnet/helium/blob/main/patches/helium/core/component-updates.patch)).
  - That proxy's allowlist at main contains only CRLSet ([helpers.ts](https://github.com/imputnet/helium-services/blob/main/svc/extension-proxy/lib/helpers.ts)), forwards to Google's update endpoint ([constants.ts](https://github.com/imputnet/helium-services/blob/main/svc/extension-proxy/lib/omaha/constants.ts)), and rejects requests with no allowed IDs. Analysis: this explains the user report of Widevine stuck at version `0.0.0.0` with status "Update error" and an empty `WidevineCdm` dir on the Linux AppImage ([helium-linux#331](https://github.com/imputnet/helium-linux/issues/331), v0.13.6.1, closed as a duplicate by a maintainer).
  - [PR #822](https://github.com/imputnet/helium/pull/822) (merged 2026-01-26) re-allowed the WidevineCdm component installer so that a sideloaded CDM is picked up "on some platforms". [PR #731](https://github.com/imputnet/helium/pull/731) (an AI-assisted attempt) was closed unmerged.
- **Sideloading works for some users (user reports, not maintainer-documented):**
  - Helium on Linux: copying the whole `WidevineCdm` directory from Brave into `~/.config/net.imput.helium/WidevineCdm` changed the reported version from `0.0.0.0` to `4.10.3050.0`, and Apple Music protected playback worked ([helium-linux#331](https://github.com/imputnet/helium-linux/issues/331)).
  - Symlinking Chrome's `WidevineCdm` next to the Helium binary on CachyOS worked on the Bitmovin demo (2025-10-28); another Arch user with `chromium-widevine` could not get DRM content working (2025-12-15) ([helium#116](https://github.com/imputnet/helium/issues/116)).
  - A user posted a hint-file method that works for AppImage and tarball: write `{"Path":"<CDM dir>"}` into `~/.config/net.imput.helium/WidevineCdm/latest-component-updated-widevine-cdm` (same thread, 2025-12-18).
  - Crunchyroll specifically: one Windows user watched anime on Crunchyroll after copying Google's Widevine folder, before Helium 0.7.4.1 restricted components ([helium#669](https://github.com/imputnet/helium/issues/669)). A Windows user on 0.15.6.1 got Crunchyroll error KAT-6005 with no answer ([helium#2366](https://github.com/imputnet/helium/issues/2366)). I found no Linux Crunchyroll report for Helium. Unknown: whether Crunchyroll works on Helium/Linux.
  - A maintainer wrote in 2025-09 that with the Chrome-folder workaround Netflix still failed and Spotify worked for about a third of songs (platform not stated; the issue was filed from Windows). One commenter speculates that Windows and macOS need a verified-media-path licence that Linux does not (Unverified: user opinion, no source). Treat the maintainer's remark as a caution, not a Linux result.
- **Upstream mechanics** (Chromium source, so these hold for a Chromium-155-based Helium unless Helium patches them; I found no Helium patch touching them):
  - On Linux the browser reads a hint file at `<user-data-dir>/WidevineCdm/latest-component-updated-widevine-cdm` ([chrome_paths.cc](https://github.com/chromium/chromium/blob/main/chrome/common/chrome_paths.cc)). The file is JSON with a `Path` key ([hint file code](https://github.com/chromium/chromium/blob/main/chrome/common/media/component_widevine_cdm_hint_file_linux.cc)). The directory it names must contain `manifest.json` and `_platform_specific/linux_x64/libwidevinecdm.so` ([cdm_registration.cc](https://github.com/chromium/chromium/blob/main/chrome/common/media/cdm_registration.cc)). The Widevine component installer policy writes the hint file when a CDM version becomes ready ([installer](https://github.com/chromium/chromium/blob/main/chrome/browser/component_updater/widevine_cdm_component_installer.cc)). Analysis: the sideload layout in the next bullet depends on that component being registered, which is why the allowlist change in #822 matters; I did not read the generic component-installer code that scans the install directory.
  - The ungoogled-chromium wiki describes the same layout: place the CDM under the user-data dir's `WidevineCdm/<version>/`, make `libwidevinecdm.so` executable, and use a Chrome of the same major version to avoid crashes ([wiki FAQ](https://github.com/ungoogled-software/ungoogled-chromium-wiki/blob/master/faq.md)). It also says to pass `--enable-widevine`; I found no source for that switch in Helium or ungoogled-chromium and do not know whether it exists.
  - Unknown: why the "symlink next to the binary" reports worked for some users. Upstream only reads the binary-adjacent directory when `BUNDLE_WIDEVINE_CDM` is set, and Helium's flags do not set it.
- **Nix-side ingredients exist.** nixpkgs `widevine-cdm` (unfree, version 4.10.3050.0 as of the 2026-06-05 bump) installs `share/google/chrome/WidevineCdm/{manifest.json,LICENSE.txt,_platform_specific/linux_x64/libwidevinecdm.so}` ([package](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/wi/widevine-cdm/x86_64-linux.nix)), which matches the directory shape the loader expects. 4.10.3050.0 is the same version the Brave-copy workaround in #331 reported. `amaanq/helium-flake` adds a `helium-widevine` output (commits of 2026-07-29) that symlinks that directory to `$out/opt/helium/WidevineCdm`, i.e. the binary-adjacent location ([package.nix](https://github.com/amaanq/helium-flake/blob/main/package.nix), [flake.nix](https://github.com/amaanq/helium-flake/blob/main/flake.nix)). Unverified: that this variant actually yields working DRM on current Helium, since the repo shows no test evidence and the adjacent-dir mechanism is unexplained (see above).

**Implications for this repo:** Helium is a poor fit for the one hard requirement (Crunchyroll via Widevine). It is the only candidate of the three (Chrome, Chromium+`enableWideVine`, Firefox) whose maintainers say DRM is unsupported, will not triage DRM bugs, and (on my reading of the allowlist above) have a proxy that currently would not serve the CDM. If used anyway, the declarative route would be: package `widevine-cdm` from nixpkgs (allowUnfree for that one package), and write a hint file `{"Path": "<store path>/share/google/chrome/WidevineCdm"}` into `~/.config/net.imput.helium/WidevineCdm/latest-component-updated-widevine-cdm` before the kiosk starts (for example from a systemd `ExecStartPre` or `systemd.tmpfiles`). That route follows the Chromium source and one user report but nobody has demonstrated it on Crunchyroll with Helium on Linux, so it needs a test on the real box before anything is committed (analysis). Each Helium bump to a new Chromium major could also change Widevine compatibility, as the ungoogled wiki warns (analysis).

### 4. Kiosk and Wayland behaviour

**Findings**

- **`--kiosk`.** Upstream Chromium defines `--kiosk` ([chrome_switches.h](https://github.com/chromium/chromium/blob/main/chrome/common/chrome_switches.h)) and, when it is present, toggles fullscreen on startup ([startup_browser_creator_impl.cc](https://github.com/chromium/chromium/blob/main/chrome/browser/ui/startup/startup_browser_creator_impl.cc)). GitHub code search over `imputnet/helium` finds no patch touching `kKioskMode`; the four files that mention "kiosk" only touch ChromeOS kiosk help links, the user-education check, a manifest header list, and a comment in the fullscreen-exit patch. Helium's wrapper passes arguments straight through. No issue in the imputnet org mentions `--kiosk`. Unverified: that `--kiosk` works in Helium 0.19.2 (no test, no report either way).
- **Kiosk-friendly extras in Helium.** `patches/series` includes ungoogled-chromium's `add-flag-to-hide-fullscreen-exit-ui.patch`, which adds `--hide-fullscreen-exit-ui` to hide the top "X" control and the "press F11 to exit" popup ([series](https://github.com/imputnet/helium/blob/main/patches/series), [patch](https://github.com/imputnet/helium/blob/main/patches/ungoogled-chromium/add-flag-to-hide-fullscreen-exit-ui.patch)).
- **First run.** Helium's onboarding patch replaces the start tabs with Helium's setup page on first launch (pref `kHeliumDidOnboarding` false) unless `--no-first-run` is passed or the window is incognito/guest ([patch](https://github.com/imputnet/helium/blob/main/patches/helium/core/onboarding-page.patch)). The homepage says Helium makes no web requests on first launch and that every request to Helium services needs the user's approval.
- **Wayland.** The Chromium tree builds the Wayland Ozone backend by default and selects it with `--ozone-platform=wayland` ([ozone_overview.md](https://github.com/chromium/chromium/blob/main/docs/ozone_overview.md)); Helium's flags do not disable it. Helium on Wayland is widely exercised: helium-linux has dozens of open and closed issues mentioning Wayland, reported on KDE, GNOME, niri and Hyprland (for example [#364](https://github.com/imputnet/helium-linux/issues/364) drag-and-drop hang, [#222](https://github.com/imputnet/helium-linux/issues/222) unstable UI on KDE, [#205](https://github.com/imputnet/helium-linux/issues/205) window not filling the screen when maximized, [#407](https://github.com/imputnet/helium-linux/issues/407) GNOME on-screen keyboard, closed). One user passes `--ozone-platform=wayland` to Helium in a `.desktop` file ([helium-linux#246](https://github.com/imputnet/helium-linux/issues/246)), so the switch is accepted.
- **Intel iGPU.** [helium-linux#302](https://github.com/imputnet/helium-linux/issues/302) (open): brief checkerboard flash on every click under Wayland with Intel iGPU plus an NVIDIA Optimus dGPU on Fedora/KDE, not reproduced in Brave by the reporter. [helium-linux#246](https://github.com/imputnet/helium-linux/issues/246) (open): HEVC video not rendering on 0.11.1.1 with a VA-API init error (also seen in ungoogled-chromium). Both are single-user reports on different hardware.
- **Cage / wlroots.** I found no Helium issue mentioning Cage, labwc or sway kiosks (searches on the imputnet repos returned only unrelated hits). General Chromium-under-Cage facts, not Helium-specific: Cage v0.3.1 (2026-06-30, also the version in `nixos-unstable`) includes [cage#504](https://github.com/cage-kiosk/cage/pull/504), which fixes windows that request fullscreen at startup, with `chromium --kiosk` named as an affected case. [cage#320](https://github.com/cage-kiosk/cage/issues/320) (open) reports that Chromium and Firefox kiosk modes still accept Ctrl+T and Ctrl+W under Cage and Sway.

**Implications for this repo:** Nothing in the sources blocks running Helium as `cage -- helium --ozone-platform=wayland --kiosk --no-first-run <url>`. That is untested; it relies on upstream Chromium behaviour that Helium does not appear to patch away. Add `--hide-fullscreen-exit-ui` if the exit popup shows on the projector. Keyboard shortcuts escaping the kiosk (Ctrl+W and so on) is an upstream Chromium and Cage property, not a Helium regression; if it matters, Chromium enterprise policies (which the community NixOS module writes to `/etc/chromium/policies/managed/`) are one lever (analysis, untested). Use a recent Cage (0.3.1 or later) so `--kiosk` fullscreen works. The Intel-iGPU and VA-API reports are not conclusive for a plain Intel-only box; they argue for a test on the real hardware (analysis).

### 5. Resource footprint versus Firefox

**Findings**

- Unknown: I found no first-party or reproducible measurement of Helium's memory or CPU use against Firefox or any other browser. The helium.computer homepage claims minimal resource use and efficiency "by default" with no numbers or method ([homepage](https://helium.computer/)). Searches of the imputnet issue trackers for benchmarks, memory and RAM turned up user bug reports only, none with a comparison.
- A maintainer's only statement on the subject: Helium suspends inactive tabs aggressively and offers a manual "hibernate tab" action ([helium#1922](https://github.com/imputnet/helium/issues/1922), where a Windows user reported about 1.1 GB across 17 processes for one heavy page on an 8 GB machine, with no Firefox comparison). That is an anecdote, not a measurement.
- Helium is a Chromium fork, so it uses Chromium's multi-process architecture (README and tree layout); nothing I read says it changes that.

**Implications for this repo:** No evidence either way that Helium is lighter than Firefox or than stock Chromium/Chrome for one playing-video tab. For a single-tab, single-site kiosk the tab-hibernation feature is moot (analysis). If footprint is a deciding factor, the only way to settle it is to measure the candidates on the actual 8 GB box with the same Crunchyroll stream.

### Open questions

1. Does Crunchyroll actually play on Helium 0.19.x on Linux with a sideloaded Widevine (nixpkgs `widevine-cdm` via hint file)? No source answers this; it needs a test on the box.
2. Why do binary-adjacent `WidevineCdm` symlinks work for some users when `BUNDLE_WIDEVINE_CDM` is off? Does the `helium-widevine` output of `amaanq/helium-flake` really work? Unknown.
3. Does `--kiosk` (plus `--no-first-run`) behave correctly in Helium 0.19.2 under Cage 0.3.1? Not tested by anyone I could find.
4. Does Crunchyroll treat Helium differently (unsupported browser, error KAT-6005 as seen on Windows)? Unknown.
5. Memory/CPU comparison against Firefox and Chrome for this workload: Unknown, needs on-box measurement.
6. Decision for Renaud: is a beta browser whose maintainers disclaim DRM support acceptable for the one function the box exists to do?
7. Not checked: search.nixos.org (JS app); the AppImage-based community flakes (`J0schu/helium.nix`, `AARayane/logpose`); whether the AppImage is a type-2 AppImage.
